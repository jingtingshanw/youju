# 有据 · 产品入口（app/）

一句人话进去，一份能自己验的回答出来。

```bash
python app/server.py        # → http://127.0.0.1:8848
python app/trace.py --report   # 看攒下来的 badcase
```

零依赖，只用 Python 标准库。启动时只读打开 `data/kb.db`（935 MB）和 `data/catalog.db`（56 MB），
不建索引、不写缓存，秒级启动。埋点写 `data/app.db`。

---

## 一、六步，三处在人手里

| | 谁 | 做什么 | 界面上是 |
|---|---|---|---|
| 1 | **人** | 说出需求，可以模糊 | 一个输入框 |
| 2 | 机器 | 拆成取证方向 | 指令卡 |
| 3 | 机器 | 按方向找文件 | 候选列表 |
| 4 | **人** | 确认用哪些 | 勾选框 |
| 5 | 机器 | 写判断、依据、路径、缺口、下一步 | 五段回答 |
| 6 | **人** | 说哪里不对 | 「本次留痕 N」 |

第 2 步拆完可以改、可以补方向，但那不是必须动作。必须人动手的只有第 1、4、6 步。

**为什么中间非要停一次**：一个方向 20 条候选，哪些算「这个项目要用」是判断，不是检索。
工具替你判断，你就永远不知道它丢了什么。

## 二、四屏怎么读

### 第 1 屏 · 提问

下面三行是库的实际情况，不是宣传：全文库 21,774 份可引原文（国家 18,608 / 江苏省 1,585 /
南京市 1,581）；地方目录 66,692 条，其中 3,166 条已补抓正文，其余只有标题、文号、链接；
失效台账覆盖全部 21,774 份，分四态：

| 状态 | 份数 | 判据 | 界面 |
|---|---|---|---|
| `repealed` 已废止 | 795 | 源站标记 702 份；另有后代文件正文点名废止 | C3 判失败 |
| `superseded` 旧版本 | 29 | 同名的更新版本已入库 | C3 判失败，并给出新版名与日期 |
| `no_signal` 未见废止 | 20,950 | 全库正文里没有一份说它失效 | C3 判通过 |
| `unknown` 目录层 | 66,692 条 | 只有标题，没有正文可查 | C3 判未知 |

**`no_signal` 不是「确认有效」，是「全库读过，没有一份说它失效」**——这是一个有依据的判断，
能写进界面；`unknown` 不能。

### 第 2 屏 · 指令

每条指令给四样东西：**查哪个范围**（南京市 / 江苏省 / 国家 / 不限）、**找哪一类文件**
（本地法规 / 本地规划 / 本地政策 / 省级法规 / 省级政策 / 国家法规 / 国家政策 / 同类案例 /
技术标准）、**为什么必须有它**、**用哪些词去撞标题**。

- 带 `必查` 的不能删——五层取证里缺一层，结论就有盲区。
- 带 `自动补齐` 的是模型漏掉、代码补的。看到这个标签说明那次拆解不完整。
- 关键词是可改的。改词比改标题有用：库里只有标题，词必须出现在文件名里。

### 第 3 屏 · 候选

顶部一行：`候选 60 份 · 已选 10 份 · 其中 5 份有正文可引原文`。最后一个数字只统计
**已勾选**的文件——它决定这份报告里有多少引注能回原文核对。

每条候选三个标签，都要看：

| 标签 | 含义 |
|---|---|
| `条例` `法律` `办法` `规划` `名录` `批复` `通知` | 文件形态。判断这是硬依据还是软要求，主要看这个 |
| `有正文` / `仅公告` / `仅目录` | 有正文能引到条；仅公告是源站只发了几百字公告、本体是图件；仅目录只能确认存在 |
| `同类` | 灰色。标题里没出现这件事的名字，只是沾边。没这个标签 = 直接命中 |

方向头上给一句汇总：「直接命中 6 份，其余为同类」，或者「没有专门针对本项目的，
以下是同类」。**这一句比在每一条上标一遍有用**——四层全命中时，逐条标等于没标。

`另有 N 条同模板文件` 是把「国务院关于同意将 X 列为国家历史文化名城的批复」这种
一份一份发了几十遍的文件折叠成一条。鼠标停上去能看到几个例子。57 条国家法规折叠
成 12 条，不然《历史文化名城名镇名村保护条例》要滑过十几屏才看得见。

`另 N 个方向也有` 是重复提醒：同一份文件可能被两条指令同时捞到，勾一次就够。

### 每个方向按什么排

**一、形态必须先对上。** 法规方向只收条例、法律、规章、办法；规划方向只收规划和批复。
不设这道闸，「本地法规」里会躺着《南京总统府历史文化街区保护规划（批后公布）》——
它命中了「历史文化街区保护」这个关键词，但它不是法规。用户看到「法规」分类里混着
规划，会怀疑整个分类是不是在瞎标。

**二、法规方向要按目录兜底，不能只按关键词。** 法规标题不一定含问题里的词。
《南京市夫子庙秦淮风光带风景名胜区条例》管的就是老门西所在那一带，但标题里没有
「历史文化街区」五个字，纯关键词永远召回不了。所以关键词命中少于 3 条时，会按
「本市 + 条例/办法」把目录翻一遍，再用主题词筛（历史、遗产、文物、街区、陵墓、
石刻、城墙、秦淮…）。南京 8 条法规全是有正文的，包括那部夫子庙条例。

主题词不能用「保护」「文化」「建筑」这种谁都能带的字——实测「保护」放进
《南京市水资源保护条例》、「建筑」放进《南京市建筑垃圾资源化利用管理办法》。

**三、同类案例按地域可比性加权。** 同城 +0.18，同省 +0.08，县级 −0.12。
不这样排，第一屏是「芷江侗族自治县历史文化街区、历史地段保护管理办法」——
它的标题同时命中两个领域词，得分 0.85；《南京总统府历史文化街区保护规划》只命中
一个，0.63 排第五。对南京的规划师来说前者是噪音，后者才是他要对照深度要求和审批
流程的那份。加权后南京自己那两份排到前两位。

**四、国家法规要单独兜一次目录层。** 《文物保护法》《城乡规划法》不在 gov.cn 政策
文件库里，只在目录层。不兜的话国家法规方向只剩《历史文化名城名镇名村保护条例》
一条——而规划师做这件事第一顺位要看的就是那两部法。

两个按钮。`只选有正文的` 是把列表收缩成「能引原文」的子集，用于快速出一个全部可核的报告；
`开始撰写` 用当前勾选。

默认勾选分三轮：**① 每个方向一条直接命中的，全局只取一次**（顺序即优先级，一份文件
出现在两个方向时归排在前面的那个）；**② 每个方向补到 3 条**，先有正文的，跳过已被
别处选中的之后继续往下找。

第二轮的「继续往下找」是修出来的：旧版先算出候选再交给 Set 去重，被跳过的位置不补，
案例方向于是拿《六合文庙历史地段保护规划》补位——它跟老门西不在一个量级。

鼠标移到条目上才出现「不相关」，点了会记一条 `mark`——这是最值钱的信号，它说明
排序或分档错了。

### 第 4 屏 · 回答

五段固定结构，不是一段散文：

| 段 | 回答什么 |
|---|---|
| 判断 | **第一句给立场**：能做 / 不能做 / 有条件能做。不要「视情况而定」 |
| 依据 | 分三档：硬约束 / 程序义务 / 可争取的空间。只写有正文的文件 |
| 路径 | 2—4 条路子，每条写清审批层级、周期、代价，按代价从小到大排 |
| 缺口 | 哪些方向没找到依据，没找到意味着什么 |
| 下一步 | 办什么事、找谁、拿哪条去说 |

「判断」段是第一眼要看的东西。给不出立场，后面写得再全也只是搜索框。

「缺口」通常是最有用的一段。南京老门西那一问的具体产出：

> 市级未检索到针对「老门西」专项编制的历史文化街区保护规划（仅有总统府街区规划），
> 该街区法定保护边界、核心/建设控制地带划分、建筑分类管控要求等关键空间管控依据缺失，
> 直接影响更新方案合规性判定。

这不是「没找到」，是「没找到意味着什么」。只给已有的，用户仍然不知道边界在哪。

回答下方是核验条：强度徽章 + 引注数 / 回原文核对 / 仅目录 / 逐句有出处比例，再下面是
逐条明细。点开每一条能看到五项检查各自判了什么、凭什么这么判。

## 三、几个数字怎么来的

**证据强度只有两档**，不设「弱相关」：直接命中 / 同类相关。弱相关基本等于不相关，
混在列表里只浪费注意力。

直接命中要满足两条里的一条：命中模型排在前两位的词，**或**命中任何 5 字以上的专业词
（历史文化街区、历史文化名城、防止大拆大建）。

只看位置会漏。关键词切分出来的短词排在索引 3、4 上，永远进不了前两位，省级法规
和同类案例两层 22 条候选会全落成「同类」，界面一片灰，用户以为库里没东西。只看
长度也会漏：「城市更新」四个字太宽，可它排在第一位时正是要找的东西。

**只命中泛词就丢掉**。`办法 / 规定 / 通知 / 意见 / 规划 / 试点 / 方案 / 建设 / 发展`
这类词全部命中、不含任何主题词的，直接不进候选——「南京市碳达峰试点方案」命中「试点」，
它跟历史文化街区没关系。

**核验三档**：

| 档 | 含义 | 怎么处理 |
|---|---|---|
| `verified` | 有正文，条号 / 引文 / 名称都对得上 | 可照抄 |
| `unverifiable` | 只有目录条目，能确认文件存在，不能确认内容 | 标「未核内容」，**不参与降级** |
| `failed` | 有正文，但条号不存在 / 引文查不到 / 引错文件 | 必须改 |

`unverifiable` 不降级，因为它是数据边界，不是内容错误。把「地方文件我们只拿到标题」
说成「报告有问题」是错的，说成「这几份文件要回源确认」才对。

**强度按错的比例定**，不按「有没有错」定。15 处里 1 处引文被改写，和 15 处里 8 处条号
不存在，是两件事：前者改那一句就行，后者整篇不能用。

**依据密度只算「依据」段**。结论和下一步本来就是判断和动作，该用自己的话写；拿它们算
「有出处比例」会稳定得到 0.3，然后天天报警，最后没人看这个指标。

## 四、实测（2026-10-24，deepseek-chat）

问题：南京老门西历史文化街区城市更新，建筑高度和密度能不能突破现行控规？

| 步 | 结果 | 耗时 |
|---|---|---|
| 1 → 2 拆解 | 8 条指令（本地法规 / 本地规划 / 本地政策 / 省级法规 / 省级政策 / 国家法规 / 国家政策 / 同类案例） | 4.5–4.8 s |
| 3 取证 | 61–88 份候选（折叠同模板后），其中 40–67 份有正文 | 0.7–0.9 s |
| 4 勾选 | 16 份，全部有正文 | — |
| 5 撰写 + 核验 | 18 处引注全部回原文核对通过，密度 94.7% | 10.1 s |
| 6 留痕 | 每次 2–6 条（`gap` / `unverifiable`） | — |

最近一次（`261024015215-980a99`）：8 条指令 / 61 份候选（40 份有正文）/ 勾 16 份 /
装配正文 24,322 字 / 18 处引注全部 `verified` / 密度 94.7% / **可交付**。

产出 27,777 字，结论是「不能直接突破，合规路径只有两条」，依据按效力排序写满 22 条，
每条都带条号：

- 核心保护范围内原则上不得新建、扩建 → 【《历史文化名城名镇名村保护条例》第二十八条】
- 老城建筑高度未经法定程序不得修改，需调整须经城市设计研究、景观视线分析、专家论证、
  社会公示后报市政府批准 → 【《关于进一步加强老城风貌管控严格控制老城建筑高度规划管理规定的通知》第四条】
- 老城南明清传统民居类型历史风貌区的檐口高度 9–12 米弹性，但用地强度不得改变、
  建筑基地占地不超过可建设用地 15% → 【同上，第八条】
- 建筑密度、间距、退线达不到现行技术标准的，可按保护要求编制方案，专家论证后报市政府批准
  → 【《南京历史文化名城保护条例》第四十二条】
- 控规「修订」与「调整」的分界：涉紫线、道路红线属修订，报市政府审批；其余属调整，
  市规划局审批 → 【《南京市控制性详细规划执行与调整规定》第六条、第八条】

缺口段第一条是**「未检索到老门西历史文化街区保护规划、保护图则的正文，无法核对其中
确定的高度、密度控制指标，这是审批对话中最关键的一份缺失依据」**——这就是规划师
拿到资料后该先问的问题。

**这一轮的变化来自两处，都不在提示词里。**

*一是补数据。* 10-23 时南京 1,581 条全是元信息，依据段只能写「据《X》，该文件已由
某机关发布」；现在能写「保护对象改造利用中建筑密度、间距、退线达不到现行技术标准的，
可经专家论证报市政府批准后实施」。

*二是装配预算的用法。* 原来每份文件固定装 3 块，一份 10,607 字的条例只装 284 字，
一份 1,044 字的规定只装 172 字——它的第三、四、五条（「已批准的控详是…依据」
「哪些情况可局部修改」）正好是答案，模型读不到，只能写「从文件名称看…」。
改成按字数预算装满（每份 1,750 字、上限 14 块、大块装不下就截断）之后，
正文从 13,451 字增到 27,777 字，18 处引注全部落到条号上。

模型从 qwen-plus 换到 deepseek-chat 是因为前者的免费额度用尽（HTTP 403）。
`core.call_llm` 现在会自己往下换，不再整体降级成规则兜底。

## 五、边界

1. **地方正文只补了两个地方。** 66,692 条地方目录里，南京 1,581 条和江苏 1,691 条
   已抓正文（3,166 份 / 1,230 万字），其余 63,526 条仍只有元信息，勾了只能确认
   文件存在，引注会落 `unverifiable`。选这两个地方是因为提问最集中——
   用户问的是南京，上位依据在省。
2. **规划类的正文常常只是个壳。** 保护规划的「批后公布」页往往只有一两百字公告，
   规划本体是图件。这类文件在库里算「有正文」，但引不到条文，界面上标 `仅公告`，
   核验时判 `unverifiable` 而不是 `failed`——判 `failed` 等于把数据边界说成内容错误。
   南京这一类有 136 份（占 8.6%）。
3. **省级历史文化名城保护条例确实不存在。** 江苏只有省政府批复和名录公布通知，
   没有公开的省级保护条例。这一层现在是空的，缺口段会如实写出来。
4. **「未见废止记录」不等于「确认有效」。** 它的依据是「全库 21,774 份正文都读过，
   没有一份说它失效」。源站自己标了 702 份失效。
5. **废止判定按句子语法判宾语，不按最近的两个词判。** 这条是被真实误判逼出来的：
   「根据《土地管理法实施条例》有关规定，经省人民政府研究，决定废止《江苏省征地补偿
   安置争议协调裁决办法》」——按「书名号到废止动词的距离」判，会把《土地管理法实施
   条例》这部核心上位法标成失效。现在按中文废止句的四种语序认宾语（①废止《X》
   ②《X》同时废止 ③《X》《Y》一并废止 ④本规定自…起废止，无宾语不产生边），
   加三道拦截：依据词（根据/依据/按照…）、模态词（应当/需要/建议…）、代词
   （下列/上述/相应…）。
6. **单文件修改决定不判时效。** 「关于修改《X》的决定」废止的是 X 的**旧版本**，
   而库里同名的通常是新版本身——照着判会把《军人抚恤优待条例》这类现行文件标成失效。
   这类只记边、不改状态。但「关于修改和废止部分…的决定」是打包清单，逐条「废止《X》」
   都是真废止，必须判，且要扫正文中段（能列到一百多条，只扫末尾 5,000 字会漏掉前面）。
7. **同名多版本按发布日期切。** 库里有 275 个标题存在多份（新条例与旧条例、修订前后）。
   废止对象只可能是早于废止方发布的那一份，且取其中最晚的——「同时废止」废的是上一版，
   不是最初版。若废止方日期明确但库里没有更早版本，说明被废那版没进库：不判状态。
8. **同名法规有新版入库，旧版直接判 `superseded`。** 新版正文里不一定写「旧版废止」
   （废止说明常在发布令里，不在这份文件里），但同名法规不可能同时有效。这层推断
   不需要原文依据。只对「条例/办法/规定/细则/规则/标准/法」这类法规标题做——
   「通知/意见/批复」是文件容器名，不同年份常讲不同事。
9. **依据密度不是正确率。** 它只说明「这句话在原文里能找到相近的话」，不说明
   「这句话在业务上是对的」。后者要人判断。
10. **依据密度的合理下限还没定。** 同一句问题连跑 12 次，依据段密度落在 30%–70%，
    条文类问题能稳到 90% 以上。现在只当预警用：低于 60% 落一条 `low_trace`，
    不直接降级结论。一个波动 40 个百分点的指标，不能拿来判合格线。
11. **法律本体（《文物保护法》《城乡规划法》）只有目录，没有条文。**
    `flk.npc.gov.cn` 整站被 WAF 挡着，零依赖拿不下来。这两部法只能作事实性陈述，
    引用时落 `unverifiable`。这是目前最要紧的一个缺口——它们是第一顺位依据。

## 接口

界面用 SSE（要进度），外部系统用 JSON（要能挂到百炼/魔笔）。两套并存，同一套阶段函数。

### `/api/*` — 界面用，SSE 流

```
POST /api/plan     {q}                                  → SSE: plan
POST /api/gather   {run_id, plan, scope}                → SSE: gather
POST /api/write    {run_id, q, plan, picked, default}   → SSE: bodies → write → verify → done
POST /api/mark     {run_id, kind, target, note}         → {ok, n}
GET  /api/trace?run_id=…                                → 这次的全部留痕
GET  /                                                  → 界面
```

每一次运行有 `run_id` 贯穿全程。用户在第 2 步改了什么、第 3 步丢了哪份文件，都挂在它下面。

### `/v1/*` — 外部系统用，同步 JSON

```
POST /v1/plan      {q}                                  → {plan}
POST /v1/gather    {plan, scope, run_id}                → {tasks, n_items, n_body, n_web}
POST /v1/write     {q, plan, picked, run_id}            → {answer, verify, bodies}
GET  /v1/coverage                                       → 库与联网的真实边界
GET  /v1/health                                         → 存活与可用模型
GET  /v1/openapi.json                                   → OpenAPI 3.0.3 描述
```

异常一律转成 `{"ok":false,"error":"..."}`，不返回 HTML 错误页——低代码平台
拿到 500 页面只会显示「请求失败」，无从排查。

### `/v1/jobs` — 长任务的异步版本

`/v1/write` 实测 17—60 秒，`/v1/gather` 开联网 20—40 秒，都超过低代码平台
和插件调用的等待上限。超时的后果是「服务端跑完了、结果丢了、token 也花了」。

```
POST /v1/jobs  {"op":"plan|gather|write", ...同同步接口参数}  → {ok, job_id}
GET  /v1/jobs/<job_id>                                        → {state, ms, result}
```

`state` 取 `running` / `done` / `error`，`result` 与同步接口返回完全一致。
结果存在进程内存，保留 1 小时。扩到多实例前要换成 Redis。

### 鉴权

`.env` 里设 `PV_TOKEN` 即开启，`/v1/*` 全部要带 `X-PV-Token` 或
`Authorization: Bearer`，只有 `/v1/health` 免校验。不设就是裸奔——
`/v1/write` 一次 3200 token，公网被人刷额度当天见底。

发布到百炼/魔笔的完整步骤见 [`../docs/魔笔接入说明.md`](../docs/魔笔接入说明.md)。
