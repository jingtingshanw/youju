0.3.3 关键判断：这是两个任务，不是一个任务的两种做法

竞品盘点最容易得出的错误结论是「打不过，所以换战场」。这个结论接受了对方定义的战场。

北大法宝 / 威科 / 法信有据
回答的问题有哪些文件你引的这一条站不站得住
判据覆盖判定
赢的条件数据量规则完备
「8 部 vs 320 万篇」致命不进这个比较

检索与校验是两个不同的任务。 竞品改善的是「生成质量」，本产品提供的是「交付前的合规判定」。 覆盖比不过，判定根本不需要覆盖——用户从权威源查到依据，把依据交给本产品核。

技术路径的差别是可验证的，不是修辞：竞品的「降低幻觉」是概率改善，「一键溯源」是把原文摆出来让人自己看； 本产品的 C1–C5 是不调用模型的机器闸门，核不过就不给结论，且同输入必同结论。

最有说服力的实证是 C5 的诞生过程（research/10 §4）：66 题在 Dify 链路上零失误的错误——

模型把库内《呼伦贝尔市城市市容和环境卫生管理条例》当成用户所问的库外《城市市容和环境卫生管理条例》，

C1–C4 全部通过——换成直连 qwen-plus 第一次跑就复现了。

它证明的是：写在提示词里的硬约束，可靠性跟模型绑死；搬进规则层才成立。

0.3.4 竞品的三个结构性盲区，以及各自的水分

盲区一 · 地方非立法类文件。 竞品收录核心是有立法效力层级的文件；而规划师做立项论证时最直接的依据—— 市级专项规划、年度计划、实施方案、攻坚行动——多数不在里面。

此盲区真实，但本产品对它的覆盖能力尚未验证，当前不得作为卖点。

目录层省级源恒为 blocked，flk 亦 blocked，manual.csv 只有表头。

收录率已于 2026-10-19 实测（见 data/catalog/audit_yingtan.json、docs/优化方向-v1.md §0）：

鹰潭站源端 287 条、去重 212 条、真误杀 1 条（≈0.5%）。误杀率可接受，但 26% 的重复率说明「源端命中数」不能当文件数用。

盲区二 · 没有私有稿件入口。 三家全是检索型工具，没有一家接受用户上传自己的稿件逐条核对。 原因是结构性的：责任边界（稿件是未公开资产）、技术路径（需要确定性判定而非生成）、商业模式（账号订阅 vs 按次计费 + 服务责任）。

这是本产品最重要的战略发现：已有的技术资产，配的是一个尚未做的场景。

C1–C5 的天然输入是「一批引用」，不是「一个自然语言问题」。FR-04 排在 P1 是优先级错误。

盲区三 · 不对结论负责。 竞品的准确率是营销话术；本产品有一整套可验收指标（§7.2）。 在政府项目、国企送审场景里，「可写进合同的准确率承诺」有真实付费意愿，因为出错责任在甲方。

0.3.6 定位修订（待决策，尚未采纳）

候选表述：

有据是一个法规引用的确定性校验层。它不替代权威数据库——用户仍从那里查依据。

有据做的是在依据写入正式文件之后、送审之前，用不调用模型的规则逐条核对：条号是否越界、引文是否真实、法规是否失效、名称是否错配、所问法规划界。

核不过，就不给结论。输入是「你已经查到的依据」，输出是「一份可以随稿提交的核验报告」。

采纳这条定位有三个前提，目前一个都没验：

  1. 「送审被打回常常因为引用错」——未访谈验证（T-15 的第 1 问）
  2. 核验场景下 C3（时效）可用——实际上用户带来的文件通常不写效力状态，省级与 flk 均 blocked，

    3. C3 在稿件场景大概率只能标「未核」

  3. 核验场景下 C5（所问法规划界）可用——稿件场景没有「问题」，C5 无输入，直接失效

所以定位只在 §0.3.6 存为候选，§1.1 的定位暂不替换。 翻转的完整代价核算见 docs/优化方向-v1.md §2.2：五项检查搬过去只剩三项半，不是五项。

1. 背景与目标

1.1 业务背景

规划师写的东西要交出去，交出去的东西会被人追问「依据是什么」。这个追问在三个环节上出现，每个环节现有工具都不管用。

环节一：立项前的政策梳理。 接了江西鹰潭的城市更新项目，需要知道鹰潭市本级有哪些文件、江西省有哪些、国务院和部委有哪些，以及历史文化保护方面的相关规定。现状是人工在 4–6 个政府站之间翻，边翻边记。产出的清单直接进项目建议书的「政策依据」一章。这一步的判据是不能漏——漏了一份关键文件，整章的论证基础就不完整。

环节二：起草时的引用核对。 写完一章，逐条核对引用的条号是否存在、引用的法规是否还有效。现状靠人记和地方经验。这一步的判据是不能错。

环节三：送审前的自查。 把稿子交给评审前跑一遍，产出引用清单 + 时效状态 + 疑似问题列表。现状是抽查。这一步的判据是可解释——每一条问题都要能指到具体位置，否则作者没法改。

2. 用户与场景

2.1 用户角色

角色是谁主要诉求对 AI 的容忍度
规划师（主用户）规划院/所的项目负责人、主创要一份能进文档、能被追问的清单与依据低。错一次就不再信任，且不会主动举报

管理员一个人维护全部专题库要库别烂、别过期中。看重可维护、可批量

2.2 权限矩阵

功能规划师审校人管理员

触发重新抓取（联网）✅❌✅
装配专题库❌（只能申请）❌✅
确认文件效力状态❌✅（复核）✅（主责）

2.3 典型场景（端到端，鹰潭城市更新）

① 规划师输入：地域=鹰潭，主题=城市更新
   → 系统出清单：国家级 21 份 / 省级 0（显式标缺）/ 市级 3 份
   → 覆盖度条首行写「省级缺失：江西省站无可用检索接口，需人工补」

② 规划师勾选 30 份，申请装配
   → 管理员执行装配：抓全文 → 解析成条 → 体检 → 出条数表
   → 体检不通过的进「待人工」，附原因（不是简单报错）

③ 管理员确认 30 份的效力状态（现行有效 / 已废止 / 未知）
   → 台账落库，进入检索池的只有「现行有效」+「未知（标注）」

④ 规划师提问或贴稿
   → 检索 → 生成 → 闸门 2 五项校验 → 结论 + 逐条依据 + 时效状态

⑤ 送审前跑全稿自查
   → 输出引用清单 + 问题列表 + 漏引候选（目录 N 份 vs 稿子引了 M 份，N-M 是候选）

第 ① 步里最重要的一行是「省级缺失」。市级抓到 3 份、省级 0 份，如果只打印清单，用户会以为江西省没有相关文件。兜底型工具宁可显得笨，不能显得全。

4.3 异常与降级流程

异常判定条件降级动作用户感知
模型服务超时单次 > 30s返回「本次未能生成，以下为检索到的原文」顶部提示「已切换为原文模式」，仍给条文
模型服务不可用连续 3 次调用失败全局关闭生成能力，只保留清单 + 原文界面进入「只读模式」
检索无结果闸门 1 判定话题级不命中不生成结论明确写「库里没有这个话题」，并给目录层的文件清单作为替代
条号越界（C1）引用的条号 > 条数表该条依据标「不通过」，结论降级显示「引用的第 X 条不存在，该文件共 N 条」
引用废止文件（C3）名称命中台账且状态非现行有效拦截该依据显示「《X》已于 YYYY-MM-DD 废止，替代文件为《Z》」
目录源不可用连续 2 次抓取失败保留上次缓存，标 stale清单顶部写「数据截至 YYYY-MM-DD，该源今日未更新」
成本超预算日成本 > 预算 120%降低检索 topk，关闭非必要重排无感知（延迟略降）

降级的目标是「退回一个仍然有用的形态」，报错不算降级。 这个产品有三个形态，任何一个都比报错好：

  1. 完整形态：清单 + 结论 + 依据 + 校验
  2. 原文形态（模型挂了）：清单 + 检索到的原文，用户自己读
  3. 清单形态（全挂）：只有目录层，用户至少知道有哪些文件

第 3 种形态之所以还有用，是因为目录层不依赖模型、不依赖外部 API，只依赖政府站和自己的 SQLite。

5. 功能需求

FR-01 政策清单（目录层）

  • 优先级：P0
  • 功能描述：按「地域链 × 主题」输出政策文件清单，带覆盖度与失效状态
  • 前置条件：data/catalog.db 存在或有可用的源配置；无网络时读缓存
  • 处理规则：
  1. 地域按 regions.chain 向上展开（鹰潭市 → 江西省 → 国家）
  2. 主题按 11 个词表匹配标题；跨领域可用多个主题（如城市更新 + 历史文化保护）
  3. 自各源抓取，每个源返回独立状态（ok / empty / blocked / unavailable / error / skipped）
  4. 同一条目多源命中时合并，每个推断字段必须带依据（文号 / 时效台账 / 来源库 / 来源站点 / 标题 / 无法判定）
  5. 按行政层级 → 发布日期倒序排列
  6. 覆盖度三级汇总（国家 / 省级 / 市级），missing 必须显式输出并附原因
  • 输入：地域、主题（可多选）、关键词（可选）、翻页深度
  • 输出：条目列表 + 覆盖度 + 各源状态 + 未覆盖清单
  • 异常处理：
  • 源端返回空 → 标 empty，不当成「没有文件」
  • 源端结构变化 → 标 error，保留上次缓存并标 stale
  • 反爬拦截 → 标 blocked，附探测记录
  • 验收标准：
  • AC-01：输入「鹰潭 / 城市更新」，输出含国家级 ≥ 20 份、市级 ≥ 3 份，省级显式标 missing
  • AC-02：任一源失败时，界面不出现「该级没有文件」这类断言
  • AC-03：离线自检 crawl.py --selftest 26/26 通过
  • 关联需求：S1、S7
  • 已实现：scripts/catalog/，实测见 §9.4

FR-02 专题库装配

  • 优先级：P0
  • 功能描述：从清单勾选 N 份文件，抓全文、解析成条、体检、出三张表
  • 前置条件：清单已生成；文件 URL 可用
  • 处理规则：
  1. 抓全文（HTML 优先；.docx 用 zipfile 读 word/document.xml；.doc / .pdf 归入 pending_convert）
  2. 判型（分条型 / 分段型 / 无结构型），按型选判据，避免用条数判据误杀分段式文件
  3. 体检三重判据：结构完整性、内容完整性、可引用性（见 §6.5）
  4. 通过者生成条数表；不通过者进「待人工」并附具体原因
  5. 出准入分级：accepted / accepted_with_warning / pending_manual / rejected
  • 输入：文件清单（含 URL）
  • 输出：全文 + 条数表 + 体检报告 + 待人工清单（分类统计，不能笼统报「N 份待人工」）
  • 异常处理：
  • .doc / .pdf → 归 pending_convert，附转换工具建议，不静默丢弃
  • 抓下来是错误页（200 但内容是 404 页）→ 按内容特征判，不按状态码判
  • 解析出的条数为 0 → 判型失败，进待人工
  • 验收标准：
  • AC-04：对已解析的 .docx 样本，条数与原文「第X条」计数一致
  • AC-05：体检不通过的文件 100% 出现在待人工清单里，且带原因
  • AC-06：报告按格式（HTML / docx / doc / pdf）分类统计成功率
  • 关联需求：S2
  • 状态：未开发

FR-03 逐条核验（闸门 2）

  • 优先级：P0
  • 功能描述：对一次问答或一条引用，执行五项确定性校验，输出可解释结论
  • 前置条件：库内有三张表；提问已检索到候选条文
  • 处理规则：
  1. 闸门 1（话题级）：检索分数过低 → 判「库里没有这个话题」，不生成
  2. 闸门 2（条文级），五项检查全部不调模型：
  • C1 条号越界：引用条号 > 条数表
  • C2 引文查不到：引用文本在原文中找不到
  • C3 时效违规：引用的文件已废止/失效
  • C4 名称错配：文件简称与全称对不上
  • C5 所问法规划界：回答引用了不在所问范围内的法规
  1. 结论分三档：可作答 / 部分作答 / 拒答
  2. 每条依据逐项列出通过与否，结论强度随之降级
  • 输入：问题 + 模型输出
  • 输出：结论 + 逐条依据 + 五项校验明细 + 引用清单
  • 异常处理：
  • 台账缺失 → C3 标「未核」，不默认现行有效
  • 条数表缺失 → C1 标「未核」
  • 模型未给条号 → C1/C2 标「无法校验」并降级结论
  • 验收标准：
  • AC-07：C1–C5 每组既有一条应通过用例，也有一条应拦截用例（现有 11 组）
  • AC-08：校验层不发起任何网络请求（可通过断网跑通验证）
  • AC-09：同一输入两次运行结论完全一致（无随机性）
  • 关联需求：S3、S4
  • 已实现：scripts/gatekeeper.py

FR-04 全稿自查

  • 优先级：P1
  • 功能描述：贴入一份稿子，抽出全部法定引用，逐条核验，并给出漏引候选
  • 前置条件：已装好对应专题库
  • 处理规则：
  1. 抽取引用（《X》第 N 条 / 依据《X》/ 文号）
  2. 逐条走 FR-03
  3. 漏引候选：目录层该方向 N 份，稿子只引了 M 份，差额按主题相关度排序输出为候选
  4. 输出按「必须改 / 建议看 / 可忽略」三级
  • 输入：稿件全文（粘贴或上传 docx）
  • 输出：引用清单 + 问题列表 + 漏引候选 + 汇总统计
  • 异常处理：抽取不到引用 → 明确写「未识别到法定引用」，不给「全部通过」的假结论
  • 验收标准：
  • AC-10：抽取召回率在 20 条人工标注引用上 ≥ 95%
  • AC-11：漏引候选必须显式标注「以下是候选清单，请自行判断」，不得表述为结论
  • 关联需求：S4
  • 状态：未开发

FR-05 时效台账维护

  • 优先级：P0
  • 功能描述：为库内每份文件维护效力状态，作为 C3 的唯一外部真值
  • 前置条件：文件已入库
  • 处理规则：
  1. 机器给出候选状态与来源链接（源站文末标注、法规库详情页）
  2. 人工逐份确认，记录确认人与时间
  3. 未确认的标「未知」，不参与「现行有效」判定
  4. 废止文件必须记录替代文件
  • 输入：文件清单
  • 输出：stale_ledger.json（含状态、依据、确认人、确认时间）
  • 异常处理：源站无标注 → 标「未知」，并在界面提示「该文件时效需查法制部门口径」
  • 验收标准：
  • AC-12：台账中每一条都有确认人与时间，无「机器自报」
  • AC-13：C3 只读台账，不读模型输出
  • 关联需求：S5
  • 状态：已实现（8 部），需扩到专题库规模

FR-06 评测与 badcase 看板

  • 优先级：P1
  • 功能描述：离线跑批 + 线上反馈汇集，回答「这次改动是优化还是劣化」
  • 处理规则：
  1. 评测集分层：能力维度 × 难度
  2. 每次改动跑全量，输出对比表
  3. 线上「这条不对」的反馈自动进 badcase 池
  4. 每月从 badcase 补充 ≥ 10 条进评测集
  • 验收标准：
  • AC-14：任意两个版本可对比，输出逐题 diff
  • AC-15：badcase 池每条带原始输入与当时的判定
  • 关联需求：S6
  • 状态：部分已实现（eval_run_app.py）

FR-07 一键降级开关

  • 优先级：P0
  • 功能描述：30 秒内关闭全部模型能力，退回清单 + 原文形态
  • 处理规则：单个配置项；关闭后前端显示「只读模式」；不影响目录层
  • 验收标准：

6. AI 能力设计

这一节是 AI 产品 PRD 的核心新增部分。本产品的特殊之处在于：模型只承担链路上的一小段，其余全是确定性工程，所以这一节的重点是「哪些地方故意不用模型」。

6.1 能力全景与方案选型

要办的事方案为什么不用别的方案
这个方向有哪些文件结构化查询（SQLite + 政府站检索接口）不用向量检索：要能穷举、要按效力级别与地域过滤、要能说出「没有」。相似度无法表达「不存在」

这份文件该归到哪一级文号 + 标题规则推断，无依据就留空不用模型：推断结果必须能说清依据，模型说不清

6.3 提示词设计

系统提示 4,317 字，实测 2,863 token，占单次输入的 72%（详见 §9.1）。结构如下：

# 角色      你是政策条文核验助手。只依据给出的条文回答。
# 硬约束    ① 不得引用给出条文之外的任何法规
            ② 不得推断未在条文中出现的数字、期限、责任主体
            ③ 不符合时明确拒答，并说明缺什么
            ④ 不回答「我该怎么办」这类建议性问题
# 输出格式  结论 / 依据（法规全称 + 条号 + 原文） / 未能回答的部分
# 拒答措辞  固定句式，便于下游规则层识别

两条边界必须写进提示词（对应 §3.2 的 N1 与 N3）：

  • N1 不给法律意见 → 提示词里写死：「当用户询问是否应该做某件事、如何规避某项规定、能否获得补偿时，必须回复『该问题需由主管部门认定』，不得给出判断性结论。」
  • N3 不自动确认效力 → 提示词里写死：「不得声称任何文件的效力状态。效力状态由系统台账给出，你的输出中不包含该字段。」

为什么不把五项校验写进提示词：写了也只是「模型自觉」。C5 的发现过程就是实证——在 Dify 链路上 66 题一次没犯的错，换成直连 qwen-plus 第一次跑就犯了，而它恰好落在原有四项检查之外。约束必须搬进规则层才能不依赖模型。

6.5.1 装配体检必须先判型

这是 v2 里最容易被真实数据打穿的一处，本版单列。

现有的 8 部法规全是「第X条」的法典式文件，条数对齐很好用。但省市级规范性文件大量是「一、（一）」分段式，根本不分条。拿条数判据去体检，会把大批真文件判成坏的。

型特征体检判据对 C1 的影响
分条型有「第X条」序列条号连续、无重复、与原文计数一致C1 正常工作
分段型有「一、」「（一）」层级层级完整、编号连续C1 降级为「编号存在性检查」
无结构型通篇段落只查长度与非空C1 不适用，标「无法校验」

判型失败 → 进 pending_manual，附「疑似 XX 型，但结构不完整」。

6.6 失败与降级设计

见 §4.3。这里只补一条设计原则：每个失败都必须有对应的界面表达。三类异常的处理方式完全不同：

异常类型例子处理用户看到什么
技术异常超时、格式错重试 1 次 → 降级「已切换为原文模式」
能力异常检索未命中兜底 + 记录回流「库里没有这个话题」+ 文件清单
正确性异常幻觉、引用失效规则拦截 + 强制溯源「第 X 条不存在」这类可核对的说明

第三类最危险，因为它不会报错。一个编造的条号在界面上与真实条号长得一样。这就是闸门 2 存在的全部理由。

7.1 评测集设计

7.1.1 现状（必须先说清）

现有 eval/golden-set.csv，66 题，按能力维度分层：

这个产品的成本约束在人力，不在 token

对照制造一个直观的刻度：同类产品（政务工单分拨）日均 7,200 件，月 API 成本 ¥10,470。本产品 10 人团队的月 API 成本 ¥16.2，相差约 650 倍。这个量级差决定了成本优化在这里不重要。

真正贵的是这一笔：

项数量单价金额
装配一个专题库：机器部分~10 分钟—≈ ¥0
装配一个专题库：人工确认效力80 份 × 1 分钟¥80/小时¥107
库的生命周期同城同主题约 5 个项目/年——
摊到单个项目107 ÷ 5—≈ ¥21
对照：人工梳理同类清单4 小时¥80/小时¥320

估算的投入产出比约 1:15（¥320 对 ¥21）。这个数字标注为估算，因为「人工梳理 4 小时」和「确认一份文件 1 分钟」两个输入都没有实测过——它们要靠 §8.1 的 ledger_confirm 埋点量出来。

结论：优化成本的方向是压人工分钟数，不是压 token。 具体做法是：装配时把「效力确认」做成批量视图（一次看 20 份，键盘连点），把待确认量从 80 次点击压到 4 屏。

10. 风险与合规

10.1 数据合规

项要求措施
抓取对象政府网站公开发布的政策文件只抓公开栏目与检索接口，遵守站点限速（0.3–0.8 s/请求），带正常 Referer
抓取频率不对源站造成压力单主机串行 + 间隔；不做并发爆破
用户稿件外泄用户贴进系统的稿件可能含未公开内容默认只发检索到的条文与问题，不发全文；全稿自查提供「纯规则模式」，不调模型（FR-04 的默认模式）
数据留存AI 调用可审计记录调用时间、能力、输入摘要（不存全文）、输出、判定结果
模型服务商政策文本经第三方 API首次使用前明示「内容将发送至模型服务商」；提供纯规则模式作为替代
来源标注每条依据可回溯到源站目录条目必带 URL；失效链接保留原 URL 并标 stale

「用户稿件外泄」是这一节唯一真正的风险。 政策文件是公开的，抓与不抓只涉及礼貌；但规划师贴进来的是还没送审的稿子，可能是敏感项目。所以全稿自查必须默认走纯规则模式——五项校验本来就不需要模型，这一点在架构上是成立的。

10.4 预期管理

界面上必须一直存在的三句话：

  1. 「本工具不给法律意见。」 效力认定以法制部门口径为准。
  2. 「清单可能不全。」 覆盖度一栏写明哪一级缺、为什么缺。
  3. 「依据请自行复核。」 每条依据都给原文与链接，点击可核。

这三句属于产品的一部分，写在功能里，不能只写在文档里。
