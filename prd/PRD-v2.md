# 0. 本版改了什么

v1 的前提是「文件已经在我手上，我来核验引用属不属实」。这个前提在真实场景里不成立：
规划师接一个项目的**第一件事**是弄清这个话题在三级政府各有哪些文件，
而这批文件他手上没有，也不知道该有哪些。

v2 把这件事补进来，同时守住一条底线：**补进来的只有「名单」，不是「全量正文」。**

| 维度 | v1 | v2 |
|---|---|---|
| 起点 | 用户提问 | 用户给「地域 + 主题」 |
| 库 | 一个知识库（8 部法规） | **全量目录（1.9 万条字段）+ 每专题一个库（50–80 份全文）** |
| 链路 | 检索 → 核验 → 交付（三段） | **发现 → 装配 → 核验 → 交付（四段）** |
| 检索的角色 | 找文件 + 找条文 | **只找条文**（找文件归目录层） |
| 指标 | 一套（66 题） | **三层分开**：目录层 / 装配层 / 问答层 |
| 新增工程 | — | 目录抓取（已做）+ 装配流水线（待做） |

**一句话概括这次改动**：把「知识库里有没有」这个不可控的前提，换成一个可控的动作——
先用 13 分钟把国家级目录穷举，再用 10 分钟把某个专题的文件装配好。

# 1. 产品定位

## 1.1 一句话

**给规划师一个「有据」：每一条结论都能指到具体条款、具体文件、具体时效状态。**

## 1.2 「据」的三层含义

这个名字不是修辞，它规定了三件必须交付的东西：

| 层次 | 用户的问题 | 产品给的东西 | 缺了这一层会怎样 |
|---|---|---|---|
| **有文件** | 这个方向有哪些文件？省里的、国家的 | 带效力级别和链接的清单，含三级覆盖度 | 用户不知道有这份文件，后面的核验再准也没用 |
| **有条文** | 这条规定写在哪？ | 法规全称 + 条号 + 原文 | 结论无法写进文书，也没法被人核对 |
| **有效力** | 它还有效吗？ | 现行有效 / 已废止 / 已失效 / 未知 | 引了废止文件，比不引更糟 |

三层缺一层，这个产品就退化成「搜索框」或「校对小工具」。

## 1.3 用户与三个真实场景

**主用户**：规划院/所的规划师、政府部门的规划管理人员。他们不是在「查法规」，
是在**写一份要交出去的东西**（专项规划、可行性研究、项目建议书、政策建议），
里面每一句涉及法定依据的话都要能被人追问「依据是什么」。

**场景 A · 立项前的文件梳理（新增，本版重点）**
接了江西鹰潭的城市更新项目。需要知道：鹰潭市本级有哪些文件、江西省有哪些、
国务院和部委有哪些，以及历史文化保护方面的相关规定。产出是一张清单，进项目建议书的
「政策依据」一章。**这一步的判据是不能漏**。

**场景 B · 起草时的引用核对**
写完一章，逐条核对：引的条号存在吗？引的法规还有效吗？有没有该引没引的重要文件？
**这一步的判据是不能错**。

**场景 C · 送审前的自查**
把稿子交给评审前，跑一遍全文，产出「引用清单 + 时效状态 + 疑似问题列表」，
随稿一起交。**这一步的判据是可解释**——每一条问题都要能指到具体位置。

## 1.4 不做什么

1. **不给法律意见。** 报告事实与效力状态，不给「你应该怎么做」。
2. **不做全量全文库。** 1.9 万份正文进库之后，效力台账维护不了，闸门 2 失效，
   整套东西退化成普通 RAG（见 [9.1](#91-为什么不做全量全文库最硬的约束)）。
3. **不替代正式法律检索。** 对外的效力认定以法制部门口径为准。
4. **不做通用问答。** 只回答「这份文件这条规定是什么、还有没有效」这类可核验的问题。
5. **不承诺覆盖全国所有地市。** 每个省市站要单独适配，做不到的部分显式标缺。

# 2. 两层库

## 2.1 为什么必须两层

两层真正的差别是**维护成本**，跟存多存少关系不大：

| | 目录层 | 专题库（全文层） |
|---|---|---|
| 存什么 | 名称 / 发文机关 / 文号 / 效力级别 / 发布与失效日 / 地域 / 主题 / 链接 | 逐条正文 + 条数表 + 时效台账 |
| 目标 | **接近穷举**（不能漏） | **按需精读**（不能错） |
| 规模 | 国家级 19,026 条 + 省市 | 一个专题 50–80 份 / 2,000–4,000 条 |
| 谁能维护 | 机器全自动 | 机器 + 人工确认效力 |
| 更新 | 每天可增量刷 | 立项时装配一次 |
| 判据 | 覆盖度 | 五项确定性校验 |

**决定性因素是维护成本。**

19,026 份文件的效力状态，只有国家法律法规数据库有权威口径，而它现在 `blocked`（§9.2）。
没有台账，闸门 2 的 C1（条号越界）和 C3（时效违规）就全部退化成「未核」——
这两条恰恰是这个产品不可替代的部分。**库一大，判据先死。**

50–80 份不一样：条数表可以由解析结果**自动导出**（解析出来就数出来了），
效力状态只需人工确认 50–80 次，一次点击一份，半小时能做完。
这是「专题库可维护、巨型库不可维护」的量化依据。

## 2.2 目录层规格

| 项 | 规格 |
|---|---|
| 存储 | SQLite（`data/catalog.db`），三张表：`items` / `source_state` / `runs` |
| 字段 | 名称、发文机关、文号、效力级别、地域、主题、发布日期、施行日、失效日、效力状态、链接、摘要 |
| 每个推断字段 | 必须带依据：`文号 / 时效台账 / 来源库 / 来源站点 / 标题 / 无法判定` |
| 国家级总量 | **19,026 条**（gw 6,222 + bm 12,804），实测可翻页穷举 |
| 刷新 | 全量 13 分钟；增量按发布日期窗口 + 文号指纹（见 §6.3） |
| 主题 | 11 个词表（城市更新 / 历史文化保护 / 土地管理 / 规划管理 / 财政资金 / 房屋征收 / 市政设施 / 生态环境 / 消防与安全 / 建筑管理 / 招标采购） |
| 地域展开 | `regions.chain` 配置：鹰潭市 → 江西省 → 国家 |
| 状态词 | `ok / empty / blocked / unavailable / error / skipped`（六种，缺一不可） |
| 已实现 | `scripts/catalog/`，自检 26/26，实测见 §2.2.1 |

### 2.2.1 实测数据（2026-10-19）

| 源 | 状态 | 实测 |
|---|---|---|
| 国务院政策文件库 | `ok` | 源端 6,222 条；主题子集 1,425 条 |
| 国务院部门文件库 | `ok` | 源端 12,804 条；主题子集 1,772 条 |
| 鹰潭市政府（站内检索） | `ok` | 源端命中 276 条 → 收录 3 份（差额未逐条核对） |
| 鹰潭市政府（文件栏目） | `empty` | 扫 32 条，无主题文件 |

| 江西省人民政府 | `unavailable` | TRS search5，前端渲染 |
| 人工清单 | `skipped` | 只有表头 |

「鹰潭 × 城市更新」全量翻页一次：扫 3,197 条，收录 **24 条**（国家 21 / 省级 0 / 市级 3），
用时 **2 分 19 秒**。同题浅抓 2 页只有 4 条国家文件——**翻页深度决定清单大小**。

## 2.3 专题库规格

**「专题库」的定义：一个主题 × 一条地域链上的全部相关文件全文。**

| 项 | 规格 |
|---|---|
| 库的键 | `topic + region_chain`，例如 `城市更新@鹰潭市→江西省→国家` |
| 组成 | 50–80 份文件全文，切成 2,000–4,000 个可检索单元 |
| 必须携带 | 条数表、时效台账、名称映射表（三张表） |
| 生命周期 | 随项目建，可长期复用（同城市同主题的第二个项目直接复用） |
| 复用规则 | 项目引用库，不复制库；库升级后所有引用它的项目一起受益 |
| 退出条件 | 三张表齐 + 检索召回达标 + 闸门自检通过 + 缺口清单已标注 |

**为什么库的粒度是「主题 × 地域」而不是「项目」**：一个规划院一年做五个城市更新项目，
如果按项目建库，就是五个 80% 重复的库。按「主题 × 地域」建，鹰潭只有一个城市更新库，
五个项目共用；换到南昌再做，新增一个南昌库，国家层文件复用同一份。

## 2.4 两层的接缝（最容易漏的地方）

目录层认「标题」，专题库认「法规全称」，闸门 2 认「全称 + 条号」。三者必须对齐：

```
目录条目：关于开展2026年度中央财政支持实施城市更新行动的通知   ← 抓来的标题
                    │ 装配时解析出正式全称
                    ▼
专题库条目：《中央财政支持城市更新行动资金管理办法》            ← 正文首部或落款
                    │ 写入 doc_names.json
                    ▼
闸门 2：认全称 → 查条数表 → 查时效台账
```

**风险**：目录标题与正文全称经常不一致（尤其是转发件、印发通知、附件形式的文件）。
处理规则写在 §6.2。

# 3. 四段链路

## 3.1 全景

```
┌─ 段 0 · 发现 ────────────────────────────────────────────────┐
│  输入：地域「鹰潭」+ 主题「城市更新」                          │
│  动作：目录层按 region_chain 展开，结构化查询（不用 RAG）      │
│  输出：候选清单 N 份 + 三级覆盖度 + 缺口清单                  │
│  判据：不能漏 → 看覆盖度，不看条数                            │
└──────────────────────────────────────────────────────────────┘
         │ 人筛：留 A/B 级、剔 C 级（新闻 / 转载 / 解读）
         ▼
┌─ 段 1 · 装配 ────────────────────────────────────────────────┐
│  五个环节：抓全文 → 解析 → 体检 → 出三张表 → 建索引          │
│  输出：专题库（50–80 份）+ 条数表 + 时效台账 + 缺口单          │
│  判据：不能错 → 体检通过率、条数对齐、人工确认率              │
└──────────────────────────────────────────────────────────────┘
         │
         ▼
┌─ 段 2 · 核验 ────────────────────────────────────────────────┐
│  提问 → ②检索（BM25/向量）→ 候选条文                          │
│        → ③生成（模型起草，逐条锚定条号）                      │
│        → ④闸门 1（话题级，分数阈值）                          │
│        → ⑤闸门 2（条文级，零模型，5 项）                      │
│  判据：不能错 → 引用可追溯、真编造、时效违规                  │
└──────────────────────────────────────────────────────────────┘
         │
         ▼
┌─ 段 3 · 交付 ────────────────────────────────────────────────┐
│  可作答 / 部分作答 / 拒答                                     │
│  + 逐条依据 + 时效状态 + 引用清单 + 判定理由                   │
└──────────────────────────────────────────────────────────────┘
```

## 3.2 段 0 · 发现

| 项 | 内容 |
|---|---|
| 输入 | `region`（可简写「鹰潭」）+ `topic` 或 `keyword` |
| 前置 | 该地域在 `sites.json` 里有配置（没有就新增一条，不改代码） |
| 动作 | 按地域链逐级调度源；每个源独立跑、独立报状态 |
| 输出 | 清单（按行政层级分组，每条带效力级别、文号、日期、链接、状态）+ 覆盖度 + 缺口 |
| 判据 | **三级各自覆盖到什么程度**；「没查到」必须显式写出来 |
| 失败 | 单源失败不影响其他源；整级为空时该级标 `missing` 并给原因 |
| 不做 | 不抓正文、不判效力、不猜 |

**这一步为什么不用 RAG**：目录层要回答的是「有哪些文件」，这是一个集合查询。
用相似度找文件会漏掉「标题不含主题词但内容相关」的文件，也会混进大量新闻。
结构化查询（地域 × 主题 × 效力级别）在这个任务上更准、更快、可穷举。

## 3.3 段 1 · 装配

详见 [§5](#5-装配流水线规格)。这里只给输入输出。

| 项 | 内容 |
|---|---|
| 输入 | 段 0 的候选清单，人已筛掉 C 级 |
| 动作 | 抓全文 → 解析 → 体检 → 出三张表 → 建索引 → 自检 |
| 输出 | 专题库 + 三张表 + 缺口单 + 装配报告 |
| 判据 | 体检通过率 ≥90%；条数表与正文一致率 100%（自动导出，必须自洽）；效力确认 100%（人工） |
| 失败 | 体检不通过的文件转「待人工」，不静默丢弃 |

## 3.4 段 2 · 核验

沿用 v1 的两道闸门，这里只写与 v2 有关的变化：

| 变化 | 说明 |
|---|---|
| 闸门 1 阈值 | **必须按每个专题库重标**。v1 的 0.40 是在 8 部法规上量的，不能直接搬 |
| 闸门 2 依据 | 三张表由装配流水线产出，不再手写。条数表自动生成，时效台账人工确认 |
| 检索层 | 默认 BM25；向量为可选增强，启用后必须重标阈值 |
| 覆盖度 | 回答里增加一句「本次依据来自专题库 X，该库省级未覆盖」 |

## 3.5 段 3 · 交付

沿用 v1 的三态与输出契约。新增两条：

1. **依据来源分级**：每条依据标明它来自「专题库全文」还是「仅有目录」。
   只到目录级别的文件，只能作为「另需查阅」提示，不能当引用。
2. **缺口声明**：本次装配的已知缺口（省级未覆盖 / 某份文件解析失败）随结论一起给出。

## 3.6 每段的失败与降级

| 段 | 失败形态 | 降级动作 | 用户看到什么 |
|---|---|---|---|
| 0 发现 | 某级源不可用 | 该级标 `missing`，继续跑其他级 | 「省级未覆盖：原因 + 补法」 |
| 0 发现 | 全源不可用 | 整个查询报错，不返回空清单 | 「本次查询失败」+ 原因 |
| 1 装配 | 抓全文失败 | 该份转「待人工」，其余继续 | 「N 份待人工处理」 |
| 1 装配 | 解析失败 / 体检不过 | 该份不入库，留在候选池 | 「N 份未通过体检」+ 原因分类 |
| 1 装配 | 效力未确认 | 该份入库但标「未知」，闸门 2 不认它为现行依据 | 「N 份效力未确认」 |
| 2 核验 | 闸门 1 不过 | 拒答 | 「本次检索结果中没有能支持该问题的条文」 |
| 2 核验 | 闸门 2 不过 | 降级或拒答 | 「第 X 条第 Y 项不通过：引用查不到」 |

# 4. RAG 在这里的位置

这一节直接回答「还有没有用 RAG」。

## 4.1 仍然在用，但只用在一处

整条链路上有三件需要「找东西」的事：

| 要办的事 | 用什么 | 为什么 |
|---|---|---|
| 这个方向有哪些文件 | **结构化查询**（目录层） | 要穷举、要能说出「没有」，相似度做不到 |
| 这几条依据在库里的哪里 | **检索**（BM25 / 向量） | 是语义匹配任务，这就是 RAG 的检索环节 |
| 模型说引了第 42 条，到底有没有 | **确定性查找**（按全称 + 条号取数） | 要可复现、要能写进承诺，不能用分数 |

**只有第二件事是 RAG。** 第一件和第三件都不是——它们不需要「相似」，需要「精确」。

## 4.2 RAG 的职责缩小了

v1 里检索要干两件事：找到相关文件 + 找到相关条文。v2 把前一件交给了目录层。

| | v1 | v2 |
|---|---|---|
| 检索负责 | 找文件 + 找条文 | **只找条文** |
| 找文件靠 | 向量相似度 | 地域 × 主题的结构化查询 |
| 找文件会不会漏 | 会（标题不含主题词就漏） | 不会（目录是全的，按字段筛） |

**这个变化的实际效果**：模型中「检索」这一环的工程量占比从大约 100% 降到 30% 左右，
剩下 70% 是目录查询 + 装配 + 规则核验，都是确定性工程。

## 4.3 检索层规格

| 项 | 默认 | 可选 |
|---|---|---|
| 召回 | BM25（纯标准库实现） | 向量召回（需 embedding） |
| 重排 | 无 | rerank（仅在阈值判定需要时） |
| 规模 | 2,000–4,000 条 / 库 | 同 |
| 实测依据 | MVP 在 8 部 / 419 单元上 top-8 召回 L1+L2 **15/15** | 完整版 66 题 recall@1 65/66 |
| 结论 | **专题库规模下 BM25 够用，向量是可选项** | 启用向量必须重标闸门 1 阈值 |

**为什么专题库可以不配向量**：目录层已经把文件圈定在 50–80 份，
检索要做的只是「在这 2,000–4,000 条里挑出相关的几条」。这个规模的词汇重叠度足够高，
BM25 的弱点（同义表述）影响有限，而且一旦出错，闸门 2 会拦下来。
**用零依赖换来的可复现性，在这个规模上比几个百分点的召回更值钱。**

## 4.4 三个反模式（不能用 RAG 的地方）

这三条都是 v1 踩出来的，写在这里防止以后有人重新踩：

1. **不能用相似度判断「这条规定是否存在」。** 查不到就是查不到，要用条号确定性查找。
   否则「库里没有」和「没检索到」会混成一件事。
2. **不能用相似度判断「文件是否失效」。** 效力只有台账和法定期刊说了算。
   模型自报「现行有效」等于自报自验。
3. **不能用相似度做「漏引检测」。** 漏引是集合差集问题（目录 N 份 − 稿子引 M 份），
   不是相似度问题。

## 4.5 诚实的回答

**还有 RAG，但它在这个产品里是配角。**

普通的法规问答 RAG 是 `检索 → 生成`。有据是 `检索 → 生成 → 核验 → 降级`。
多出来的两段都不需要 RAG，而这两段才是产品价值所在——
用户要的是一份能被人追问的文件。一段听起来对的话满足不了这个要求。

反过来说：**如果去掉 RAG，这个产品仍然能工作**（用户自己贴条文进来核验）；
**如果去掉核验，它就变成又一个法规问答机器人**。

# 5. 装配流水线规格

本版只有规格，尚未实现。这一节是下一轮的开发依据。

## 5.1 五个环节

| 环节 | 动作 | 判据 | 失败处理 |
|---|---|---|---|
| ① 抓全文 | 按目录 URL 下载；同一文件多源时取正文最完整的一份 | 成功率（首轮只记录，不设目标） | 转「待人工」 |
| ② 解析 | HTML / docx → 纯文本 + 结构（条、款、项） | 解析成功率（按格式分别统计） | 转「待人工」 |
| ③ 体检 | 三重判据（§5.3），不过则不入库 | 通过率（首轮只记录，不设目标） | 留候选池，标原因 |
| ④ 出表 | 自动生成条数表；时效台账待人工确认 | 条数表与正文自洽率 **100%**（这一条必须有） | 阻断 |
| ⑤ 建库 | 切分 + 建索引 + 跑自检 | 闸门自检通过 | 阻断，不给用 |

**为什么前三项不设通过率目标**：首轮真实数据还没跑过，任何百分比都是编的。
省市级文件大量以 `.doc` 附件形式发布，而 `.doc` 零依赖解不了（§5.2），
解析成功率可能低到 50% 以下。**先量出来，再定阈值**——
把目标写在没量过的地方，只会逼着实现去凑数。

## 5.2 解析能力矩阵（零依赖约束下的真实边界）

项目的硬约束是**零第三方包**。这个约束决定了哪些格式能进全文层：

| 格式 | 能否零依赖解析 | 依据 | 处理 |
|---|---|---|---|
| HTML | ✅ 可以 | 正则 + 去标签 | 首选，政府站正文多为 HTML |
| `.docx` | ✅ 可以 | `zipfile` 读 `word/document.xml`，去标签 | **已实测**：8216 字符 / 50 条，与条数表一致 |
| `.doc` | ❌ 不行 | OLE2 二进制（实测文件头 `D0CF11E0`） | 需外部转换（Word COM / LibreOffice）或人工另存 |
| `.pdf` | ❌ 不行 | PDF 内容流，标准库无解 | 同上；扫描件还需 OCR |
| 扫描件 | ❌ 不行 | 同上 | 同上 |

**这是一条真实的产品约束，要写进界面**：装配报告里必须分别统计
「HTML 成功 / docx 成功 / doc 待转换 / pdf 待转换」，不能笼统报「N 份待人工」。

**为什么不为它破例引入依赖**：一旦引入 PDF 解析库，MVP 就不能「拷走就跑」，
而这个能力是产品演示与交接的基础。替代方案是「外部转换一步，人工操作」，
成本是一个人一次点击，收益是整条链路保持零依赖。

## 5.3 体检的三重判据

单纯用「条数对齐」会大量误杀——**很多规范性文件根本不分条**（用「一、」「（一）」分层次）。
所以体检要分型后再判：

**第一步：判型**

| 型 | 判据 | 后续检查 |
|---|---|---|
| 分条型 | 能识别 ≥3 个「第X条」 | 条号连续性 + 首尾完整 |
| 分段型 | 能识别 ≥3 个「一、」或「（一）」层级 | 层级编号连续性 |
| 无结构型 | 都不满足 | 只做长度与落款检查 |

**第二步：三项检查**

| 检查 | 判据 | 拦什么 |
|---|---|---|
| 完整性 | 正文含落款或成文日期；长度 ≥500 字 | 截断、只抓到附件、抓到导航文字 |
| 结构完好 | 分条型：条号从「第一条」连续到最后一条，无跳号、无重复 | 解析漏段、混入两份文件 |
| 一致性 | 正文首 200 字与目录摘要重合度 ≥50% | 抓错文件（链接跳转、栏目错位） |

**第三步：分型记录**

体检结果必须记下「这份文件是什么型、多少条/多少段」，因为闸门 2 的 C1（条号越界）
只对分条型有效。分段型的文件，C1 要降级为「条款编号存在性检查」。

## 5.4 准入分级

不是所有抓到的文件都该进全文层：

| 级 | 判定 | 处理 |
|---|---|---|
| **A 必入** | 法律 / 行政法规 / 部门规章 / 地方性法规（文号可判、效力级别明确） | 进全文层，效力必须人工确认 |
| **B 可入** | 省市规范性文件（标题命中主题、有文号或落款） | 进全文层，效力必须人工确认 |
| **C 只留目录** | 新闻、转载、解读、政策问答、会议报道 | 留在目录层，不进全文层 |

判定顺序：先看 `doc_type`（由文号推），推不出再看标题核心词，最后看来源栏目。
C 级的判据已经实现在 `looks_like_doc()` 里。

## 5.5 状态词（装配层）

与目录层同一套思路——**没做成的事必须说出来**：

| 状态 | 含义 |
|---|---|
| `assembled` | 已入专题库，三张表齐，效力已确认 |
| `parsed` | 已解析入库，但效力未确认（闸门 2 只作参考依据） |
| `pending_convert` | 需要外部转换（doc / pdf） |
| `pending_manual` | 抓取失败或体检不过，待人工处理 |
| `catalog_only` | 只在目录层，未进全文层（C 级或用户剔除） |
| `excluded` | 用户主动剔除 |

**装配报告必须给出这六类的条数。** 只报「成功 62 份」是误导。

# 6. 数据规格

## 6.1 目录层

| 表 | 内容 |
|---|---|
| `items` | key（`sha1(fold(doc_no or title))`）、名称、发文机关、文号、效力级别、地域、主题、日期、状态、链接、摘要、多源来源、首见/末见 |
| `source_state` | 每个源最后一次运行的状态、收录数、扫描数、源端命中数、耗时、原因 |
| `runs` | 每次抓取的查询、覆盖度快照、统计 |

## 6.2 专题库

| 文件 | 内容 | 谁生成 |
|---|---|---|
| `kb_text/<slug>/` | 落库文本，每行形如《全称》第X条　正文 | 装配流水线 |
| `article_counts.json` | 每部法规的条数 | 装配流水线（自动） |
| `stale_ledger.json` | 每部法规的效力状态 | 人工确认后生成 |
| `doc_names.json` | 目录标题 ↔ 正式全称 | 装配流水线（自动 + 人工校正） |
| `assemble_report.json` | 六类状态计数、缺口清单、体检明细 | 装配流水线 |

**标题到全称的对齐规则**（§2.4 的接缝）：

1. 优先取正文首部的书名号内容；
2. 其次取落款前的标题行；
3. 都没有则用目录标题，并标记 `name_src = 目录标题`（闸门 2 会因此更容易失败，
   这是诚实的代价，不能靠猜补齐）。

## 6.3 增量刷新

| 项 | 规格 |
|---|---|
| 增量判据 | ① 源端按 `pubtime` 倒序取前 N 页；② 与库里 `last_seen` 比对；③ 用文号做二次去重 |
| 已知漏洞 | 政府站修订版常常沿用原文号、不发新日期 → 增量会漏掉修订 |
| 补法 | 每周一次全量（13 分钟），不完全依赖增量 |
| 记录 | 每次刷新记 `runs`，报告「新增 / 变动 / 消失」三个数 |

# 7. 指标口径

v1 只有一套指标（66 题）。v2 必须拆成三层，**因为三层的判据不同**，
混在一起会掩盖问题。

## 7.1 目录层（判据：不能漏）

| 指标 | 口径 | 当前实测 |
|---|---|---|
| 覆盖度 | 三级各自 `ok / partial / missing` | 国家 partial / 省级 missing / 市级 ok |
| 状态完整性 | 每个源都必须有状态词，无空白 | 7/7 |
| 源端命中解释率 | 收录数 ÷ 命中数，差额必须有解释 | 鹰潭 3/276；**273 条差额只抽看过一小部分，未逐条核对** |
| 穷举能力 | 深翻页是否受限 | 实测 p=70 正常，无封顶 |
| 字段依据覆盖率 | 推断字段带依据的比例 | 100% |

## 7.2 装配层（判据：不能错）

| 指标 | 口径 | 目标 | 当前 |
|---|---|---|---|
| 抓取成功率 | 成功抓到正文 ÷ 候选数 | ≥95% | 未实现 |
| 解析成功率 | 解析成功 ÷ 抓取成功 | ≥90% | 未实现 |
| 体检通过率 | 通过 ÷ 解析成功 | ≥90% | 未实现 |
| 条数表自洽率 | 条数表与正文一致 ÷ 总数 | 100% | 未实现 |
| 效力确认率 | 人工确认 ÷ 入库数 | 100% | 未实现 |
| 装配耗时 | 50–80 份端到端 | 未验证 | **未验证** |

## 7.3 问答层（判据：不能错）

沿用 v1 的 66 题口径（引用可追溯 100%、真编造 0%、时效违规 0、边界 40/40、
闸门自检 11/11），但**必须满足两个前提才算数**：

1. 指标只在**当次评估所用的那个库**上有效；
2. 换库（换专题）之后必须重跑，**不得沿用旧数字**。

## 7.4 不得沿用的旧数字

这一条单独列出来，因为它是本版最容易犯的错：

| 旧数字 | 来源 | 换专题库后能否沿用 |
|---|---|---|
| 闸门 1 阈值 0.40 | 8 部法规上标定 | **不能**，必须重标 |
| recall@1 65/66 | 8 部法规 | **不能** |
| top-8 召回 15/15 | 8 部 / 419 单元 | **不能**，库变了 |
| 引用可追溯 100% | 66 题 | **不能**，需重测 |

沿用的后果是「看起来有实测支撑，其实是换了语料没换数字」——比没有数字更危险。

# 8. 冷启动

新用户打开时库里必须有东西，否则第一印象就是空的。

| 做法 | 规格 |
|---|---|
| 预置专题库 | 4 个：城市更新 / 历史文化保护 / 土地征收 / 规划许可 |
| 每个库的构成 | 国家级（30–40 份）+ 3 个典型省市（各 10–15 份） |
| 幂等 | 预置库的效力状态必须是**已人工确认**的，否则闸门 2 只能半工作 |
| 展示 | 首屏直接给「这 4 个库各有哪些文件、覆盖到哪一级」，不让用户先学会提问 |
| 成本 | 4 库 × 80 份 = 320 份的人工效力确认，是这个方案最大的冷启动成本 |

**这条成本要提前认**：预置库如果不确认效力，它就只能当目录用；
当目录用的话，预置的价值主要是「演示」，不是「可用」。两者要分清。

# 9. 已知边界与风险

## 9.1 为什么不做全量全文库（最硬的约束）

19,026 份 × 平均 5 千字 ≈ 9,500 万字 ≈ 30 万个切分单元。能存能检，但：

| 能力 | 8 部 / 419 单元 | 19,026 份 / 30 万单元 |
|---|---|---|
| 条数表 | 手工核对，精确 | 无来源，只能解析导出，准确性未知 |
| 时效台账 | 逐部核对 | **不可能逐部核对** |
| 闸门 2 C1/C3 | 可用 | **失效（退化為「未核」）** |
| 闸门 1 的「没有」 | 可信（库小，能确认装了什么） | **不可信**（检索不到 ≠ 不存在） |
| 答案冲突 | 人脑可裁 | 需另一套冲突裁决机制 |

**结论**：巨型库会让这个产品的核心判据失效，退化成普通 RAG。所以全文层按专题装配。

## 9.2 风险登记

| # | 风险 | 现状 | 应对 |
|---|---|---|---|
| 1 | 省级源抓不到（江西 TRS） | 省级恒为 `missing` | 人工清单兜底（**当前为空**）；或换源（省政府公报导出） |
| 2 | flk 接口未通 | `blocked`，17 个路径已知，参数体打不通 | ① 官方导出后 `--import`；② 投一天逆向 `search/list` |
| 3 | doc / pdf 不能零依赖解析 | 实测 OLE2 / PDF 均不可 | 外部转换一步；装配报告分开统计两类 |
| 4 | 标题与全称不一致 | 接缝风险（§2.4） | 三级对齐规则；对不齐时标 `name_src`，不猜 |
| 5 | 体检误杀分条不明显的文件 | 判型机制尚未实现 | 先判型再检查；分段型不套用条数判据 |
| 6 | 闸门 1 阈值需逐库重标 | v1 的 0.40 不可搬 | 每个新库标定一次，标定结果写进库的元数据 |
| 7 | 装配耗时未实测 | 「10 分钟」是估算 | **不得作为承诺对外说**，先测再说 |
| 8 | 增量漏掉修订版 | 政府站改文不改日期 | 每周一次全量（13 分钟） |
| 9 | 预置库效力未确认 | 冷启动成本高 | 先做 1 个库验证，再决定要不要做 4 个 |
| 10 | 无真实用户验证 | 66 题是自造的 | 找 3 个从业者各问 3 个真实问题 |

## 11.1 已改（正文已是修正后的版本）

## 11.2 保留未改（有理由）

| # | 问题 | 为什么不改 |
|---|---|---|
| 1 | **「RAG 占比从 100% 降到 30%」是估的，不是量的** | 无法用代码行数或耗时客观量化。保留是因为它传达的是架构重心变化，不是精确指标。已在措辞上用「大约」 |
| 2 | **装配流水线只有规格，没有实现** | 这是本版的真实状态，不假装已完成。§0 表格里已标明「只有规格」 |
| 3 | **问答层指标仍是 8 部法规上的数字** | 换库重测需要流水线先落地，现在改不了。§7.3 已加两个前提，§7.4 已列出不可沿用的清单 |

## 11.3 审查里最值得记住的一条

**这份 PRD 最大的风险是「实测数字被跨场景挪用」。**
v1 攒下的一套漂亮数字（100% / 0% / 40-40）全都是 8 部法规上量的，
而 v2 把库换成了 50–80 份的专题库。**换库不换数字，等于用旧考卷的成绩证明新学生的水平。**

这条已经写进 §7.4。它属于流程问题，写进文档治不了——
以后每次换库，第一件事应该是把旧指标作废，而不是先跑新库。
