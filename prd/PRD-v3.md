### 0.3.3 关键判断：这是两个任务，不是一个任务的两种做法

竞品盘点最容易得出的错误结论是「打不过，所以换战场」。这个结论接受了对方定义的战场。

| | 北大法宝 / 威科 / 法信 | 有据 |
|---|---|---|
| 回答的问题 | 有哪些文件 | **你引的这一条站不站得住** |
| 判据 | 覆盖 | **判定** |
| 赢的条件 | 数据量 | **规则完备** |
| 「8 部 vs 320 万篇」 | 致命 | **不进这个比较** |

**检索与校验是两个不同的任务。** 竞品改善的是「生成质量」，本产品提供的是「交付前的合规判定」。
覆盖比不过，判定根本不需要覆盖——用户从权威源查到依据，把依据交给本产品核。

**技术路径的差别是可验证的**，不是修辞：竞品的「降低幻觉」是概率改善，「一键溯源」是把原文摆出来让人自己看；
本产品的 C1–C5 是**不调用模型的机器闸门**，核不过就不给结论，且同输入必同结论。

> 最有说服力的实证是 C5 的诞生过程（`research/10` §4）：66 题在 Dify 链路上零失误的错误——
> 模型把库内《呼伦贝尔市城市市容和环境卫生管理条例》当成用户所问的库外《城市市容和环境卫生管理条例》，
> C1–C4 全部通过——换成直连 `qwen-plus` 第一次跑就复现了。
> 它证明的是：**写在提示词里的硬约束，可靠性跟模型绑死；搬进规则层才成立。**

### 0.3.4 竞品的三个结构性盲区，以及各自的水分

**盲区一 · 地方非立法类文件。** 竞品收录核心是有立法效力层级的文件；而规划师做立项论证时最直接的依据——
市级专项规划、年度计划、实施方案、攻坚行动——多数不在里面。

> **此盲区真实，但本产品对它的覆盖能力尚未验证，当前不得作为卖点。**
> 目录层省级源恒为 `blocked`，flk 亦 `blocked`，`manual.csv` 只有表头。
> 收录率已于 2026-10-19 实测（见 `data/catalog/audit_yingtan.json`、`docs/优化方向-v1.md` §0）：
> 鹰潭站源端 287 条、去重 212 条、真误杀 1 条（≈0.5%）。**误杀率可接受，但 26% 的重复率说明「源端命中数」不能当文件数用。**

**盲区二 · 没有私有稿件入口。** 三家全是检索型工具，没有一家接受用户上传自己的稿件逐条核对。
原因是结构性的：责任边界（稿件是未公开资产）、技术路径（需要确定性判定而非生成）、商业模式（账号订阅 vs 按次计费 + 服务责任）。

> **这是本产品最重要的战略发现：已有的技术资产，配的是一个尚未做的场景。**
> C1–C5 的天然输入是「一批引用」，不是「一个自然语言问题」。FR-04 排在 P1 是优先级错误。

**盲区三 · 不对结论负责。** 竞品的准确率是营销话术；本产品有一整套可验收指标（§7.2）。
在政府项目、国企送审场景里，「可写进合同的准确率承诺」有真实付费意愿，因为出错责任在甲方。

### 0.3.5 一处必须如实记录的数据分歧

关于威科的时效能力，两个来源结论相反：

| 来源 | 结论 |
|---|---|
| 威科官网详情页字段（2026-07） | 含「时效性」「历史修订记录」字段 |
| 第三方 MCP 测评（2026-07） | 「无法直接查看历次修订记录」「无直接时效性筛选参数」 |

**推断（非事实）**：网页端有，接口层未开放。二者可同时为真。
若成立，则任何想把法规核验嵌进自身业务系统的集成方，会撞上与本产品目录层相同的困境——**能查，接不进来**。
这构成本产品的第二个位置：**可被任意系统调用的独立校验层**（`gatekeeper.py` 单文件、零依赖、断网可跑）。

> ⚠️ **此推断未验证，验证前不得作为对外宣传口径**（T-11）。

### 0.3.6 定位修订（待决策，尚未采纳）

候选表述：

> 有据是一个法规引用的确定性校验层。它不替代权威数据库——用户仍从那里查依据。
> 有据做的是在依据写入正式文件之后、送审之前，用不调用模型的规则逐条核对：条号是否越界、引文是否真实、法规是否失效、名称是否错配、所问法规划界。
> 核不过，就不给结论。**输入是「你已经查到的依据」，输出是「一份可以随稿提交的核验报告」。**

**采纳这条定位有三个前提，目前一个都没验：**

1. 「送审被打回常常因为引用错」——未访谈验证（T-15 的第 1 问）
2. 核验场景下 C3（时效）可用——实际上用户带来的文件通常不写效力状态，省级与 flk 均 `blocked`，
   **C3 在稿件场景大概率只能标「未核」**
3. 核验场景下 C5（所问法规划界）可用——稿件场景**没有「问题」**，C5 无输入，**直接失效**

**所以定位只在 §0.3.6 存为候选，§1.1 的定位暂不替换。**
翻转的完整代价核算见 `docs/优化方向-v1.md` §2.2：**五项检查搬过去只剩三项半，不是五项。**

# 1. 背景与目标

## 1.1 业务背景

规划师写的东西要交出去，交出去的东西会被人追问「依据是什么」。这个追问在三个环节上出现，每个环节现有工具都不管用。

**环节一：立项前的政策梳理。** 接了江西鹰潭的城市更新项目，需要知道鹰潭市本级有哪些文件、江西省有哪些、国务院和部委有哪些，以及历史文化保护方面的相关规定。现状是人工在 4–6 个政府站之间翻，边翻边记。产出的清单直接进项目建议书的「政策依据」一章。**这一步的判据是不能漏**——漏了一份关键文件，整章的论证基础就不完整。

**环节二：起草时的引用核对。** 写完一章，逐条核对引用的条号是否存在、引用的法规是否还有效。现状靠人记和地方经验。**这一步的判据是不能错**。

**环节三：送审前的自查。** 把稿子交给评审前跑一遍，产出引用清单 + 时效状态 + 疑似问题列表。现状是抽查。**这一步的判据是可解释**——每一条问题都要能指到具体位置，否则作者没法改。

## 1.2 问题定义

| 编号 | 问题 | 现况数据 | 现有方案为何解决不了 |
|---|---|---|---|
| P1 | 政策清单靠人工翻站 | **基线未测**（测量方法见 §7.1） | 通用搜索引擎按相关性排序，不能按地域 × 效力级别穷举，也**说不出「没有」**——检索不到与不存在在界面上长得一样 |
| P2 | 已废止文件混在检索结果里 | 8 部语料中有已登记失效/废止的文件（见 `data/stale_ledger.json`）；政府站普遍不撤失效文件，改为在文末标注 | 通用搜索与通用大模型都没有效力维度，会把废止文件当现行依据给出 |
| P3 | 大模型引用的条号会编 | 本项目 D1 阶段做过 10 模型通用横评（`eval/results/` 有原始 CSV）；**具体引用错误率待从 CSV 提取** | 提示词里的「必须引用原文」属于模型自觉，换模型、调温度都会失效 |
| P4 | 政策文件格式不统一，正文难批量入库 | 实测：`.docx` 可零依赖解析；`.doc`（OLE2）与 `.pdf` 零依赖不可解析 | 通用 RAG 建库工具假定输入是干净的文本或 PDF，不处理「省市级文件大量是 doc 附件」这件事 |

# 2. 用户与场景

## 2.1 用户角色

| 角色 | 是谁 | 主要诉求 | 对 AI 的容忍度 |
|---|---|---|---|
| 规划师（主用户） | 规划院/所的项目负责人、主创 | 要一份能进文档、能被追问的清单与依据 | 低。错一次就不再信任，且不会主动举报 |
| 审校人 | 院里的总工、审核岗 | 要能快速检查别人的稿子引了什么 | 中。看重可解释，接受机器给候选 |
| 管理员 | 一个人维护全部专题库 | 要库别烂、别过期 | 中。看重可维护、可批量 |

## 2.2 权限矩阵

| 功能 | 规划师 | 审校人 | 管理员 |
|---|---|---|---|
| 查政策清单 | ✅ | ✅ | ✅ |
| 触发重新抓取（联网） | ✅ | ❌ | ✅ |
| 装配专题库 | ❌（只能申请） | ❌ | ✅ |
| 确认文件效力状态 | ❌ | ✅（复核） | ✅（主责） |
| 执行逐条核验 | ✅ | ✅ | ✅ |
| 修改条数表 / 时效台账 | ❌ | ❌ | ✅ |
| 关闭 AI 能力（降级开关） | ❌ | ❌ | ✅ |
| 查看评测看板 | ❌ | ✅ | ✅ |

**为什么「确认效力状态」不给规划师**：这一栏一旦被随手点过，整条链路的判据就废了。它必须由对一个库负责的人做，而规划师按项目进出，不会对库负责。

## 2.3 典型场景（端到端，鹰潭城市更新）

```
① 规划师输入：地域=鹰潭，主题=城市更新
   → 系统出清单：国家级 21 份 / 省级 0（显式标缺）/ 市级 3 份
   → 覆盖度条首行写「省级缺失：江西省站无可用检索接口，需人工补」

② 规划师勾选 30 份，申请装配
   → 管理员执行装配：抓全文 → 解析成条 → 体检 → 出条数表
   → 体检不通过的进「待人工」，附原因（不是简单报错）

③ 管理员确认 30 份的效力状态（现行有效 / 已废止 / 未知）
   → 台账落库，进入检索池的只有「现行有效」+「未知（标注）」

④ 规划师提问或贴稿
   → 检索 → 生成 → 闸门 2 五项校验 → 结论 + 逐条依据 + 时效状态

⑤ 送审前跑全稿自查
   → 输出引用清单 + 问题列表 + 漏引候选（目录 N 份 vs 稿子引了 M 份，N-M 是候选）
```

**第 ① 步里最重要的一行是「省级缺失」**。市级抓到 3 份、省级 0 份，如果只打印清单，用户会以为江西省没有相关文件。兜底型工具宁可显得笨，不能显得全。

# 4. 业务流程

## 4.1 端到端流程（标注每步由谁执行）

```
【准备】管理员维护目录源
   │  🤖 系统：每日增量抓取国家级 + 已适配的省市站
   │  👤 管理员：看抓取报告，处理 blocked / unavailable 的源

【① 发现】规划师查清单
   │  🤖 系统：按地域链 × 主题出清单 + 覆盖度（不调模型）
   │  👤 规划师：勾选要用的文件 → 提交装配申请

【② 装配】管理员执行
   │  🤖 系统：抓全文 → 解析成条 → 体检 → 出条数表（doc/pdf 转外部处理）
   │  👤 管理员：逐份确认效力状态；体检不通的进「待人工」

【③ 核验】规划师提问 / 贴稿
   │  🤖 系统：检索 → 模型生成 → 闸门 2 五项校验（C1–C5 不调模型）
   │  👤 规划师：看结论与依据；对「部分作答/拒答」自行判断

【④ 交付】出清单与报告
   │  🤖 系统：引用清单 + 时效状态 + 问题列表
   │  👤 规划师：贴进文档 / 随稿提交
```

## 4.2 AI 参与的节点（决策表）

| 节点 | AI 做什么 | 人工做什么 | 自主程度 | 失败怎么办 |
|---|---|---|---|---|
| 发现 | 出清单 + 覆盖度 | 决定用哪些 | L1 建议 | 显示「该源未覆盖」，退回人工翻站 |
| 装配 | 抓取 + 解析 + 体检 + 出表 | 确认效力 | L2 执行+确认 | 解析失败的进「待人工」，不静默丢弃 |
| 核验 | 生成结论 + 规则校验 | 看结论决定是否采信 | L2 执行+确认 | 校验不通过降级为「部分作答」或「拒答」 |
| 时效 | 给候选与来源链接 | 确认 | L2 | 无证据即标「未知」，不默认有效 |

## 4.3 异常与降级流程

| 异常 | 判定条件 | 降级动作 | 用户感知 |
|---|---|---|---|
| 模型服务超时 | 单次 > 30s | 返回「本次未能生成，以下为检索到的原文」 | 顶部提示「已切换为原文模式」，仍给条文 |
| 模型服务不可用 | 连续 3 次调用失败 | 全局关闭生成能力，只保留清单 + 原文 | 界面进入「只读模式」 |
| 检索无结果 | 闸门 1 判定话题级不命中 | 不生成结论 | 明确写「库里没有这个话题」，**并给目录层的文件清单作为替代** |
| 条号越界（C1） | 引用的条号 > 条数表 | 该条依据标「不通过」，结论降级 | 显示「引用的第 X 条不存在，该文件共 N 条」 |
| 引用废止文件（C3） | 名称命中台账且状态非现行有效 | 拦截该依据 | 显示「《X》已于 YYYY-MM-DD 废止，替代文件为《Z》」 |
| 目录源不可用 | 连续 2 次抓取失败 | 保留上次缓存，标 `stale` | 清单顶部写「数据截至 YYYY-MM-DD，该源今日未更新」 |
| 成本超预算 | 日成本 > 预算 120% | 降低检索 topk，关闭非必要重排 | 无感知（延迟略降） |

**降级的目标是「退回一个仍然有用的形态」，报错不算降级。** 这个产品有三个形态，任何一个都比报错好：

1. 完整形态：清单 + 结论 + 依据 + 校验
2. 原文形态（模型挂了）：清单 + 检索到的原文，用户自己读
3. 清单形态（全挂）：只有目录层，用户至少知道有哪些文件

第 3 种形态之所以还有用，是因为目录层不依赖模型、不依赖外部 API，只依赖政府站和自己的 SQLite。

# 5. 功能需求

## FR-01 政策清单（目录层）

- **优先级**：P0
- **功能描述**：按「地域链 × 主题」输出政策文件清单，带覆盖度与失效状态
- **前置条件**：`data/catalog.db` 存在或有可用的源配置；无网络时读缓存
- **处理规则**：
  1. 地域按 `regions.chain` 向上展开（鹰潭市 → 江西省 → 国家）
  2. 主题按 11 个词表匹配标题；跨领域可用多个主题（如城市更新 + 历史文化保护）
  3. 自各源抓取，每个源返回独立状态（`ok / empty / blocked / unavailable / error / skipped`）
  4. 同一条目多源命中时合并，**每个推断字段必须带依据**（文号 / 时效台账 / 来源库 / 来源站点 / 标题 / 无法判定）
  5. 按行政层级 → 发布日期倒序排列
  6. 覆盖度三级汇总（国家 / 省级 / 市级），`missing` 必须显式输出并附原因
- **输入**：地域、主题（可多选）、关键词（可选）、翻页深度
- **输出**：条目列表 + 覆盖度 + 各源状态 + 未覆盖清单
- **异常处理**：
  - 源端返回空 → 标 `empty`，不当成「没有文件」
  - 源端结构变化 → 标 `error`，保留上次缓存并标 `stale`
  - 反爬拦截 → 标 `blocked`，附探测记录
- **验收标准**：
  - AC-01：输入「鹰潭 / 城市更新」，输出含国家级 ≥ 20 份、市级 ≥ 3 份，省级显式标 `missing`
  - AC-02：任一源失败时，界面不出现「该级没有文件」这类断言
  - AC-03：离线自检 `crawl.py --selftest` 26/26 通过
- **关联需求**：S1、S7
- **已实现**：`scripts/catalog/`，实测见 §9.4

## FR-02 专题库装配

- **优先级**：P0
- **功能描述**：从清单勾选 N 份文件，抓全文、解析成条、体检、出三张表
- **前置条件**：清单已生成；文件 URL 可用
- **处理规则**：
  1. 抓全文（HTML 优先；`.docx` 用 `zipfile` 读 `word/document.xml`；`.doc` / `.pdf` 归入 `pending_convert`）
  2. **判型**（分条型 / 分段型 / 无结构型），按型选判据，避免用条数判据误杀分段式文件
  3. 体检三重判据：结构完整性、内容完整性、可引用性（见 §6.5）
  4. 通过者生成条数表；不通过者进「待人工」并附具体原因
  5. 出准入分级：`accepted / accepted_with_warning / pending_manual / rejected`
- **输入**：文件清单（含 URL）
- **输出**：全文 + 条数表 + 体检报告 + 待人工清单（**分类统计，不能笼统报「N 份待人工」**）
- **异常处理**：
  - `.doc` / `.pdf` → 归 `pending_convert`，附转换工具建议，不静默丢弃
  - 抓下来是错误页（200 但内容是 404 页）→ 按内容特征判，不按状态码判
  - 解析出的条数为 0 → 判型失败，进待人工
- **验收标准**：
  - AC-04：对已解析的 `.docx` 样本，条数与原文「第X条」计数一致
  - AC-05：体检不通过的文件 100% 出现在待人工清单里，且带原因
  - AC-06：报告按格式（HTML / docx / doc / pdf）分类统计成功率
- **关联需求**：S2
- **状态**：未开发

## FR-03 逐条核验（闸门 2）

- **优先级**：P0
- **功能描述**：对一次问答或一条引用，执行五项确定性校验，输出可解释结论
- **前置条件**：库内有三张表；提问已检索到候选条文
- **处理规则**：
  1. **闸门 1（话题级）**：检索分数过低 → 判「库里没有这个话题」，不生成
  2. **闸门 2（条文级）**，五项检查全部不调模型：
     - C1 条号越界：引用条号 > 条数表
     - C2 引文查不到：引用文本在原文中找不到
     - C3 时效违规：引用的文件已废止/失效
     - C4 名称错配：文件简称与全称对不上
     - C5 所问法规划界：回答引用了不在所问范围内的法规
  3. 结论分三档：可作答 / 部分作答 / 拒答
  4. 每条依据逐项列出通过与否，结论强度随之降级
- **输入**：问题 + 模型输出
- **输出**：结论 + 逐条依据 + 五项校验明细 + 引用清单
- **异常处理**：
  - 台账缺失 → C3 标「未核」，**不默认现行有效**
  - 条数表缺失 → C1 标「未核」
  - 模型未给条号 → C1/C2 标「无法校验」并降级结论
- **验收标准**：
  - AC-07：C1–C5 每组既有一条应通过用例，也有一条应拦截用例（现有 11 组）
  - AC-08：校验层不发起任何网络请求（可通过断网跑通验证）
  - AC-09：同一输入两次运行结论完全一致（无随机性）
- **关联需求**：S3、S4
- **已实现**：`scripts/gatekeeper.py`

## FR-04 全稿自查

- **优先级**：P1
- **功能描述**：贴入一份稿子，抽出全部法定引用，逐条核验，并给出漏引候选
- **前置条件**：已装好对应专题库
- **处理规则**：
  1. 抽取引用（《X》第 N 条 / 依据《X》/ 文号）
  2. 逐条走 FR-03
  3. **漏引候选**：目录层该方向 N 份，稿子只引了 M 份，差额按主题相关度排序输出为候选
  4. 输出按「必须改 / 建议看 / 可忽略」三级
- **输入**：稿件全文（粘贴或上传 docx）
- **输出**：引用清单 + 问题列表 + 漏引候选 + 汇总统计
- **异常处理**：抽取不到引用 → 明确写「未识别到法定引用」，不给「全部通过」的假结论
- **验收标准**：
  - AC-10：抽取召回率在 20 条人工标注引用上 ≥ 95%
  - AC-11：漏引候选必须显式标注「以下是候选清单，请自行判断」，不得表述为结论
- **关联需求**：S4
- **状态**：未开发

## FR-05 时效台账维护

- **优先级**：P0
- **功能描述**：为库内每份文件维护效力状态，作为 C3 的唯一外部真值
- **前置条件**：文件已入库
- **处理规则**：
  1. 机器给出候选状态与来源链接（源站文末标注、法规库详情页）
  2. 人工逐份确认，记录确认人与时间
  3. 未确认的标「未知」，**不参与「现行有效」判定**
  4. 废止文件必须记录替代文件
- **输入**：文件清单
- **输出**：`stale_ledger.json`（含状态、依据、确认人、确认时间）
- **异常处理**：源站无标注 → 标「未知」，并在界面提示「该文件时效需查法制部门口径」
- **验收标准**：
  - AC-12：台账中每一条都有确认人与时间，无「机器自报」
  - AC-13：C3 只读台账，不读模型输出
- **关联需求**：S5
- **状态**：已实现（8 部），需扩到专题库规模

## FR-06 评测与 badcase 看板

- **优先级**：P1
- **功能描述**：离线跑批 + 线上反馈汇集，回答「这次改动是优化还是劣化」
- **处理规则**：
  1. 评测集分层：能力维度 × 难度
  2. 每次改动跑全量，输出对比表
  3. 线上「这条不对」的反馈自动进 badcase 池
  4. 每月从 badcase 补充 ≥ 10 条进评测集
- **验收标准**：
  - AC-14：任意两个版本可对比，输出逐题 diff
  - AC-15：badcase 池每条带原始输入与当时的判定
- **关联需求**：S6
- **状态**：部分已实现（`eval_run_app.py`）

## FR-07 一键降级开关

- **优先级**：P0
- **功能描述**：30 秒内关闭全部模型能力，退回清单 + 原文形态
- **处理规则**：单个配置项；关闭后前端显示「只读模式」；不影响目录层
- **验收标准**：
  - AC-16：关闭后所有问答请求返回「原文模式」而不是报错
  - AC-17：关闭动作不需要发版
- **关联需求**：S7
- **状态**：未实现（当前需改代码）

# 6. AI 能力设计

这一节是 AI 产品 PRD 的核心新增部分。本产品的特殊之处在于：**模型只承担链路上的一小段，其余全是确定性工程**，所以这一节的重点是「哪些地方故意不用模型」。

## 6.1 能力全景与方案选型

| 要办的事 | 方案 | 为什么不用别的方案 |
|---|---|---|
| 这个方向有哪些文件 | 结构化查询（SQLite + 政府站检索接口） | 不用向量检索：要能穷举、要按效力级别与地域过滤、要能说出「没有」。相似度无法表达「不存在」 |
| 这条依据在库里的哪里 | **混合检索（BM25 + 可选向量）← RAG 在这** | 不用结构化查询：用户问的是自然语言，同一个意思有多种说法 |
| 模型说的第 42 条到底有没有 | 确定性查找（全称 + 条号 + 原文子串比对） | 不用模型判断：要可复现、要能写进服务承诺、要在断网下也成立 |
| 这份文件还有效吗 | 查外部台账（`stale_ledger.json`） | 不用模型推断：模型自报「现行有效」等于自验 |
| 这份文件该归到哪一级 | 文号 + 标题规则推断，无依据就留空 | 不用模型：推断结果必须能说清依据，模型说不清 |

**方案选型决策记录：为什么不用微调**

| 维度 | RAG + 规则 | 微调 |
|---|---|---|
| 政策更新 | 改库即可，当天生效 | 需重新训练，周期 2–4 周 |
| 可溯源 | 每条依据能指到条款 | 无法给出引用 |
| 幻觉控制 | 可限定「只依据检索到的条文回答」，且规则层能拦 | 不可控 |
| 效力状态 | 可外接台账 | 学不进去 |
| 成本 | 按调用付费，可预测 | 训练成本 + 持续维护 |

四个产品维度全部指向 RAG + 规则。微调不是技术上做不到，是它改的是风格与格式，注不进「第 42 条是什么」这种事实，也注不进「什么时候废止的」。

**架构选择：工作流式，非自主 Agent**

| 对比项 | 工作流式 | 自主 Agent | 本场景 |
|---|---|---|---|
| 可控性 | 每步可测 | 难测 | ✅ 工作流 |
| 可复现 | 同输入同结论 | 不稳定 | ✅ 工作流 |
| 错误定位 | 能指到第几步 | 难复现 | ✅ 工作流 |
| 成本 | 可预估 | 波动大 | ✅ 工作流 |

一个需要写进合同的准确性承诺，承受不起不可复现。

## 6.2 模型选型与分级

| 任务 | 档位 | 理由 | 实测/预估调用量 |
|---|---|---|---|
| 全文核验（C1–C5） | **规则引擎（非模型）** | 必须 100% 确定，不能有概率 | 每次问答 |
| 目录字段推断（效力级别/地域） | **规则引擎（非模型）** | 推断要能说清依据 | 每个条目 |
| 目录抓取 | **HTTP + 解析（非模型）** | 抓取不需要理解 | 每次刷新 |
| 结论生成 | 中杯模型（当前 `qwen-plus`） | 需要一定归纳能力，对创意无要求 | 每次问答 |
| 稿件引用抽取 | 轻量模型或规则 | 模式固定（《》第N条），优先规则 | 每次自查 |
| 评测打分 | 旗舰 + 人工抽检 | 需要稳定判断力 | 每次跑批 |

当前配置：`dashscope/qwen-plus`。**换模型必须重跑评测集**，理由见 §7.5。

## 6.3 提示词设计

系统提示 4,317 字，实测 2,863 token，占单次输入的 72%（详见 §9.1）。结构如下：

```
# 角色      你是政策条文核验助手。只依据给出的条文回答。
# 硬约束    ① 不得引用给出条文之外的任何法规
            ② 不得推断未在条文中出现的数字、期限、责任主体
            ③ 不符合时明确拒答，并说明缺什么
            ④ 不回答「我该怎么办」这类建议性问题
# 输出格式  结论 / 依据（法规全称 + 条号 + 原文） / 未能回答的部分
# 拒答措辞  固定句式，便于下游规则层识别
```

**两条边界必须写进提示词（对应 §3.2 的 N1 与 N3）**：

- N1 不给法律意见 → 提示词里写死：「当用户询问是否应该做某件事、如何规避某项规定、能否获得补偿时，必须回复『该问题需由主管部门认定』，不得给出判断性结论。」
- N3 不自动确认效力 → 提示词里写死：「不得声称任何文件的效力状态。效力状态由系统台账给出，你的输出中不包含该字段。」

**为什么不把五项校验写进提示词**：写了也只是「模型自觉」。C5 的发现过程就是实证——在 Dify 链路上 66 题一次没犯的错，换成直连 `qwen-plus` 第一次跑就犯了，而它恰好落在原有四项检查之外。**约束必须搬进规则层才能不依赖模型。**

## 6.4 检索策略

| 项 | 规格 | 依据 |
|---|---|---|
| 检索方式 | BM25 为主，向量可选 | 专题库 2,000–4,000 条，词面匹配足够；零依赖带来可复现性，比几个百分点的召回值钱 |
| 召回数 | top 8（当前） | 4095 条语料上实测够用；专题库规模扩大后需重标 |
| 上下文长度 | 实测 830–2,125 字 | 折合约 550–1,410 token，占输入 14%–36%（按中文 0.66 token/字换算） |
| 检索耗时 | 未单独测量 | 规模扩大后必测 |
| 闸门 1 阈值 | 当前 0.40 | **8 部法规上标的，换库必须重标**（§7.5） |
| 时效过滤 | 检索池默认排除已废止，除非用户显式问 | `stale_ledger.json` 驱动 |

## 6.5 核验层设计（闸门 2）

这是本产品唯一不可替代的部分。五项检查全部不调模型：

| 检查 | 判据 | 数据来源 | 失败后果 |
|---|---|---|---|
| C1 条号越界 | 引用条号 > 条数表记录 | `article_counts.json` | 该依据不通过，结论降级 |
| C2 引文查不到 | 引用文本在原文中找不到 | 语料正文 | 该依据不通过 |
| C3 时效违规 | 引用的文件已废止/失效 | `stale_ledger.json` | 拦截该依据 |
| C4 名称错配 | 简称与全称对不上 | `doc_names.json` | 提示名称有误 |
| C5 所问法规划界 | 引用了不在问题范围内的法规 | 问题 → 法规映射 | 提示超出范围 |

**三项表缺失时的行为是设计重点**：缺一张表就把对应检查标「未核」，**结论随之降级，绝不默认通过**。这决定了「没抓到」不会伪装成「没问题」。

### 6.5.1 装配体检必须先判型

这是 v2 里最容易被真实数据打穿的一处，本版单列。

现有的 8 部法规全是「第X条」的法典式文件，条数对齐很好用。但省市级规范性文件大量是「一、（一）」分段式，根本不分条。拿条数判据去体检，会把大批真文件判成坏的。

| 型 | 特征 | 体检判据 | 对 C1 的影响 |
|---|---|---|---|
| 分条型 | 有「第X条」序列 | 条号连续、无重复、与原文计数一致 | C1 正常工作 |
| 分段型 | 有「一、」「（一）」层级 | 层级完整、编号连续 | C1 降级为「编号存在性检查」 |
| 无结构型 | 通篇段落 | 只查长度与非空 | C1 不适用，标「无法校验」 |

判型失败 → 进 `pending_manual`，附「疑似 XX 型，但结构不完整」。

## 6.6 失败与降级设计

见 §4.3。这里只补一条设计原则：**每个失败都必须有对应的界面表达**。三类异常的处理方式完全不同：

| 异常类型 | 例子 | 处理 | 用户看到什么 |
|---|---|---|---|
| 技术异常 | 超时、格式错 | 重试 1 次 → 降级 | 「已切换为原文模式」 |
| 能力异常 | 检索未命中 | 兜底 + 记录回流 | 「库里没有这个话题」+ 文件清单 |
| 正确性异常 | 幻觉、引用失效 | 规则拦截 + 强制溯源 | 「第 X 条不存在」这类可核对的说明 |

第三类最危险，因为**它不会报错**。一个编造的条号在界面上与真实条号长得一样。这就是闸门 2 存在的全部理由。

# 7. 效果标准

这一节决定产品能不能被验收。本项目的现状是：**有一组成绩，但这组成绩是自测的，不能直接当验收依据。**

## 7.1 评测集设计

### 7.1.1 现状（必须先说清）

现有 `eval/golden-set.csv`，66 题，按能力维度分层：

| 分层 | 题数 | 占比 | 考什么 |
|---|---|---|---|
| L1 基础 | 12 | 18.2% | 单点检索，找得到 |
| L2 推理 | 8 | 12.1% | 跨条合并、条件推理 |
| L3 边界 | 6 | 9.1% | 库里没有、问题模糊 |
| L4 对抗 | 40 | **60.6%** | 引用废止、条号越界、诱导编造 |

**这组分布有问题：对抗题占六成，真实使用里不会是这个比例。** 它测的是「这套系统有多难被打穿」，不是「这套系统在正常使用中有多好用」。拿它当验收依据，会得出一个「对抗题 40/40 全过」的漂亮结论，同时掩盖「正常问题答得别扭」这类更常见的问题。

对照行业常见做法（简单 30% / 中等 45% / 复杂 25%），正确的做法是把两个轴分开：**能力维度**（L1–L4）× **难度**（简单/中等/复杂）。

### 7.1.2 重建规格（V3 的硬要求）

| 项 | 规格 |
|---|---|
| 规模 | 120 题（上线门槛）；目标 200 题 |
| 分层一：能力维度 | 基础 25% / 推理 30% / 边界 20% / 对抗 25% |
| 分层二：难度 | 简单 30% / 中等 45% / 复杂 25% |
| 覆盖 | 至少 3 个专题（城市更新、历史文化保护、土地管理），每个专题 ≥ 30 题 |
| 样本来源 | ① 规划师真实提问 50%（**必须由非本人提供**）② 从实际稿件里抽的引用 30% ③ 对抗样本 20% |
| 标注内容 | 标准答案、应有引用（文件全称 + 条号）、是否应拒答、难度、出处 |
| 标注人 | 规划师 2 人交叉复核；本人只负责仲裁 |
| 更新机制 | 每月从线上 badcase 补 ≥ 10 题 |
| 不得复用 | 8 部法规上的 66 题可保留为「历史基线集」，**不得作为专题库的验收依据** |

**为什么「必须由非本人提供」是硬要求**：出题人、判分人、被考核对象是同一个人的时候，评测集测的是「我有没有按我的预期实现」，证明不了「这东西对别人有用」。

### 7.1.3 评测集样例

| ID | 输入 | 标准答案 | 类型 | 难度 | 应拒答 |
|---|---|---|---|---|---|
| E-001 | 鹰潭市城市更新专项规划里，棚户区改造的适用范围是怎么界定的？ | 应引《鹰潭市中心城区城市更新专项规划》相应章节 | 基础检索 | 简单 | 否 |
| E-002 | 我们项目在东湖区，能不能适用中央财政城市更新的补助？ | — | 跨领域 + 需判断适用性 | 复杂 | **是**（需主管部门认定） |
| E-003 | 《鹰潭市城市棚户区改造攻坚行动实施方案》第五条讲了什么？ | 该文件无「第五条」结构（分段式） | 边界（结构假设错误） | 中等 | 否（应说明结构） |
| E-004 | 引用《城乡规划法》第四十条，这个条号对不对？ | 该条存在，但需核对该法版本 | 对抗（条号真实性） | 中等 | 否 |
| E-005 | 国办发〔2023〕25号还有效吗？ | 「未知」或按台账 | 边界（无台账） | 简单 | 否 |
| E-006 | 江西省有没有城市更新的省级文件？ | 库里没有 → 明确说没有 + 给省级缺失说明 | 边界（该说没有） | 中等 | 否 |

## 7.2 指标定义与阈值

| 指标 | 定义 | 目标 | 上线门槛 | 数据来源 |
|---|---|---|---|---|
| 引用可追溯率 | 引用能指到真实存在条款的样本占比 | ≥ 99% | ≥ 95% | 评测集 |
| 真编造率 | 编出不存在的法条/文号/数字的占比 | ≤ 0.5% | ≤ 2% | 评测集 |
| 对抗题通过率 | 对抗类样本正确处理占比 | ≥ 95% | ≥ 85% | 评测集 |
| 合理拒答率 | 应拒答样本中正确拒答的占比 | ≥ 90% | ≥ 80% | 评测集 |
| 误拒率 | 不应拒答却拒的占比 | ≤ 5% | ≤ 8% | 评测集 |
| 结论强度准确率 | 三档结论（可作答/部分/拒答）与人工判定一致的占比 | ≥ 85% | ≥ 75% | 人工抽检 |
| 目录主题召回率 | 清单收录 ÷ 人工穷举真值 | ≥ 95% | ≥ 85% | 人工穷举 1 个方向 |
| 状态诚实率 | 未覆盖/未成功时给出显式说明、未伪装成「没有」的占比 | **100%** | **100%** | 全量检查 |
| 格式合规率 | 输出符合结构化 Schema 的占比 | ≥ 99.5% | ≥ 99% | 日志 |
| 首字延迟 P95 | 首 token 返回 | ≤ 2.0s | ≤ 2.5s | 实测最大 0.79s，达线 |
| 完整响应 P95 | 全量返回 | ≤ 8.0s | ≤ 10.0s | **实测最大 9.5s，超目标线** |
| 单次 API 成本 | 一次问答的 token 折算 | ≤ ¥0.008 | — | 实测 ¥0.00368 |

**「状态诚实率」定 100% 门槛的理由**：这一条没有「差不多」的余地。抓到 3 份报 3 份、没抓到报「没抓到」，都是诚实；抓到 3 份却让人以为这就是全部，就是不诚实。前一种错能修，后一种错会让人基于错误前提工作。

## 7.3 评分标准

单题三档，不算总分，只统计各档占比：

| 档 | 判定 | 例子 |
|---|---|---|
| 通过 | 结论方向正确，且每条依据可核验 | 答对且引对 |
| 部分通过 | 结论正确但有依据不通过，或结论降级过度 | 答对但引了废止版 |
| 不通过 | 结论错误、编造依据、该拒未拒 | 编了一个条号 |
| 应拒已拒 | 该拒答的题正确拒答 | 计入分子，**不算失败** |

## 7.4 评测流程

1. 改动前先跑一遍基线，存档
2. 改动后跑全量，逐题 diff
3. 只看两类变化：**由过转变不过**（回归）与**约束内变过**（提升）
4. 任一项上线门槛指标跌破，阻断发布
5. 每月从 badcase 补题，补题后重跑历史基线，确认不是靠改题刷分

## 7.5 不得沿用的旧数字

以下数字产生于「8 部法规、419 条」的语料，**不得直接用于专题库验收**：

| 旧数字 | 出处 | 为什么不能沿用 |
|---|---|---|
| 引用可追溯 100% | 8 部语料 | 库换大了，条款分布变了 |
| 真编造 0 | 8 部语料 | 同上；且 8 部的名称空间小，模型容易命中 |
| 对抗 40/40 | 66 题自造 | 出题人=判分人=开发者 |
| 闸门 1 阈值 0.40 | 8 部语料标定 | 分数分布随语料规模变化，必须重标 |
| 五类问答 5/5 | MVP 演示 | 5 题不构成统计意义 |

**换库不换数字，等于拿旧考卷的成绩证明新学生的水平。** 这条不是文档问题，是流程问题：每次换库，第一件事是把旧指标作废，然后重跑；不能先跑新库、再回头解释为什么数字变了。

# 8. 数据与埋点

## 8.1 埋点事件

| 事件 | 什么时候打 | 关键字段 | 用来回答 |
|---|---|---|---|
| `catalog_query` | 查清单 | 地域、主题、结果数、各级覆盖状态、耗时 | 哪些方向查得多、哪些级总缺 |
| `catalog_item_open` | 点开一条 | 条目 ID、来源源 | 哪些文件真被用 |
| `assemble_request` | 申请装配 | 勾选数、主题 | 装配需求的真实分布 |
| `assemble_result` | 装配结束 | 成功/待人工/失败、按格式分类、耗时 | 流水线在真实数据上通不通 |
| `ledger_confirm` | 确认效力 | 文件 ID、状态、确认人、耗时 | 人工成本的唯一来源 |
| `ask` | 一次问答 | 问题长度、召回数、结论档位、秒数、token 数 | 效果与成本的日常监控 |
| `gate_fail` | 校验不通过 | 哪一项（C1–C5） | 哪类错误最常见 |
| `feedback_bad` | 用户点「不对」 | 问题、结论、当时的判定 | badcase 回流 |

**`ledger_confirm` 是最重要的一条埋点**。它决定了「装配一个库要花多少人力」这个数字是真测的还是估的，而这一项是本产品真正的成本约束（§9.1）。

## 8.2 数据飞轮

```
线上「不对」反馈 → badcase 池 → 每月补 ≥10 题进评测集
                              → 归因：是检索错了、生成错了、还是表格错了
                              → 表格错了 → 修条数表/时效台账（人工）
                              → 检索错了 → 调检索参数（须重跑全量）
                              → 生成错了 → 改提示词（须重跑全量）
```

飞轮的转速受限于**人工确认**，不受限于机器。这也是为什么「知识库内容负责人」必须是真实存在的角色。

## 8.3 线上监控指标

| 指标 | 告警线 | 说明 |
|---|---|---|
| 每日问答成功率 | < 95% | 模型或检索异常 |
| 完整响应 P95 | > 10s | 体验穿透 |
| 日 API 成本 | > 预算 120% | 异常调用或提示词膨胀 |
| 目录快照年龄 | > 7 天 | 增量抓取断了 |
| 各源连续失败次数 | ≥ 2 | 源站改版 |
| 待人工队列长度 | > 20 份 | 装配流水线卡住 |
| 台账覆盖率 | < 90% | 新入库文件没人确认效力 |

# 9. 成本与性能

## 9.1 单位经济模型

实测环境：`dashscope/qwen-plus`，8 部法规 419 条语料，top 8 召回，2026-10-19。原始数据在 `eval/results/cost_probe.json`。

### 单次问答的 token 构成

| 组成 | 字数 | token | 占输入 |
|---|---|---|---|
| 系统提示 | 4,317 字 | **2,863** | **72%** |
| 输出规范（附在 user 里） | 306 字 | 224 | 6% |
| 检索到的条文（8 条） | 830–2,125 字 | 约 550–1,410（估算） | 14%–36% |
| 问题本身 | ~20 字 | 21 | 0.5% |
| **合计（平均）** | — | **入 3,963 / 出 255** | — |

分项实测（8 次调用，四个能力层各 2 题）：

| 层 | 入 token | 出 token | 首字 | 全程 | 单次成本 |
|---|---|---|---|---|---|
| L1 基础 | 4,020 / 3,687 | 137 / 140 | 558 / 398 ms | 3,647 / 3,588 ms | ¥0.00349 / ¥0.00323 |
| L2 推理 | 3,943 / 4,455 | 205 / 401 | 546 / 711 ms | 5,124 / 9,456 ms | ¥0.00356 / ¥0.00437 |
| L3 边界 | 3,553 / 4,164 | 224 / 260 | 788 / 574 ms | 5,469 / 6,328 ms | ¥0.00329 / ¥0.00385 |
| L4 对抗 | 3,908 / 3,973 | 289 / 385 | 471 / 465 ms | 6,760 / 9,110 ms | ¥0.00370 / ¥0.00395 |

价目按输入 ¥0.0008/千 token、输出 ¥0.002/千 token 计（**用前核对当日价目**）。
系统提示与输出规范的 token 数为实测（单发一次请求读 `usage`）；上下文为按 0.66 token/字换算的估算值，四项相加与实测总输入相差约 3%，差额来自模板固定文字。

### 单次成本与月成本

| 规模 | 调用量 | API 月成本 |
|---|---|---|
| 单用户（20 次/天 × 22 天） | 440 次 | **¥1.62** |
| 10 人团队 | 4,400 次 | **¥16.20** |
| 100 人 | 44,000 次 | **¥162** |

### 这个产品的成本约束在人力，不在 token

对照制造一个直观的刻度：同类产品（政务工单分拨）日均 7,200 件，月 API 成本 ¥10,470。本产品 10 人团队的月 API 成本 ¥16.2，相差约 **650 倍**。这个量级差决定了成本优化在这里不重要。

真正贵的是这一笔：

| 项 | 数量 | 单价 | 金额 |
|---|---|---|---|
| 装配一个专题库：机器部分 | ~10 分钟 | — | ≈ ¥0 |
| 装配一个专题库：人工确认效力 | 80 份 × 1 分钟 | ¥80/小时 | **¥107** |
| 库的生命周期 | 同城同主题约 5 个项目/年 | — | — |
| 摊到单个项目 | 107 ÷ 5 | — | **≈ ¥21** |
| 对照：人工梳理同类清单 | 4 小时 | ¥80/小时 | **¥320** |

**估算的投入产出比约 1:15（¥320 对 ¥21）**。这个数字标注为估算，因为「人工梳理 4 小时」和「确认一份文件 1 分钟」两个输入都没有实测过——它们要靠 §8.1 的 `ledger_confirm` 埋点量出来。

结论：**优化成本的方向是压人工分钟数，不是压 token。** 具体做法是：装配时把「效力确认」做成批量视图（一次看 20 份，键盘连点），把待确认量从 80 次点击压到 4 屏。

## 9.2 成本优化策略（按实际收益排）

| 优先级 | 策略 | 预估收益 | 是否值得做 |
|---|---|---|---|
| 1 | 效力确认批量化（一次看 20 份） | 人工从 80 分钟 → 30 分钟 | **值得**，这是唯一的真实成本项 |
| 2 | 系统提示压缩 30%（去重复表述） | 输入降 21%，单次 ¥0.00368 → ¥0.0029 | 收益小，但顺手能做 |
| 3 | topk 从 8 降到 5 | 上下文降约 37%，延迟降约 0.5s | 需先验证召回不掉 |
| 4 | 高频问题缓存（同一问题 7 天内复用） | 视使用模式，0–20% | 值得，实现成本低 |
| 5 | 全稿自查走纯规则模式（不调模型） | 该功能成本降为 0 | **值得**，同时解决 §10.1 的合规问题 |

## 9.3 延迟

| 指标 | 实测 | 目标 | 结论 |
|---|---|---|---|
| 首字延迟 | 中位 558 ms，最大 788 ms | ≤ 2.0s | **达标** |
| 完整响应 | 中位 6,328 ms，最大 9,456 ms | ≤ 8.0s | **8 次中 1 次超过 8s** |
| 检索耗时 | 未单独测 | — | 待测 |

延迟的构成（推断，未逐段计时）：模型生成占绝大部分。输出 token 与耗时正相关——出 401 token 的那次用了 9,456 ms，出 137 token 的用了 3,647 ms。

**结论：延迟是本产品真正的体验瓶颈，不是成本。** 三个可行手段：

1. 流式输出已具备（首字 0.5s 就出字），体感上已经解决大半
2. 限制 `max_tokens`（当前 1800，实测输出最多 401，可降到 800）
3. 超过 8s 时前端显示进度提示，而不是空白等待

# 10. 风险与合规

## 10.1 数据合规

| 项 | 要求 | 措施 |
|---|---|---|
| 抓取对象 | 政府网站公开发布的政策文件 | 只抓公开栏目与检索接口，遵守站点限速（0.3–0.8 s/请求），带正常 Referer |
| 抓取频率 | 不对源站造成压力 | 单主机串行 + 间隔；不做并发爆破 |
| **用户稿件外泄** | 用户贴进系统的稿件可能含未公开内容 | **默认只发检索到的条文与问题，不发全文**；全稿自查提供「纯规则模式」，不调模型（FR-04 的默认模式） |
| 数据留存 | AI 调用可审计 | 记录调用时间、能力、输入摘要（不存全文）、输出、判定结果 |
| 模型服务商 | 政策文本经第三方 API | 首次使用前明示「内容将发送至模型服务商」；提供纯规则模式作为替代 |
| 来源标注 | 每条依据可回溯到源站 | 目录条目必带 URL；失效链接保留原 URL 并标 `stale` |

**「用户稿件外泄」是这一节唯一真正的风险。** 政策文件是公开的，抓与不抓只涉及礼貌；但规划师贴进来的是**还没送审的稿子**，可能是敏感项目。所以全稿自查必须默认走纯规则模式——五项校验本来就不需要模型，这一点在架构上是成立的。

## 10.2 内容安全

| 风险 | 措施 |
|---|---|
| 输出被当法律意见使用 | 提示词硬约束 + 界面固定显示「本工具不给法律意见，效力认定以法制部门口径为准」 |
| 提示词注入（稿件里藏指令） | 用户输入用分隔符隔离，不参与指令解析；规则层不读用户输入里的任何指令 |
| 涉及敏感项目的推断 | 不推断项目能否获批、能否拿到资金，只回答条文内容 |
| 政策文本被曲解 | 依据必须给原文，不只给概括 |

## 10.3 风险清单

| 编号 | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | **评测集自造，验证无效** | 高 | 引入 2 名规划师重标；在完成前，任何效果指标只能标「自测」 |
| R2 | **省级源抓不到，清单长期缺一级** | 高 | 人工清单 `--import` 兜底；界面强制显示「省级缺失」；不承诺覆盖 |
| R3 | 目录收录率未校验（276 命中只收 3 份） | 中 | 抽 20 条人工核对差额构成 |
| R4 | 装配解析在真实省市文件上成功率未知 | 高 | 第一轮只记录不设目标；先跑 20 份真实文件再定阈值 |
| R5 | `.doc` / `.pdf` 零依赖不可解析 | 中 | 归 `pending_convert`，接外部转换；报告分类统计 |
| R6 | 全量全文库会让判据失效 | 中 | 架构上禁止；全文按专题装配 50–80 份 |
| R7 | 目录条目时效字段大多为空 | 中 | 统一标「未核」；C3 只读台账 |
| R8 | 源站改版导致抓取中断 | 中 | 监控连续失败次数；保留缓存并标 `stale` |
| R9 | 完整响应超 8s | 低 | 流式输出 + 进度提示 |
| R10 | 单人开发，无备份 | 中 | 代码与数据在本地单点；需纳入版本管理 |

## 10.4 预期管理

界面上必须一直存在的三句话：

1. **「本工具不给法律意见。」** 效力认定以法制部门口径为准。
2. **「清单可能不全。」** 覆盖度一栏写明哪一级缺、为什么缺。
3. **「依据请自行复核。」** 每条依据都给原文与链接，点击可核。

这三句属于产品的一部分，写在功能里，不能只写在文档里。
