# 1. 背景与痛点

这一节不谈我们做了什么，先谈这件事现在是怎么被解决的、为什么那个解法不行。

## 1.1 现在这个活儿是怎么干的

一个规划师要给方案里某句话找依据，手上的动作顺序基本固定，六步：

1. **翻自己电脑**。以前做过的项目文件夹，凭印象找。找到了算运气，但这台电脑只有他一个人能看。
2. **翻院内共享盘**。按项目名建的文件夹，没有检索，只能一层层点。他知道大概有，但不知道叫什么名字。
3. **搜百度、必应**。输入「XX市 城市更新 实施办法」。返回十页，前三条常常是资讯、政策解读、问答，第五条才是原文；原文常常是转载页，不是发布机关的页面。
4. **进政府网站翻栏目**。市政府 → 政务公开 → 政策文件 → 按部门筛。栏目四到五层，站内检索经常只搜标题不搜正文，改版一次路径全变。
5. **问人**。微信里问做过这个城市的同事。
6. **写进稿子**。多数情况写「根据相关政策规定」，或者凭印象写一个文件名。

**第六步就是把风险留在了稿子里。** 前三步的产出不落账，第四步的产出是一个网页（下次还得重走一遍），第五步的产出在人的脑子里。

一句话概括现状：**这是一条每次都从头开始、而且终点不明确的流水线。**

## 1.2 四种失败，代价完全不同

用户提的那三件事，成本结构差别很大，混在一起说就看不出该先解决哪个。拆开。

### 第一种：搜了很久，最后找到了

耗时。看得见，可计量，也是四种里最轻的——至少有个结果。

代价：一条依据 25—40 分钟（分档见 §2.4）。一份专题要 20—40 条，累计半天到一天。

### 第二种：搜了很久，最后没找到

这是最贵的一种，但它贵的地方不在花掉的那两个小时。

**贵在不知道该在哪停。**

你搜了两小时没搜到，你无法判断是「确实没有」，还是「我关键词不对」「栏目没翻到」「文件挂在区一级网站上」。这两种情况在行为上完全一样，在结论上完全相反：前者可以写「经检索未见相关规定」，后者是失职。

所以人不会停，会继续搜。**没有终止条件的搜索，时长由人的心理承受力决定，不由任务本身决定。**

搜完之后的东西也不好使。稿子里写一句「经检索未见相关规定」，这句话不可复核——换个人来，还得再搜一遍才能确认；领导问「你真查过了？」，你答不出过程。

### 第三种：找到了，但不能用

用户说的是「发现可能还没发布或者已经结束公示了」。这一类坑最多，分四种：

| 情形    | 长什么样                        | 后果                 |
| ----- | --------------------------- | ------------------ |
| 征求意见稿 | 标题跟正式文件几乎一样，页面上只有「征求意见」四个小字 | 引了不算依据，被专家一句话打回    |
| 已废止   | 文件本身还是原文，页面不标状态             | 交稿后被一句「这条废止了你知道吗」打回 |
| 被修订   | 新文件末尾一句「原XX同时废止」，旧文件里不提自己   | 你手里的是旧的，旧文件不会告诉你   |
| 尚未生效  | 发布日在前，施行日在后                 | 报审时点早于施行日，引了白引     |
| 有效期届满 | 文末一句「有效期至某年某月某日」，没人往下看 | 到期自动失效，没有任何文件宣布它废了 |

**这四种情形的共同点：文件本身不会告诉你。**

废止信息写在另一份文件里，修订信息写在新文件末尾，效力状态要靠跨文件比对才能得出。所以「时效」这个字段不能从单份文件里读出来。

【决策】这也是为什么产品里必须有「时效未知」这一档，而不是「现行有效／已失效」两档。66,851 条标的是「未见废止记录」——意思是全库正文都读过、没有一份说它失效。这跟「确认有效」是两件事，界面上必须分开写，否则就是拿不确定冒充确定。

还有一个更隐蔽的：**搜索结果里最危险的不是「没有」，是「长得像有」。** 一堆标题近似的解读文章、转载、征求意见稿堆在结果页，会让人误以为文件存在、且能用。

### 第四种：这个市就没有

规划编制里有个常态：要做的事本地没有先例。中小城市的城市更新、控规调整、历史建筑活化，本地一份文件都没有。

现在的办法是凭经验想起某个城市做过类似的，或者问同行。这个动作完全依赖个人阅历。**一个工作 12 年的人和一个工作 3 年的人，在这件事上差一个量级，而这个差距没有任何办法被复制。**

用户说的「没有这个市的文件但是有别的市的可以借鉴」，说的就是这一条。

### 还有第五种，真实存在，但本项目不解决：涉密文件没人知道在哪

涉密文件不能上外网、不能进公有云，只能存在个人电脑或项目文件夹里。这类文件复用率接近 0——不是没价值，是没人知道它存在。做过那个项目的人调走了，文件就没了。

**这一条记在这里是为了划边界，不是为了排进需求。** 它的前提是有院内服务器、有多人协作、有保密责任归属，现在的形态（单人、公网）根本碰不到。假装要做，比明确说不做更不诚实。

## 1.3 二十年都这样，为什么

三个机制，缺一个都不会是今天这样。

**机制一：三个事实分散在 1,493 个站点。**

「有没有这份文件」「它现在有效吗」「它管不管我这个事」，这三个问题的答案分别在三个不同的地方：不同站点、不同栏目、不同文件。没有任何一个入口能同时回答。搜索引擎解决第一个，解决不了后两个。

**机制二：判断的结论不留痕。**

每次有人花两小时判断「这个市没有相关规定」，这个结论跟着项目结项一起消失。下一个人来了从零开始。**同一件事被不同的人重复做了 N 遍，N 等于做过这件事的人数。**

**机制三：政策是状态量，不是静态物。**

一份文件的状态会变：起草 → 征求意见 → 发布 → 修订 → 废止。任何一次「存下来」都只是某一个时点的快照。所以这件事不是「把文件存起来」，是「维护一本带状态和出处的账」——这个区别决定了后面所有设计，尤其是 §4.6 的时效判定。

底下还有一个经济学事实，是这件事值得做的理由：**政策依据的复用率极高，留存率极低。** 一个城市的城市更新政策就那么十几份，每个项目都在引同一批。但这些引用关系从来不落账，所以每次都得重来。

## 1.4 现有的解法，各自卡在哪

用户让我「分析现在这个问题解决的方式」。逐个过一遍，包括我们自己的位置。

| 解法               | 能给什么            | 卡在哪                                            |
| ---------------- | --------------- | ---------------------------------------------- |
| 百度／必应            | 覆盖最广，冷门市的文件也能搜到 | 不认行政层级（把区级文件当市级）、不标时效、不认文号、原文常是转载页             |
| 商业法规库（北大法宝、威科先行） | 法规体系完整，有失效标注    | 地方规范性文件覆盖弱，分类口径不是规划口径；按账号年费，个人用不起 |
| 政府网站站内检索         | 权威，是一手源         | 站内检索质量普遍差，栏目层级深，改版即失效；1,400 多个站点各一套，没有统一口径     |
| 本地文件夹／共享盘          | 自己放的东西自己找得到        | 只有目录树，没有检索；放进去就沉底；不标时效；换台电脑就没了              |
| 问人／微信群           | 最快，对人而言也最准      | 不可扩展，不留痕，人走了能力归零                               |
| 通用 AI 对话工具       | 会总结，会说人话        | 会编法名和条号；给不出原文出处；编错了从表面上看不出来                     |

**六个解法，五个在解决「找到」，没有一个在解决「敢引」。**

这就是这个产品的位置。速度上打不过搜索引擎，法规覆盖上打不过商业库，唯一能占的是最后一公里：**给出结论的同时，说清依据是什么、依据现在是什么状态、哪一段没查到。**

【决策】不跟搜索引擎比覆盖，不跟商业库比法规全。定位放在「文件已经有了，判断它能不能引、引哪一条」。这个定位也决定了对错标准：一条引错比十条没找到更严重——因为没找到会被标出来，引错了不会。

## 1.5 我为什么做这个

这一节不谈商业，谈这个项目对我意味着什么。后面的取舍全部从这里来。

两件事。

**一是自用。** 我自己就要查政策——写方案、做研究、看别人的稿子，每次都要回答「这句话有没有依据」。这件事我做过很多遍，每次从零开始。有个东西能把它变成一次有终点的查询，我自己先用。

**二是作品。** 我在往 AI 产品经理转，需要一个拿得出手的东西。判断一个 AI 产品值不值得看，我自己的标准是三条：有没有真实的失败场景撑着、敢不敢说「这条我核不了」、有没有可复现的数字。这个项目三条都占——核验层会主动标未核，时效台账能说出 333 份文件已经过期，时间和成本都是跑出来的，不是估的。

所以优先级很清楚：**先做成自己能天天用的东西，再谈给别人用。** 这不是谦虚，是顺序问题——自己都不用的工具，讲给别人听也讲不圆。

代价同样清楚：不做多租户、不做账号体系、不做内网部署。这三件都是「给别人用」才需要的，现在做等于给一个不存在的用户写需求。
## 1.6 为什么是现在

三个时间点撞到一起了：

1. **我手上有个老城更新的活儿**，能拿它先跑一遍真流程。这是唯一能拿到真实使用数据的机会——不是别人的数据，是我自己的。
2. **数据刚好够用**。条文索引 10-25 从 2,202 份涨到 4,144 份，「引到条」这件事第一次成立。再早两周，工具只能给标题。
3. **上海那批正文有时效压力**。源端 3.6% 已标失效，放着不管，过两个月更容易引错。

反过来不做的代价：我还在用 v3 那个四屏界面，每周问两三次，问完还得自己回原文核。**能用，但省不了最后那一步。**

## 1.7 手上的家底

这一段是能力上限，不是成绩单。用户看到的应该是覆盖率，不是总量。

| 项                   | 量                       |
| ------------------- | ----------------------- |
| 政策目录（只有标题、文号、机关、日期） | 67,541 条，覆盖 1,493 个地域   |
| 有正文、能引到条的           | 30,687 份                |
| 切成可检索的块             | 270,694 块               |

覆盖极不平均，这个必须在界面上说清楚，不然用户会以为哪都能查：

- 上海 82.7%（8,467 / 10,235）
- 南京 93.8%（1,483 / 1,581）
- 江苏 79.8%（1,350 / 1,691）
- 福建 81%（2,838 条目录，正文在补，见 §10）
- 广州 1.3%（11 / 849）——**明确不做**。接口要单独适配，6,080 条重入两次都崩，投入产出比不如把福建、昭通这些省级／市级库补完
- 其余 1,480 个地域，约等于 0，按需联网

三个结构性缺口：

- **文号缺 75.1%**（50,745 条）。没文号就没法在报告里精确指名，只能写标题加日期，被专家追问时不好答。

【决策】为什么不先把法律正文啃下来：一部法只服务一个方向，把地方正文补上来服务所有方向。人大网那道 WAF 要执行 JS 换会话，破了还会再变，不做。

## 1.8 这套东西的欠账

排期要算它，所以放在背景里。`catalog.db` 是 2024 年那版采集脚本演进来的，几笔账还在还：

- `items` 主键叫 `key` 不叫 `id`。写 `WHERE id=?` 直接报 `no such column`，我踩过三次。
- 去重键是「有文号用文号、没文号用折叠标题」，折叠规则是硬编码正则。改它等于重刷全库，所以一直没敢动。
- 正文落盘路径并存过两条：`data/fulltext/<key>.txt` 和 `data/fulltext/<key前2位>/<key>.txt`。索引只读后者。前一条是我自己写错的，6 份文件已迁回，但以后加采集器必须调 `local_full.key_of / ft_path`，不能自己拼。
- 广州接口的元数据字段全带前缀，`_gz_zcwjk_gzgfxwj_file_status` 这种。我照文档写 `file_status`，`.get()` 不报错，跑完发现失效标记 0 份、文号全空。⚠️ 接 JSON 接口必须先打字段快照再写映射。

# 2. 目标与衡量指标

## 2.1 一句话

**把「查一条政策依据」从一次开放式搜索，变成一次有终点的查询。**

「有终点」是这句话的重心。1.2 里最贵的成本不是时间，是不知道该在哪停。

## 2.2 什么算终点：四种结束方式，三种算交付

一次查询只能有四种结束：

| 结束方式    | 输出                                 | 算不算交付   |
| ------- | ---------------------------------- | ------- |
| 有       | 条文原文 + 条号 + 时效状态 + 出处链接            | 算       |
| 半有      | 只有目录（标题、文号、机关、日期），明确标「仅目录，未取正文」    | 算，但要标清  |
| 没有      | 明确说「本次没找到」，附试过的关键词和区／市／省／国家四层各自的状态 | 算       |
| 转圈、假装没有 | 空页面、超时无提示、把「没抓取」渲染成「0 条结果」         | 不算，这是失败 |

**第四种是全项目唯一一个 100% 门槛：1,000 次查询里，出现 0 次。**

## 2.3 三个初衷，三个能力目标

用户提的三件事，各对应一个能力，指标不同。

### （一）存下来，省时间

- 单条依据耗时：25—40 分钟 → ≤ 3 分钟（含读结果、确认时效）
- 一份专题依据梳理：4—8 小时 → ≤ 1.5 小时
- 同一条依据第二次被查时，直接出库，不再联网

### （二）本地没有时，给替代

- 空白城市的查询不返回空页面：需要替代时，至少给 3 个可比城市的同类文件
- 替代建议被采纳率：给出的参照里用户实际勾选的比例 ≥ 30%
- **红线**：替代文件必须标「仅可参照，不可直接引用」。参照和引用混在一起，就是拿别人的地方法规当自己的依据，这个错比找不到严重得多

### （三）公网能访问，挂了能看出来

- 一台机器起服务，公网 HTTPS 可达，`/v1/health` 每次探活返回真实的库规模

## 3.1 时刻一：写方案时卡在一句话上

手上是老门西那片的一个更新方案，周五要交。里面写了「建筑高度可按程序适当突破」，写下去容易，但我知道这句话会被问「依据呢」。

以前：先搜半小时，找到《南京市控制性详细规划执行与调整规定》，翻到具体条款，再花二十分钟确认它现在还有效。半小时到一小时，其中一半时间花在确认时效上。

现在：输入「老门西历史文化街区更新，建筑高度和密度能不能突破现行控规」，等 25 秒。

1. 拆出 8—10 个取证方向，其中一半标「必查」
2. 回来 70—90 条候选，每条标着「有正文」「仅目录」「已届满」
3. 默认勾选只勾有效的；已失效的留在列表里带红标，要引得自己勾
4. 17 秒出五段报告，判断段第一句给立场，依据段引到条
5. 判断段和依据段复制进 Word，路径段留着应付提问

**省下的不是那半小时，是「这条废止了没有」这个必须自己确认的动作。** 台账替我核了。

## 3.2 时刻二：要问一个本地根本没有的事

做昭通、攀枝花这类中小城市的题目时，本地一份文件都没有。以前的办法是凭印象想起某个城市做过类似的，或者问同行。这个动作完全靠阅历，而且没法验证想起来的那份对不对。

现在输入之后，系统明说：本地库没有这个市的文件，附上区／市／省／国家四层各自查到了什么、试过哪些关键词；再给三个同级别、已经做过同类事情的城市，每份标「仅可参照，不可直接引用」。

**红线不变：外市的地方法规参考可以，直接引就是拿别人的规矩当自己的依据。** 这个错比找不到严重。

# 4. 功能方案

## 4.0 边界

一句话：**输入一个问题，输出一份每条依据都能回查到条款、并标明时效状态的判断。** 除此之外都不做。

## 4.1 第一步：把问题拆成取证方向

输入一句话，输出 3—10 个方向，每个方向带「为什么必须查」和「这一层通常是空的还是满的」。

规则（跟 v5 一致，不改）：

- 地域按 `regions.chain` 往上展开（区 → 市 → 省 → 国家）
- 每个数据源独立状态：`ok / empty / blocked / unavailable / error / skipped`
- 多源命中合并，每个推断出来的字段都带依据（文号 / 台账 / 来源库 / 站点 / 标题 / 无法判定）
- 排序：完整串命中优先，然后日期倒序
- 缺的那一层必须显式输出并写原因，不许吞掉

验收：AC-01 鹰潭 / 城市更新，国家 ≥ 20 条、市 ≥ 3 条、省显式 missing；AC-02 任一源失败时界面不出现「该级没有文件」这类断言；AC-03 离线自检 30/30；AC-04 覆盖率数字跟 `data/catalog/local_sites.json` 对得上（1,545/2,491）；AC-26 新增城市不改检索代码，`region LIKE '%城市名%'` 就命中（上海已验证）。

**异常流程**：所有源都空 → 输出「本次没找到任何文件」，附试过的关键词和三层状态，不许说「没有相关政策」。源站结构变了 → 该源标 `error` 并保留上次缓存，标 `stale`。

## 4.2 第二步：取证

### 检索三档

用户自己选从哪查：

- `kb` 只查本地库。南京实测 1.1 秒 / 89 条。
- `both` 库优先，某个方向正文不足 3 份才出去补。默认这档。
- `web` 只联网。库外城市靠它。

【决策】`both` 不做「每个方向都联网」。
  
权衡：8 个方向各抓一轮要一分多钟，而大多数问题在库里已经够用。全方向联网让平均耗时从 1 秒变一分半，换来的增量只有最后几个方向。**先按现在的做法上，如果数据显示「库内不足」的方向超过一半，再改成全方向。**

### 联网两条通道


1. **城市政策库 JSON 接口**。广州 `gz_gfxwjk` 6,989 份，带 `file_status`（有效 / 失效 / 失效（提前废止））。上海另一种形态：列表 `POST /gwk/policy/page` + 详情 `POST /gwk/policy/detail`，10,501 条，详情 0.17 秒/条，返回带 `evolutionList` 沿革和 `expired`。上海这个通道数据质量比广州好。
2. **现探门户栏目**。复用 `local_catalog.probe_site`，成功率约 62%。

三条硬规矩写在 `websearch.py` 文件头：只收政府域名、抓不到正文不算数、失败要说话。

### 踩过的坑，写下来省得再踩

- **别接公开搜索引擎。** 必应无视 `site:`——搜 `site:www.gz.gov.cn 城市更新`，前两条是国务院文件，一条广州的都没有。搜狗反爬，360 链接加密，百度拒绝裸请求（回 1.4 KB 拒绝页）。接了等于给用户「搜到了但不对」的错觉。
- `quote()` 默认把 `site:` 的冒号编成 `%3A`，必应就不认前缀了。要 `safe=":"`。
- `with ThreadPoolExecutor` 会让超时预算失效——`with` 退出时 `shutdown(wait=True)` 要把没跑完的线程等完。必须显式 `shutdown(wait=False, cancel_futures=True)`。
- **4 个方向并发打同一个站会互相拖死。** 按目标站分组，组内串行、组间并发。
- `gz.gov.cn` 证书配置老旧，默认 SSL 上下文会卡在旧版重协商，裸 urllib 稳定挂死 30 秒。必须 `net.get(insecure=True)`。
- **相关性闸门**：只命中「行动方案」「详细规划」这类纯形态词等于没命中。之前省级方向捞回过《广东省遏制与防治艾滋病行动方案》。
- **时效排序**：广州那批 2015—2019 的失效文件在召回里占多数，不排的话首屏全是作废规定。
- **单页上限不稳定**。`limit=50` 只回 41 条、`limit=100` 只回 64 条，分页会漏。保持 `limit=20`。
- **源端自报总数会变**。广州从 6,989 掉到 6,209（隔几小时）。结束条件必须是翻到空页，`total` 只用来显示进度。
- **合肥查不了。** 全站 HTTP 521 + 加速乐，第二层是混淆 JS，要完整浏览器环境。停在 `BLOCKED_SITES`，0.00 秒返回原因，界面用橙色阻断框写「看不到，不等于没有」。放灰色空状态里会被读成「合肥确实没这方面政策」。

验收：AC-31 三档返回的条目能用 `where` 字段区分来源；AC-32 `kb` 档不发任何网络请求，断网能跑；AC-33 `both` 档在库内充足时不发起联网；AC-34 广州方向命中率 ≥ 90%，每条带源端时效标记；AC-35 安徽省方向返回 0 条时报告里写明「源站只收省政府规章」；AC-36 单方向联网总耗时 ≤ 60 秒，超时要留部分结果。

**异常流程**：接口 429 / 限流 → 等 45 秒重试一次，仍失败就跳过并记录；字段名变了 → 该通道整体标 `error`，报告里降级为「本城市暂不可联网查」；证书错 → 走 `insecure` 并记一条告警日志。

## 4.3 第三步：核验（这块最值钱）

五项检查，全部不调模型，纯加减和字符串比对：

- **C1 条号越界**：引的「第 88 条」超过这份文件实际条数。判据来自 `blocks` 里 `kind='art'` 的块，覆盖 4,144 份。
- **C2 引文查不到**：引的那句话在原文里搜不到。判三档——逐字命中（放行）、只差标点（放行）、能对上 70% 以上（标「引文被改写」，黄）、对不上 70%（拦截，判为编造）。有正文就能查，不需要别的数据。
- **C3 时效违规**：引了失效文件当现行用。判据读台账，不读模型输出。判五种情形：
  已废止（拦）、被新版替代（拦）、有效期届满（拦）、尚未生效（提示，不拦——问的就是新规时不算错）、
  期限内有效（放行，并给出到期日）。
- **C4 名称错配**：简称跟全称对不上。
- **C5 所问法规划界**：引了问题范围外的法规。

**⚠️ 最重要的一条：任一检查执行不了，必须标「未核」并降级结论，不许默认通过。**
不是洁癖。C1 只覆盖 4,144 份，C3 只有 1,393 份是「原文载明有效期且未过」这种正面证据，占 4.5%。这种覆盖率下默认「通过」，产品就变成一个假的核验器——它会给一份看起来很专业、实际什么都没核的报告。**这比直接报错危险得多，因为用户看不出来。**

验收：AC-12 C1—C5 每组都有「该过」和「该拦」两类用例（现 11 组）；AC-13 校验层不发任何网络请求，断网能跑；AC-14 同一输入跑两次结论完全一致；AC-15 判据缺失必须标「未核」并降级。

**异常流程**：文件没正文 → C2、C4 标「未核」，C1 标「无法判定」，结论降为「部分作答」；台账里没有这份文件 → C3 标「未核」，界面写「未查到废止记录」。

## 4.4 第四步：出报告

固定五段，第一段必须给立场。

| 段 | 回答什么 | 硬要求 |
|---|---|---|
| 判断 | 能做 / 不能做 / 有条件能做 | 第一句给立场，不许用「需视情况而定」收尾 |
| 依据 | 硬约束 / 程序义务 / 可争取空间 | 每条引到条号或文号；只有标题的文件不许进 |
| 路径 | 审批层级 + 周期 + 代价 | 三条要素齐全 |
| 缺口 | 哪一层、缺什么、意味着什么 | 每条写「要去找哪份文件、为什么必须找」 |
| 下一步 | 办什么事、找谁、拿哪条去说 | 「加强学习」「高度重视」不算建议 |

【决策】从四段改五段。
原来四段交付出来就是一次依据梳理，把有的东西排一遍，用户还是不知道该干嘛。加「路径」这段，逼着把「走哪级审批、大概多久、代价是什么」写出来。**代价是报告变长（实测 5,367 字），这条还没跟真实用户验证过，见 U-03。**

判断段的要求：把堵点分成「明文禁止」和「程序没走到」两类。这两类处理方式完全不同，前者只能改方案，后者是补手续。南京老门西那一问实测拆得挺准：高度是「明文限制＋有限例外」，考古是「程序没走到」。

两个补丁：

- **只有标题的文件不许进依据段。** 上一版允许写「据《某通知》，该文件已由某机关发布，从名称看针对……」——依据段混进三条这种凑数句，零信息量，还显得专业。现在这类只能进缺口段，写「需调取原文核实」。
- **提示词里必须注入当天日期。** 模型不知道今天几号，读到《南京历史文化名城保护条例》「自 2026 年 7 月 1 日起施行」，就写「届时才施行，需核对旧版过渡期」。当时已经生效快四个月。

验收：AC-44 五段齐全，缺段算失败；AC-45 判断段第一句必须是「能做 / 不能做 / 有条件能做」三选一（正则可判）；AC-46 依据段每条都能回查到 `chars > 300` 的正文文件；AC-47 连续 5 个不同问题跑通，五段结构都成立。

## 4.5 覆盖与缺口怎么说（这块决定用户信不信）

六个显示位，缺一个这产品就开始骗人：

1. 清单顶部：各级命中数 + 各级状态
2. 缺口区：哪些源没通、原因、最后成功时间
3. 每条目录条目：`仅目录` 徽标
4. 每条缺字段条目：`文号缺失` / `日期缺失`
5. 报告页：整体覆盖度（站点 62% / 正文 18.6% / 条文 4,144 份 / 时效 3.9%）
6. **`已抓未索引` 徽标**——上海那 8,903 份就是这种状态：文件在磁盘上，检索里没有

验收：AC-22 任一 `blocked` 源有可见说明；AC-23 全量 1,000 次查询，没有一次把「未抓取」渲染成「0 条结果」；AC-24 六个显示位默认视图全部可见；AC-29 被拦站点用橙色阻断，不用灰。

## 4.6 接口与发布

给低代码平台用的 JSON 接口，不走 SSE。`POST /v1/plan|gather|write`、`POST /v1/jobs` + `GET /v1/jobs/{id}`、`GET /v1/coverage|health`、`GET /v1/openapi.json`（OpenAPI 3.0.3）。

**为什么必须有异步**：`/v1/write` 实测 17—60 秒，超过百炼插件和魔笔数据源的等待上限。同步调用会「服务端跑完、结果丢了、token 也花了」。异步实测提交 0.08 秒，16.8 秒后取到结果。

鉴权走 `PV_TOKEN` + 请求头 `X-PV-Token`，默认为空即不校验，公网必须开。`/v1/health` 免校验。

上线前四件事，一件不能省：公网可访问、HTTPS、开 token 加限流、异步结果落库（现在在内存里，重启即丢，多实例不共享）。

**时效台账（F-06）。** 六种状态，全机器判定，每条都能给出依据原文：

| 状态 | 判据 | 数量（10-26 重建） |

| `pending` 尚未生效 | 原文载明施行日，还没到 | 20 |
| `in_force` 期限内有效 | 原文载明有效期，未过 | 1,393 |
| `no_signal` 未见信号 | 全库正文比对无废止记录，原文也未载有效期 | 28,077 |

没有任何文件宣布它废。实测 333 份已经过期，330 份原来标的是 `no_signal`——用户看到的是

## 4.9 Plan B：模型不可用时只出原文

【决策】主线调模型写五段，备选不调模型、直接排原文。

**Plan B 是什么**：环境变量 `QW_RAW_ONLY=1` 开启，或者模型调用抛异常时自动切换。撰写这一步不走 LLM，把选中文件的条文按文件排出来，开头一句「这一份是原文条文清单，不是分析结论」。

**为什么它必须有**：撰写是唯一一步失败就整份报告没了的环节。拆解失败还能手写指令，取证失败还有目录，撰写失败什么都没有。而它同时最容易被限流打中——3,200 token、16 秒，三家模型的 key 同时 429 是真的发生过。

**降级产物长什么样**：五段结构保留。判断段写「跳过撰写，能引的 N 份条文可以直接核，能不能做没判」；路径段写「本段不产出，路径判断依赖跨文件归纳」；依据段逐条抄原文，每份最多 8 条、每条 220 字。核验照走，而且更容易过——它没有概括，只有原文。

**为什么不拿它当主线**：它不给判断，也不给路径。而人要的是「能不能这么做」，条文清单只回答「规定是什么」。

## 4.10 脏活累活

这部分没人愿意写，但不写就会在上线前一天爆。

### 数据迁移

三笔账必须清：

1. **上海正文的 url 跟目录对不上。** 正文走新接口，url 是 `zhengce/list#<businessId>`；目录里是 `zhengce/list#<另一批 hash>`，交集 0。现在靠标题挂接（对上 8,467 条），剩下 1,707 条挂不上。**方案：先在索引层按标题挂，挂多少算多少；剩下的不追。** 追这点要重抓上海目录（69 秒翻 106 页），而它影响的是 17% 的条目标题对不上正文，不影响已有的 83%。
2. **广州明确不做。** 6,080 条撞写锁整批丢过一次，重入时接口字段前缀又踩坑一次。两次都是因为适配它要单独写一套。**决定放弃，库里剩的 849 条目录保留不删**——检索时它会以「仅目录」出现，比假装没有强。
3. **索引要重建。** 上海入索引后地域全错（8,903 份全标「国家」），已修，重建耗时 2 分 13 秒。以后每次入新城市都要核对 `docs` 的 region 分布，这个检查已写进附录。

### 老用户习惯兼容

v3 那个四屏界面我自己还在用。改版会撞三件事：

- **老链接不能失效。** `/` 和 `/index.html` 继续指四屏，`/v1/*` 是新接口，两套并存，不合并。
- **老接口不删。** `/api/plan|gather|write` 的 SSE 流保留。删了我自己收藏的那个带参数链接就打不开了，我不会重新去翻文档，我会直接不用。
- **术语别换。** 界面上「可引」「仅目录」这两个词已经用了两周，改成「可引用」「仅目录收录」这种更准确的说法没意义，反而会让我以为换了东西。

### 第三方接口不稳定，怎么兜

| 情况 | 表现 | 兜底 |
|---|---|---|
| 限流（429） | 响应从 0.6 秒掉到 6.6 秒 | 等 45 秒重试一次，仍失败跳过并记录；缓存 TTL 7 天，只缓存成功结果 |
| 字段改名 | `.get()` 不报错，数据静默为空 | 每次接入打字段快照，跑完对一次字段清单，缺了告警 |
| 证书老旧 | 挂死 30 秒 | `net.get(insecure=True)`，记一条日志 |
| 站点改版 | 探不到栏目 | 该源标 `error`，保留缓存标 `stale`，界面写「上次成功时间」 |
| 整站反爬（合肥） | HTTP 521 | 直接短路，0 秒返回原因，不重试 |

## 4.11 灰度计划

只有我一个人用，所以没有「按人灰度」这回事。改成按**问题类型**分期开放，每一期只验一件事。

**第 0 期（2 天）**：只跑 `kb` 档，不联网。目的是把全链路跑顺、看埋点有没有漏事件。这一期不看效果，只看有没有报错。
**第 1 期（1 周）**：开 `both` 档，只问我自己手上真有的题目（老门西、昭通、攀枝花）。目的是看真实问题上的判断段能不能用、缺口段说不说得清。
**第 2 期（2 周）**：开始问完全不熟的领域（税收、环保、教育）。目的是检验「我不知道答案时，它会不会编」。

**三个回滚开关**（都是环境变量，改完重启生效，不发版）：

| 开关 | 作用 | 什么时候用 |
|---|---|---|
| `QW_DISABLE_WEB=1` | 关联网，只查库 | 接口大面积挂、或者被抓太狠 |
| `QW_RAW_ONLY=1` | 退回原文模式，不调模型 | 报告出现编造或明显跑偏 |
| 撤 `PV_TOKEN` | 服务下线 | 出现引废止文件还标现行这种事故 |

**监控什么**（具体指标，见第 8 节埋点）：

- 取证空结果率 > 30%，说明检索坏了或者数据没更新
- 撰写失败率 > 5%
- 「未核」占比（C1—C4 口径）> 70%，说明核验层形同虚设，报告页的黄色横幅要加重
- 平均耗时 > 60 秒，说明该砍方向数

上线后只看三个数：**空结果率、未核占比、复制率**。前两个判系统坏没坏，第三个判有没有人真的在用——复制率低于 20%，说明报告能看但不能用，问题出在措辞而不在数据。

# 7. 风险与应对

## 7.1 技术风险

- **并发扛不住。** `ThreadingHTTPServer` 单进程。虽然只有一个用户，但一个进程同时跑三个请求（plan+gather+write）就会互相抢 SQLite 读锁。**10-26 已修**：异步任务从内存 dict 改成落 `app.db` 的 `job` 表，重启不再丢，多实例也能共享。剩下没解决的是进程级：真要多实例，前面得加一层反向代理。
- **索引 1.9 GB。** 部署包太大，传到公网机器要十几分钟，增量更新也没有方案。**应对**：数据目录和代码分开，代码 Git 走，数据用压缩包一次性上传再增量补。这是发布阶段最容易卡住的一步。
- **地域归属整批误标。** 上海 8,903 份曾被标成国家，等于地方文件冒充上位法。**应对**：三级判定（url 精确 → 域名投票 → 只有 www.gov.cn 算国家），每次入库后核对 region 分布。
- **「抓到了」不等于「能用」。** 上海那批白放两天就是例子。**应对**：加「已抓未索引」状态，独立显示。

## 7.2 业务风险

- **自己的习惯被打破。** v3 的四屏流程用了两周，改成五段报告加检索范围选择，第一反应会是想切回去。**应对**：老接口和老页面全保留，新版并行，不替换。**这是刻意的技术债，认了。**
- **承诺过度。** 一旦对外说「能查政策」，听的人会理解成「什么都能查」。**应对**：所有对外材料只写具体覆盖（上海、南京、江苏、福建、昭通），不写「全国」。
- **法务口径。** 输出必须带免责声明。这条不是产品选择，是硬约束。

## 7.3 运营风险

- **答疑成本归零，但维护成本不归零。** 没有别人用，就没有答疑。但政府网站改版、接口字段变、模型涨价这三件事会持续发生，每次都要人改代码。**这是我一个人的项目，停下来就会烂。**
- **数据没人维护。** 台账是机器判的，不需要人工确认——这是它跟「人工维护台账」方案最大的区别。
  但机器判有个新风险：333 份 `expired` 全是正则从正文尾部抽的日期，抽错了没人发现。
  **应对**：抽出来的原句存在 `valid_raw` 里，界面上可以直接看那句话对不对；
  抽错的表现是日期离谱（比如 1900 年），加一条合理性检查就够。
- **评测集自造。** 66 道题，出题人、判分人、被考核对象是同一个人。**应对**：补 30 道发现层题，找 2 名规划师复核。这件事在灰度第 2 阶段做，那时候才有人能帮忙看。

## 7.4 已知没验证的

- **U-01** ~~上海 8,903 份未进索引~~ ✅ 10-25 21:52 解决，检索 10/10 可引。

- **U-04** 联网通道只验过广州。其他城市没试。
- **U-05** v1 接口只在本机测过。公网、HTTPS、跨域都可能挂。
- **U-06** 成本没随 3,200 tokens 重算。¥0.00368 那个数别拿去报预算。
- **U-07** 新增四个地区的核验层没测。上海整库抓的，条文块 46,816，但「通知」类文件其实没有分条结构，可能被切成一整块。

# 8. 数据埋点方案

## 8.1 事件

现在只有 `trace.py` 按 run_id 留痕，缺用户行为。下面这些本期要补，先只埋不分析。

| 事件名 | 触发时机 | 参数 | 用来判断什么 |
|---|---|---|---|
| `q_start` | 用户点提交 | `run_id, city, province, scope, q_len` | 有没有人在用、问什么城市的 |
| `plan_done` | 方向拆完 | `run_id, n_tasks, n_required, ms` | 拆解是否稳定 |
| `gather_done` | 每个方向取证完 | `run_id, task_id, kind, n_items, n_body, n_usable, ms, where, err` | **空结果率**、哪层总空 |
| `scope_switch` | 用户切检索范围 | `from, to` | 用户到底想不想联网 |
| `report_done` | 报告生成完 | `run_id, chars, n_sections, ms, tokens, model` | 报告长度、成本 |
| `verify_result` | 核验完 | `run_id, c1, c2, c3, c4, c5, n_unchecked, n_cite` | **未核占比**，这是诚实层的关键数 |
| `cite_click` | 点某条引用 | `run_id, doc_key, art_no` | 哪些依据真被看了 |
| `copy_report` | 复制报告正文 | `run_id, chars, section` | **真实使用信号**，比停留时长有用 |
| `fallback_raw` | 退回原文模式 | `run_id, reason, chars, err` | 降级触发频率、触发原因 |
| `guard_block` | 撞到被拦站点 | `site, reason, ms` | 哪些城市总撞墙 |

## 8.2 上线后只看三个数

1. **取证空结果率** = `gather_done` 里 `n_usable=0` 的比例。超过 30% 说明检索或数据坏了。
2. **未核占比** = C1—C4 的 skip 数 / C1—C4 的总检查数。超过 70% 说明核验层没起作用，报告页的横幅要加重。
   **必须排除 C5**：问题没点名法规时 C5 一定跳过，算进去这个数会永远在 40% 上下，预警线成了摆设。
3. **复制率** = `copy_report` / `report_done`。低于 20% 说明报告写出来没人用，问题在内容不在功能。

## 8.3 实现现状

**十个事件全部落库（10-26 补完）。** 一轮完整事件链长这样：

```
q_start        q_len 30, scope kb
plan_done      n_tasks 10, n_required 5, city 南京市, 4458ms
gather_done×10 每方向一条，带 n_items / n_body / n_usable
gather_sum     n_items 78, n_body 55
report_done    chars 3692, n_sections 5, n_cites 14, 可交付, ratio 1.0
verify_result  n_cite 14, n_check 70, c1 13p/0f/2s / c2 1p/0f/14s / c3 15p / c4 15p / c5 15s
```

四个前端事件（`q_start` / `scope_switch` / `cite_click` / `copy_report`）走独立的
`POST /api/ev`，不进 SSE 流——SSE 一断就丢，而复制、点引用恰恰发生在报告出完之后。

**`verify_result` 的「未核占比」口径改过一次，这是埋点立刻照出来的问题。**
第一版按 C1—C5 全算，跑出来 41.4%，看着像核验层瘫了；实际 29 个未核里 15 个是 C5
（问题没点名任何法规时，C5 必然跳过，属于结构性 skip）。改成 C1—C4 口径后，
同一轮数据是 **26.7%**。不这么改，§8.2 那条「70% 加重横幅」永远触发不了，因为永远在 40% 上下。

**埋点照出了 C2 空转，当晚修完了。** 修之前：C1 核 13/15、C3 核 15/15、C4 核 15/15，
**C2 只核了 1/15**，其余 14 条是「未给引文」直接跳过——模型不摘原文，C2 就无从核起。
C2 问的是「你写的这句话原文里到底有没有」，这是五项里最值钱的一项。

修法分两层，缺一层都不行：

**第一层，改提示词，要求每条依据都带原文引文**，格式固定成
「说要管什么 → 原文：「逐字照抄」→【《文件》第X条】」。代价是报告从 3,700 字涨到 4,775 字，
所以 `max_tokens` 从 3,200 提到 4,200。

**第二层，修解析器的一个 bug。** 改完提示词第一次跑，引文倒是写出来了，但 C2 还是只识别 2/14。
查下来是 `parse_cites` 按「句号/分号」切句再找引号的：引文自己几乎一定含句号
（「…是老城高度管理的依据，应当严格执行。…不得修改。」），切点落在引文中间，
引号开头在前一句、结尾在后一句，两边都凑不成对，`quote` 一律为空。
**模型明明摘了原文，系统判它没摘。** 改成先把全文所有成对引号的位置一次算出来，
再按引注切区间分配，一条引注只认「上一条引注之后、本条之前」最近的那个引号。

修完实测：带引文的引注 **2/14 → 12/13**，C2 通过 10 条、拦截 2 条、未核 1 条。
那 2 条拦截是真问题——模型摘的引文跟原文对不上，它自己没发现。**这才是这个产品该干的事。**

**按天聚合没做。** 现在只能 `sqlite3 data/app.db` 手查。够用——一个用户一周不到 100 条 run，
做看板不如直接看 SQL。

【决策】不再加埋点。十个事件已经覆盖三个核心指标，加事件要改代码要回归，
而看不过来是更大的浪费。
