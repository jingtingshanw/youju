0. 本版改了什么

v1 的前提是「文件已经在我手上，我来核验引用属不属实」。这个前提在真实场景里不成立： 规划师接一个项目的第一件事是弄清这个话题在三级政府各有哪些文件， 而这批文件他手上没有，也不知道该有哪些。

v2 把这件事补进来，同时守住一条底线：补进来的只有「名单」，不是「全量正文」。

维度v1v2
起点用户提问用户给「地域 + 主题」
库一个知识库（8 部法规）全量目录（1.9 万条字段）+ 每专题一个库（50–80 份全文）
链路检索 → 核验 → 交付（三段）发现 → 装配 → 核验 → 交付（四段）
检索的角色找文件 + 找条文只找条文（找文件归目录层）
指标一套（66 题）三层分开：目录层 / 装配层 / 问答层
新增工程—目录抓取（已做）+ 装配流水线（待做）

一句话概括这次改动：把「知识库里有没有」这个不可控的前提，换成一个可控的动作—— 先用 13 分钟把国家级目录穷举，再用 10 分钟把某个专题的文件装配好。

1. 产品定位

1.1 一句话

给规划师一个「有据」：每一条结论都能指到具体条款、具体文件、具体时效状态。

1.2 「据」的三层含义

这个名字不是修辞，它规定了三件必须交付的东西：

层次用户的问题产品给的东西缺了这一层会怎样
有文件这个方向有哪些文件？省里的、国家的带效力级别和链接的清单，含三级覆盖度用户不知道有这份文件，后面的核验再准也没用
有条文这条规定写在哪？法规全称 + 条号 + 原文结论无法写进文书，也没法被人核对
有效力它还有效吗？现行有效 / 已废止 / 已失效 / 未知引了废止文件，比不引更糟

三层缺一层，这个产品就退化成「搜索框」或「校对小工具」。

1.3 用户与三个真实场景

主用户：规划院/所的规划师、政府部门的规划管理人员。他们不是在「查法规」， 是在写一份要交出去的东西（专项规划、可行性研究、项目建议书、政策建议）， 里面每一句涉及法定依据的话都要能被人追问「依据是什么」。

场景 A · 立项前的文件梳理（新增，本版重点） 接了江西鹰潭的城市更新项目。需要知道：鹰潭市本级有哪些文件、江西省有哪些、 国务院和部委有哪些，以及历史文化保护方面的相关规定。产出是一张清单，进项目建议书的 「政策依据」一章。这一步的判据是不能漏。

场景 B · 起草时的引用核对 写完一章，逐条核对：引的条号存在吗？引的法规还有效吗？有没有该引没引的重要文件？ 这一步的判据是不能错。

场景 C · 送审前的自查 把稿子交给评审前，跑一遍全文，产出「引用清单 + 时效状态 + 疑似问题列表」， 随稿一起交。这一步的判据是可解释——每一条问题都要能指到具体位置。

1.4 不做什么

  1. 不给法律意见。 报告事实与效力状态，不给「你应该怎么做」。
  2. 不做全量全文库。 1.9 万份正文进库之后，效力台账维护不了，闸门 2 失效，

    3. 整套东西退化成普通 RAG（见 9.1）。

  3. 不替代正式法律检索。 对外的效力认定以法制部门口径为准。
  4. 不做通用问答。 只回答「这份文件这条规定是什么、还有没有效」这类可核验的问题。
  5. 不承诺覆盖全国所有地市。 每个省市站要单独适配，做不到的部分显式标缺。

2. 两层库

2.1 为什么必须两层

两层真正的差别是维护成本，跟存多存少关系不大：

目录层专题库（全文层）
存什么名称 / 发文机关 / 文号 / 效力级别 / 发布与失效日 / 地域 / 主题 / 链接逐条正文 + 条数表 + 时效台账
目标接近穷举（不能漏）按需精读（不能错）
规模国家级 19,026 条 + 省市一个专题 50–80 份 / 2,000–4,000 条
谁能维护机器全自动机器 + 人工确认效力
更新每天可增量刷立项时装配一次
判据覆盖度五项确定性校验

决定性因素是维护成本。

19,026 份文件的效力状态，只有国家法律法规数据库有权威口径，而它现在 blocked（§9.2）。 没有台账，闸门 2 的 C1（条号越界）和 C3（时效违规）就全部退化成「未核」—— 这两条恰恰是这个产品不可替代的部分。库一大，判据先死。

50–80 份不一样：条数表可以由解析结果自动导出（解析出来就数出来了）， 效力状态只需人工确认 50–80 次，一次点击一份，半小时能做完。 这是「专题库可维护、巨型库不可维护」的量化依据。

2.3 专题库规格

「专题库」的定义：一个主题 × 一条地域链上的全部相关文件全文。

项规格
库的键topic + region_chain，例如 城市更新@鹰潭市→江西省→国家
组成50–80 份文件全文，切成 2,000–4,000 个可检索单元
必须携带条数表、时效台账、名称映射表（三张表）
生命周期随项目建，可长期复用（同城市同主题的第二个项目直接复用）
复用规则项目引用库，不复制库；库升级后所有引用它的项目一起受益
退出条件三张表齐 + 检索召回达标 + 闸门自检通过 + 缺口清单已标注

为什么库的粒度是「主题 × 地域」而不是「项目」：一个规划院一年做五个城市更新项目， 如果按项目建库，就是五个 80% 重复的库。按「主题 × 地域」建，鹰潭只有一个城市更新库， 五个项目共用；换到南昌再做，新增一个南昌库，国家层文件复用同一份。

2.4 两层的接缝（最容易漏的地方）

目录层认「标题」，专题库认「法规全称」，闸门 2 认「全称 + 条号」。三者必须对齐：

目录条目：关于开展2026年度中央财政支持实施城市更新行动的通知   ← 抓来的标题
                    │ 装配时解析出正式全称
                    ▼
专题库条目：《中央财政支持城市更新行动资金管理办法》            ← 正文首部或落款
                    │ 写入 doc_names.json
                    ▼
闸门 2：认全称 → 查条数表 → 查时效台账

风险：目录标题与正文全称经常不一致（尤其是转发件、印发通知、附件形式的文件）。 处理规则写在 §6.2。

3.2 段 0 · 发现

项内容
输入region（可简写「鹰潭」）+ topic 或 keyword
前置该地域在 sites.json 里有配置（没有就新增一条，不改代码）
动作按地域链逐级调度源；每个源独立跑、独立报状态
输出清单（按行政层级分组，每条带效力级别、文号、日期、链接、状态）+ 覆盖度 + 缺口
判据三级各自覆盖到什么程度；「没查到」必须显式写出来
失败单源失败不影响其他源；整级为空时该级标 missing 并给原因
不做不抓正文、不判效力、不猜

这一步为什么不用 RAG：目录层要回答的是「有哪些文件」，这是一个集合查询。 用相似度找文件会漏掉「标题不含主题词但内容相关」的文件，也会混进大量新闻。 结构化查询（地域 × 主题 × 效力级别）在这个任务上更准、更快、可穷举。

4. RAG 在这里的位置

这一节直接回答「还有没有用 RAG」。

4.1 仍然在用，但只用在一处

整条链路上有三件需要「找东西」的事：

要办的事用什么为什么
这个方向有哪些文件结构化查询（目录层）要穷举、要能说出「没有」，相似度做不到
这几条依据在库里的哪里检索（BM25 / 向量）是语义匹配任务，这就是 RAG 的检索环节
模型说引了第 42 条，到底有没有确定性查找（按全称 + 条号取数）要可复现、要能写进承诺，不能用分数

只有第二件事是 RAG。 第一件和第三件都不是——它们不需要「相似」，需要「精确」。

4.2 RAG 的职责缩小了

v1 里检索要干两件事：找到相关文件 + 找到相关条文。v2 把前一件交给了目录层。

v1v2
检索负责找文件 + 找条文只找条文
找文件靠向量相似度地域 × 主题的结构化查询
找文件会不会漏会（标题不含主题词就漏）不会（目录是全的，按字段筛）

这个变化的实际效果：模型中「检索」这一环的工程量占比从大约 100% 降到 30% 左右， 剩下 70% 是目录查询 + 装配 + 规则核验，都是确定性工程。

4.3 检索层规格

项默认可选
召回BM25（纯标准库实现）向量召回（需 embedding）
重排无rerank（仅在阈值判定需要时）
规模2,000–4,000 条 / 库同
实测依据MVP 在 8 部 / 419 单元上 top-8 召回 L1+L2 15/15完整版 66 题 recall@1 65/66
结论专题库规模下 BM25 够用，向量是可选项启用向量必须重标闸门 1 阈值

为什么专题库可以不配向量：目录层已经把文件圈定在 50–80 份， 检索要做的只是「在这 2,000–4,000 条里挑出相关的几条」。这个规模的词汇重叠度足够高， BM25 的弱点（同义表述）影响有限，而且一旦出错，闸门 2 会拦下来。 用零依赖换来的可复现性，在这个规模上比几个百分点的召回更值钱。

4.4 三个反模式（不能用 RAG 的地方）

这三条都是 v1 踩出来的，写在这里防止以后有人重新踩：

  1. 不能用相似度判断「这条规定是否存在」。 查不到就是查不到，要用条号确定性查找。

    2. 否则「库里没有」和「没检索到」会混成一件事。

  2. 不能用相似度判断「文件是否失效」。 效力只有台账和法定期刊说了算。

    3. 模型自报「现行有效」等于自报自验。

  3. 不能用相似度做「漏引检测」。 漏引是集合差集问题（目录 N 份 − 稿子引 M 份），

    4. 不是相似度问题。

4.5 诚实的回答

还有 RAG，但它在这个产品里是配角。

普通的法规问答 RAG 是 检索 → 生成。有据是 检索 → 生成 → 核验 → 降级。 多出来的两段都不需要 RAG，而这两段才是产品价值所在—— 用户要的是一份能被人追问的文件。一段听起来对的话满足不了这个要求。

反过来说：如果去掉 RAG，这个产品仍然能工作（用户自己贴条文进来核验）； 如果去掉核验，它就变成又一个法规问答机器人。

5. 装配流水线规格

本版只有规格，尚未实现。这一节是下一轮的开发依据。

5.1 五个环节

环节动作判据失败处理
① 抓全文按目录 URL 下载；同一文件多源时取正文最完整的一份成功率（首轮只记录，不设目标）转「待人工」
② 解析HTML / docx → 纯文本 + 结构（条、款、项）解析成功率（按格式分别统计）转「待人工」
③ 体检三重判据（§5.3），不过则不入库通过率（首轮只记录，不设目标）留候选池，标原因
④ 出表自动生成条数表；时效台账待人工确认条数表与正文自洽率 100%（这一条必须有）阻断
⑤ 建库切分 + 建索引 + 跑自检闸门自检通过阻断，不给用

为什么前三项不设通过率目标：首轮真实数据还没跑过，任何百分比都是编的。 省市级文件大量以 .doc 附件形式发布，而 .doc 零依赖解不了（§5.2）， 解析成功率可能低到 50% 以下。先量出来，再定阈值—— 把目标写在没量过的地方，只会逼着实现去凑数。

5.2 解析能力矩阵（零依赖约束下的真实边界）

项目的硬约束是零第三方包。这个约束决定了哪些格式能进全文层：

格式能否零依赖解析依据处理
HTML✅ 可以正则 + 去标签首选，政府站正文多为 HTML
.docx✅ 可以zipfile 读 word/document.xml，去标签已实测：8216 字符 / 50 条，与条数表一致
.doc❌ 不行OLE2 二进制（实测文件头 D0CF11E0）需外部转换（Word COM / LibreOffice）或人工另存
.pdf❌ 不行PDF 内容流，标准库无解同上；扫描件还需 OCR
扫描件❌ 不行同上同上

这是一条真实的产品约束，要写进界面：装配报告里必须分别统计 「HTML 成功 / docx 成功 / doc 待转换 / pdf 待转换」，不能笼统报「N 份待人工」。

为什么不为它破例引入依赖：一旦引入 PDF 解析库，MVP 就不能「拷走就跑」， 而这个能力是产品演示与交接的基础。替代方案是「外部转换一步，人工操作」， 成本是一个人一次点击，收益是整条链路保持零依赖。

5.3 体检的三重判据

单纯用「条数对齐」会大量误杀——很多规范性文件根本不分条（用「一、」「（一）」分层次）。 所以体检要分型后再判：

第一步：判型

型判据后续检查
分条型能识别 ≥3 个「第X条」条号连续性 + 首尾完整
分段型能识别 ≥3 个「一、」或「（一）」层级层级编号连续性
无结构型都不满足只做长度与落款检查

第二步：三项检查

检查判据拦什么
完整性正文含落款或成文日期；长度 ≥500 字截断、只抓到附件、抓到导航文字
结构完好分条型：条号从「第一条」连续到最后一条，无跳号、无重复解析漏段、混入两份文件
一致性正文首 200 字与目录摘要重合度 ≥50%抓错文件（链接跳转、栏目错位）

第三步：分型记录

体检结果必须记下「这份文件是什么型、多少条/多少段」，因为闸门 2 的 C1（条号越界） 只对分条型有效。分段型的文件，C1 要降级为「条款编号存在性检查」。

5.4 准入分级

不是所有抓到的文件都该进全文层：

级判定处理
A 必入法律 / 行政法规 / 部门规章 / 地方性法规（文号可判、效力级别明确）进全文层，效力必须人工确认
B 可入省市规范性文件（标题命中主题、有文号或落款）进全文层，效力必须人工确认
C 只留目录新闻、转载、解读、政策问答、会议报道留在目录层，不进全文层

判定顺序：先看 doc_type（由文号推），推不出再看标题核心词，最后看来源栏目。 C 级的判据已经实现在 looks_like_doc() 里。

5.5 状态词（装配层）

与目录层同一套思路——没做成的事必须说出来：

状态含义
assembled已入专题库，三张表齐，效力已确认
parsed已解析入库，但效力未确认（闸门 2 只作参考依据）
pending_convert需要外部转换（doc / pdf）
pending_manual抓取失败或体检不过，待人工处理
catalog_only只在目录层，未进全文层（C 级或用户剔除）
excluded用户主动剔除

装配报告必须给出这六类的条数。 只报「成功 62 份」是误导。

8. 冷启动

新用户打开时库里必须有东西，否则第一印象就是空的。

做法规格
预置专题库4 个：城市更新 / 历史文化保护 / 土地征收 / 规划许可
每个库的构成国家级（30–40 份）+ 3 个典型省市（各 10–15 份）
幂等预置库的效力状态必须是已人工确认的，否则闸门 2 只能半工作
展示首屏直接给「这 4 个库各有哪些文件、覆盖到哪一级」，不让用户先学会提问
成本4 库 × 80 份 = 320 份的人工效力确认，是这个方案最大的冷启动成本

这条成本要提前认：预置库如果不确认效力，它就只能当目录用； 当目录用的话，预置的价值主要是「演示」，不是「可用」。两者要分清。

9. 已知边界与风险

9.1 为什么不做全量全文库（最硬的约束）

19,026 份 × 平均 5 千字 ≈ 9,500 万字 ≈ 30 万个切分单元。能存能检，但：

能力8 部 / 419 单元19,026 份 / 30 万单元
条数表手工核对，精确无来源，只能解析导出，准确性未知
时效台账逐部核对不可能逐部核对
闸门 2 C1/C3可用失效（退化為「未核」）
闸门 1 的「没有」可信（库小，能确认装了什么）不可信（检索不到 ≠ 不存在）
答案冲突人脑可裁需另一套冲突裁决机制

结论：巨型库会让这个产品的核心判据失效，退化成普通 RAG。所以全文层按专题装配。
