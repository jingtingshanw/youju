## 一、结论先说

1. **手册第 6 步的阻塞解开了。** 本机此前**没有任何 rerank 模型**，重排序根本做不了。现在 Dify 里挂上了 `tongyi/gte-rerank-v2`，重排序成为默认开启的环节。
2. **重排的价值不在答案层，在检索层。** 四轮端到端对照里，「真编造 0% / 引用可追溯 100%」在 v3 和 v4 是并列的——**重排没有把答案变得更好**。它真正改变的是检索层多了**一个可用的硬闸门**：纯事实题（L1+L2，n=20）与对抗题（L4，n=4）在重排分数上可以被一条阈值完全分开（min 0.509 vs max 0.447）。余弦做不到这件事，两次独立实测都做不到。
3. **一个反直觉的副产物**：时效题（L3）的重排分数横跨整个区间（0.366–0.954）。这不是缺陷——「这条法规现在还有效吗」的答案**根本不在语料正文里**，它只存在于台账元数据。检索层给低分是**正确行为**，恰好印证了 v2 把时效台账注入提示词的做法：**时效件事不该指望检索。**
4. **本机有一个隐蔽的容器出网分裂**，绕了很久才定位。解决方案是宿主机上一个带鉴权与白名单的转发代理。这个代理现在是这套栈的**单点依赖**，挂了会导致所有百炼调用静默失败（表现为评估表一片 0%，像模型不行）。已写 `check_stack.py` 兜住。

## 二、容器出网分裂：本轮最费时间的问题

### 现象

| 目标 | 宿主机 | Docker 容器 |
|---|---|---|
| `dashscope.aliyuncs.com` | ✅ 0.13s 返 401 | ❌ TCP 超时（000，8s） |
| `api.moonshot.cn` | ✅ 401 | ❌ 超时 |
| `open.bigmodel.cn` | ✅ 401 | ❌ 超时 |
| `api.deepseek.com` | ✅ | ✅ |
| `ark.cn-beijing.volces.com` | ✅ | ✅ |
| `bailian.console.aliyun.com` | ✅ | ✅ |
| `www.baidu.com` | ✅ | ✅ |

### 排查过程（每一步都排掉了一个可能）

1. **不是 DNS**。容器与宿主机的解析结果逐条对比，四个 IP 完全一致（`8.152.159.24` / `39.96.213.166` / `39.96.198.249` / `8.140.217.18`）。
2. **不是某个 IP**。用 `--resolve` 强制走单个 IP，四个从容器全超时、从宿主机全 401。
3. **不是 TLS**。TCP 连接本身就建不起来，`000` 而不是握手失败。
4. **不是系统代理**。`netsh winhttp show proxy` 显示「直接访问」。宿主机的 curl 也是直连。
5. **不是应用层防火墙按域名拦**。被拦的 `dashscope` 和能通的 `bailian.console.aliyun.com` 都是阿里云域名。

结论：**问题出在容器所在的虚拟网卡出口**（Docker Desktop 的 WSL2/Hyper-V NAT 路径），不在解析、不在证书、不在应用。根治 Windows 网络栈成本远高于收益。

### 解法：宿主机转发代理

容器能通宿主机（`host.docker.internal` 实测 200），所以在宿主机开一个转发口，让容器借道宿主机的网络出口：

```
容器 → host.docker.internal:18888 → 宿主机 Python 代理 → 物理网卡 → dashscope
```

`scripts/host_proxy.py`，三个设计决策：

- **只做 `CONNECT` 隧道**，双向转发字节流，不改写不缓存不解析内容。
- **强制鉴权**。必须绑 `0.0.0.0`（容器看到的 `host.docker.internal` 是 Docker 网关 `192.168.65.254`，不是 Windows 真实网卡，没法只绑那一个），而绑 `0.0.0.0` 意味着同局域网也能用。所以加 `Proxy-Authorization` 校验，缺凭据一律 407。
- **域名白名单**（`dashscope.aliyuncs.com` / `api.deepseek.com` / tiktoken 的 CDN），白名单外一律 403。

Dify 侧用 `docker-compose.override.yaml` 注入 `HTTPS_PROXY`（**不改上游 compose 文件**），`NO_PROXY` 覆盖 `db/redis/weaviate/ollama` 等内网服务名。

### 这中间踩的三个坑（都是我自己造的）

**坑一：listen backlog 只有 5。** 代理用的是 `socketserver.ThreadingTCPServer`，默认 `request_queue_size = 5`。而 Dify 0.15.3 的索引器里 `max_workers = 10` 是写死的（`core/indexing_runner.py:541`）——10 个线程同时建连直接打满 backlog，多出来的 SYN 被丢。表现为**部分文档索引偶发失败**（报 `Response output is missing or does not contain embeddings`），换个时间重跑又能过。修法：`request_queue_size = 256`。修完做 20 并发压测，20/20 通过。

> 这个坑值得记：报错信息指向"向量模型返回异常"，实际是**我自己代理的 backlog**。误导性极强。

**坑二：用 `nohup ... &` 启动的代理活不过这一个 shell 会话。** 它安静地死了，而 Dify 的调用全部失败——但失败的表现是**检索返回 0 条记录**，评估脚本打出一片 `0%`。第一眼看像"模型不行"。修法：改用受管的常驻方式启动。

**坑三：重建 api 容器后 nginx 缓存了旧 IP。** `docker compose up -d api` 之后 api 拿到新 IP，而 nginx 在启动时把 `api` 解析成了 `172.20.0.10` 就不再更新，于是所有请求 502。修法：`docker compose restart nginx`。

## 三、把百炼接进 Dify

### 一个前提事实

**Dify 0.15.3 是插件系统之前的版本**（插件系统从 v1.0.0 才有）。所以：
- 没有 `plugin_daemon` 容器，没有插件市场；
- 模型供应商**硬编码在镜像里**（`/app/api/core/model_runtime/model_providers/`，共 62 个）；
- 不能靠装插件扩供应商。

好消息：镜像自带的 `tongyi` 供应商本来就支持 `llm` / `text-embedding` / `rerank` 三类，配置方式是 `predefined-model` + `customizable-model` 混合——也就是说，预置模型直接用，**新模型可以自建**。

### 具体做法

| 步骤 | 内容 |
|---|---|
| 1 | `POST /workspaces/current/model-providers/tongyi` 写供应商级凭据（`dashscope_api_key`），返回 201 |
| 2 | 向量用**预置的** `text-embedding-v3`（1024 维，镜像自带，无需自建） |
| 3 | 重排序**自建模型项** `gte-rerank-v2`，因为镜像里只声明了老的 `gte-rerank`，而本账号对老版返回 403 `AccessDenied` |
| 4 | 把工作区默认向量模型指到 `tongyi/text-embedding-v3` |

脚本：`scripts/dify_add_bailian.py`。

> 一处判断：**没有用 `text-embedding-v4`**。v4 在自建模型项里能登记成功、容器内直调也返回 200，但镜像是 2024 年底的、它认识的模型只到 v3，走 Dify 的调用链时 `_get_max_chunks` 拿不到模型属性会退回默认值 1（即每次只发 1 条文本），430 多段会变成 430 多次请求。v3 有完整的 `model_properties`（context_size 8192 / max_chunks 25），是这条路里唯一稳妥的选择。

## 四、重建语料库与那次索引失败

用 `tongyi/text-embedding-v3` 重建为 `政策法规语料库v3`：**8 篇 / 435 段**。

第一次建库时有 **3 篇索引失败**（深圳条例、土壤污染防治法、噪声污染防治法，正好是最大的三篇），报 `[tongyi] Error: Response output is missing or does not contain embeddings.`。

排查路径：

1. 先在容器里对失败文档的段落逐条直调 SDK：**前 40 段连续全部 200**，没有限流、没有长度问题（连 12600 字的超长输入也返回 200）。所以不是模型侧。
2. 排掉 tiktoken 假设：我给白名单加了 `raw.githubusercontent.com` 和 `openaipublic.blob.core.windows.net`（Dify 分词表 CDN），但重试时代理日志里**没有任何这两个域名的请求**——说明本次根本没用上它们，假设不成立。**已记录为"未证实"，不做因果声称。**
3. 真正的原因回到坑一：**Dify 索引器 10 线程 vs 代理 backlog 5**。修掉 backlog（256）之后重传，8/8 全部成功。

顺带解决一个操作问题：**Dify 的 `processing/resume` 对 `error` 状态无效**（返回 `Document is not in paused status`），官方没有"重试"按钮。所以给 `dify_build_kb.py` 加了 `--repair`：删掉 error 文档、从可再生的人库文本重传。删除无信息损失。

## 五、检索层 A/B：重排实测效果

同一套 30 题、同一个知识库文本（`kb_text_v2`），只改检索配置。两次都从**评估脚本读取知识库自身存储的配置**（不再在脚本里写死一份，见下"判分口径"）。

### A 组 · 百炼向量、不重排

```
L1基础  n=12  recall@1  92%   @3 100%  @5 100%
L2推理  n= 8  recall@1  88%   @3 100%  @5 100%
L3边界  n= 6  recall@1 100%   @3 100%  @5 100%
合计    n=26  recall@1  92%   @3 100%  @5 100%

对抗题相似度：3/4 条 ≥ 正确题的最低分   ← 穿透
```

### B 组 · 百炼向量 + `gte-rerank-v2` 重排序

```
L1基础  n=12  recall@1 100%
L2推理  n= 8  recall@1  88%
L3边界  n= 6  recall@1 100%
合计    n=26  recall@1  96%   @3 100%  @5 100%

对抗题相似度：1/4 条 ≥ 正确题的最低分
```

### 分数分布（B 组）

| 层 | n | min | 中位 | max |
|---|---|---|---|---|
| L1 基础 | 12 | 0.904 | 0.941 | 0.949 |
| L2 推理 | 8 | 0.509 | 0.882 | 0.930 |
| L3 边界 | 6 | 0.366 | 0.690 | 0.954 |
| L4 对抗 | 4 | 0.134 | 0.261 | 0.447 |

**L1+L2 合并 min = 0.509；L4 max = 0.447。间隔 +0.062，一条阈值可以分开。**

这是**第二次**独立复现同一个结论。第一次在 `research/05` 里用 `text-embedding-v4` 在进程内做（余弦重叠 −0.071、重排间隔 +0.066）；这次换 `text-embedding-v3`、在真实 Dify 链路里做，结论一致（余弦 3/4 穿透、重排 L1+L2 与 L4 完全分离）。

> **同一个失效模式，两套向量模型，两次都复现——这不是偶然。** 双塔检索模型分不清「同一领域的无关文档」和「真正回答问题的文档」，cross-encoder 能。这是架构差异，不是调参问题。

### L3 为什么横跨整个区间——这不是缺陷

L3 六题是问「这条法规现在还有效吗 / 还能引用吗」。它们的重排分数是 0.366 / 0.467 / 0.602 / 0.777 / 0.778 / 0.954，横跨从"无依据"到"完全匹配"的全部区间。

拆开看就明白了：
- L3-05「呼伦贝尔条例的施行日期是哪一天」= **0.954**。答案**就在正文第五十条里**，检索当然给高分。
- L3-03「土壤污染防治法关于农用地分类管理制度的规定还能作为执法依据引用吗」= **0.366**。这条问的是**效力**，而效力根本不在法条正文里——土壤法正文一个字都没说自己已废止。
- L3-06「环境噪声污染防治法关于夜间施工噪声的规定还能直接引用吗」= **0.467**。同理，而且这部法的名称本身就是旧名。

**重排分数其实在回答一个更朴素的问题：「语料里到底有没有一段文字能回答你」。对时效题，诚实的答案就是"没有"。** 这恰好从检索侧印证了 v2 的做法——时效台账必须注入提示词，因为检索通道在结构上就够不着它。

## 六、端到端四轮对照（判分口径已修正）

| 轮次 | 配置 | L1+L2 判据词命中 | 引用可追溯 | 真编造 | 清单合规 | L4 拒答 | L3 时效提示 |
|---|---|---|---|---|---|---|---|
| v1 | Ollama `bge-m3`、无时效台账 | 100% | 90% | 7% | 100% | 4/4 | 17% |
| v2 | ＋时效台账注入提示词 | 100% | 87% | 13% ↑ | 100% | 4/4 | 67% |
| v3 | ＋切分段自带法规名 | 100% | **100%** | **0%** | 100% | 4/4 | 67% |
| v4 | 百炼向量＋`gte-rerank-v2` | 100% | **100%** | **0%** | 100% | **4/4** | **83%** |

### ⚠ 判分口径修正（会影响与上一轮汇报的数字对比）

上一轮汇报里「判据词命中 82% → 91% → 95%」这个指标，**本次改了统计范围，数字不可直接对比**。

原因：`判据词命中率` 是"回答里有没有出现预设答案键"。它在 L3/L4 上**系统性地骗人**：
- L4 的正确回答**本来就该是拒答**，不去命中任何答案键——把它的 0%/50% 读成缺陷，会去"修"一个不存在的问题；
- L3 问的是"还有效吗"，正确措辞和出题时写的答案键几乎不可能逐字对上。实测有两条**完全正确**的回答（都答出了"检索结果中没有该法典全文，无法给出"），因为和预设的『库中无法典全文』差几个字，被判未命中。

所以现在**只在 L1+L2 上统计这个指标**，L3/L4 显示 `—`。修正后四轮在 L1+L2 上都是 100%——说明"答到点上"这件事从第一轮起就没问题，**真正的差异全在引用可追溯和时效处理上**。修正前的 82% 是被 L3/L4 的噪声拉低的。

### 同时修掉的一个假阳性

L3-02 那条"真编造"，是清单里写 `无具体条号（仅依据语料时效台账判定效力，未引用具体条文）`——这是**诚实且正确**的做法，却被我的 `art_ok` 当成"条号反查不到"。已修：清单条目以「无」开头一律视为合规。

修完后 v4 的**真编造 = 0%**（30/30），四轮里 v1 有 7%、v2 有 13%、v3 和 v4 是 0%。

### v4 相比 v3 到底改善了什么

硬指标（引用可追溯 100% / 真编造 0% / 清单合规 100% / L4 拒答 4/4）**四轮里 v3 和 v4 完全并列**。v4 的真实增量是：

1. **L3 时效提示 67% → 83%**（重排把更相关的时效条文排到前面，模型更容易注意到时效状态）；
2. **检索 recall@1 92% → 96%**；
3. **检索层多了一个硬闸门**——这才是重点，见下节。

## 七、重排的真实定位：从"可选优化"改为"安全阀"

`research/04` 里 L4 的 4/4 拒答率，靠的是**提示词里写死一条规则**（"检索结果中没有的法规，必须明确说找不到"）。这是**软约束**：换模型、上下文挤了、温度变了都可能失守。它不是一个可以写进 SLA 的保证。

重排给的是**检索层的硬约束**：在文本还没进模型之前，就能判断这次召回到底有没有拿到能回答问题的东西。两者不替代，是**叠加**关系——软约束负责表达，硬约束负责拦截。

**所以手册第 6 步的定位要改。** 它原本被写成"精度优化"的可选环节（本机没有 rerank 模型时甚至写明可以跳过）。现在看，**重排序是本产品的安全阀，不是优化项**。

### 边界必须说清楚

1. **对抗样本只有 4 道。** 间隔 0.062 是在这个样本上量出来的，**不足以宣称"0.48 是工业级阈值"**。要变成可上线规则，对抗题至少要扩到 30–50 道把分布打实。**这是当前最该补的一件事。**
2. **阈值只能用来触发三态降级，不能用来直接拒答。** L2-02（怀化的城区内/外处罚主体对比，一道两跳题）重排只有 0.509，紧贴边界。如果阈值卡高一点，这道正确答案就被误杀了。合理形态：
   - 高分 → 正常作答
   - 中间带 → 标注「依据强度弱，建议人工复核」
   - 低分 → 明确告知检索不到依据
3. **反向风险同样存在**：答案确实在语料里但表述间接时，重排也可能误杀。**不能用"低分即无依据"直接判死。**

## 八、这套栈的三个易碎点

| 易碎点 | 断了会怎样 | 兜底 |
|---|---|---|
| 宿主机转发代理 | 百炼调用全挂，**表现为评估表一片 0%**，像模型不行 | `check_stack.py` 第 2/3 项专测这一环 |
| 重建容器后的 nginx | 全部请求 502（缓存了旧 IP） | `docker compose restart nginx` |
| 知识库的检索配置 | 应用自己还有一份 `dataset_configs`，**两份不一致会静默失效** | `check_stack.py` 第 5 项做自洽性校验 |

`scripts/check_stack.py` 一次体检五项（Docker / 代理 / 容器出网 / 知识库 / 检索配置），每项都给可执行的修复命令。**换机器、重启后、跑评估前先跑它。**
