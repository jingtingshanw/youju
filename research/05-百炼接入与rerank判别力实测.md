# 百炼接入与 rerank 判别力实测

日期：2026-10-14　机器：本机（Windows 11）
触发：用户提供了 `.env`（此前以为是空模板），内含此前开通的三家账号

---

## 一、先说结论

1. **三把钥匙里两把是活的。** 百炼（DashScope）与 DeepSeek 实测可调且各有额度；火山方舟那把钥匙**本身有效，但账号下一个模型都没开通**。
2. **百炼一次补齐了本机缺的两块能力**：向量模型（`text-embedding-v4`，1024 维）和**重排序模型**（`gte-rerank-v2`）。后者正是手册第 6 步一直做不下去的原因——本机此前**没有任何 rerank 模型**。
3. **最重要的产品结论：rerank 分数可以作为「这次检索到底有没有依据」的判据，而向量余弦不能。** 这是本项目此前记录在案的最致命失效模式（对抗题拿到 0.71 的相似度），本次在 24 道题上做出了可分离的阈值区间。

三个必须区分开的失败态，这次都碰到了，值得写进排查手册：

- **钥匙不对** → 401 / `InvalidApiKey`
- **钥匙对、模型没开通** → `ModelNotOpen`
- **能用但没钱/超频** → 402 / 429（本次没碰到）

**⚠ 本节有一处自我更正（2026-10-14 晚补正）。** 本文初稿写的是「方舟把『未开通』和『模型名写错』合并成同一条错误」——**这是错的**。当时只试了三个模型 ID 就下了结论，实际把 135 个目录模型全跑一遍后，方舟的错误码是**分得开**的：

| 错误码 | 含义 | 处置 |
|---|---|---|
| `ModelNotOpen` | 模型存在、账号没开通 | 去控制台开通即可 |
| `InvalidEndpointOrModel.NotFound` | 模型 ID 不存在 / 已下架 / 无权访问 | 换 ID，开通也没用 |

而且 `/api/v3/models` **确实能列**——返回 135 个模型，带 `status` 字段（`Shutdown` 83 / `Retiring` 17 / 空 35）。所以方舟是可以枚举的，初稿说「清单藏得深」也不准确。

**教训**：用三个样本下结论，风险就在这。当时那条「两个错误合并成一条」，只要多试几个模型就会发现自相矛盾。凡是准备写进文档的规律性结论，样本量要先说清楚。

补正后的方舟实况（账号 2132084895，2026-10-14）：`Shutdown` 的 83 个一律 `NotFound`，非 Shutdown 的 52 个里 **7 个可用 / 21 个 `ModelNotOpen` / 24 个 `NotFound`**。

**7 个可用模型**：`doubao-seed-2-0-mini-260428`、`doubao-seed-2-0-lite-260428`、`deepseek-v4-flash-ga-260731`、`deepseek-v4-pro-ga-260813`、`doubao-seed-2-1-lite-260915`、`glm-5-3-flash-260828`、`deepseek-v4-1-flash-260910`。

**关键缺口**：方舟**没有可用的向量模型**（7 个 `doubao-embedding-*` 全在 NotFound 或 ModelNotOpen 里，唯一可开通的 `doubao-embedding-vision-251215` 是视觉向量模型，不适合纯文本法规检索），**整份 135 个模型的目录里一个 rerank 都没有**。所以：对话可以走方舟，**向量和重排序仍然只能走百炼**。

> 关键：百炼的 `/compatible-mode/v1/models` 列出的模型有几十个（含 `qwen3.8-flash`、`glm-5.3-prime`、`step-5-preview` 等），但**列表里有 ≠ 能调**——`qwen3-max` 就在列表里却返回 404 `model_not_found`。清单只说明「平台上存在」，说不明「你的账号能用」。方舟同理：目录里有 135 个，你的账号能用 7 个。

### 百炼可用能力清单（实调确认）

| 类别 | 模型 | 实测 |
|---|---|---|
| 对话 | `qwen-plus`、`qwen-max`、`qwen-turbo` | ✓ |
| 向量 | `text-embedding-v4`（1024 维）、`text-embedding-v3`（1024 维）、`text-embedding-v2`（1536 维） | ✓ |
| 重排序 | `gte-rerank-v2` | ✓ |
| 重排序 | `gte-rerank`（旧版） | ✗ 403 `AccessDenied`（需单独申请） |

**注意一个数**：`text-embedding-v4` 是 1024 维，与本机 Ollama 的 `bge-m3` 同维。维数相同**不等于**可以混用——两者的向量空间完全不同，换供应商必须整库重建索引。同维的好处是数据库 schema 不用改。

## 三、核心实验：rerank 能不能当「有没有依据」的判据

### 为什么必须做这个实验

`research/02` 记录过一件极其危险的事：问一部语料里根本不存在的《生态环境法典》，向量检索照样给到 **0.711** 的相似度，与真正答对的题（0.669–0.806）**落在同一个分数带**。当时下的结论是：**不能用相似度阈值判断「有没有依据」**，产品必须显式做引用存在性检查。

那个结论是对的，但它是**双塔模型**的先天缺陷：查询和文档各自压缩成向量、再算余弦，本质在比「这两段话像不像」，而不是「这段话是否回答了这个问题」。

cross-encoder 重排序原理不同：它把查询和文档**拼成一条输入**过一遍模型，输出的是相关性判断。理论上应该能分开。

**本次就是去验证这件事。**

### 实验设计

- 检索单元：`data/kb_text_v2/*.txt` 的每一行，共 **427 段**，来自 8 部法规——这正是入库 Dify 的切分段，所以候选集与线上召回的同一批文本。
- 向量化：`text-embedding-v4`，1024 维（带缓存，重跑不再烧钱）。
- 对照题：**20 道应当命中的**（L1 基础 12 + L2 推理 8）对 **4 道 L4 对抗题**（含"生态环境法典"、"上海市生活垃圾管理条例"、"怀化第四十条"这类语料里根本不存在的内容）。
- 流程：余弦取 top5 → 把 top5 交给 `gte-rerank-v2` → 比较两组的 top1 分布。脚本 `scripts/probe_cloud_stack.py`。

### 结果

```
【余弦相似度（双塔）】
  应命中题（n=20） min=0.8061  中位=0.8935  max=0.9259
  对抗题  （n=4）  min=0.6215  中位=0.6690  max=0.8772
  → 应命中题最低 − 对抗题最高 = -0.0710   ✗ 区间重叠，不可分离

【rerank 相关性（cross-encoder）】
  应命中题（n=20） min=0.5124  中位=0.9236  max=0.9491
  对抗题  （n=4）  min=0.1284  中位=0.1945  max=0.4462
  → 应命中题最低 − 对抗题最高 = +0.0661   ✓ 可被一条阈值分开
     可用阈值区间：（0.4462, 0.5124），例如取 0.4793
```

**余弦侧的重叠不是「差一点」，是彻底穿透。** 最刺眼的一条是 L4-03（问《怀化市扬尘污染防治条例》**第四十条**，该条例只有 34 条）：

| | 余弦 top1 | rerank top1 |
|---|---|---|
| L4-03 怀化第四十条（**不存在**） | **0.8772** | 0.1941 |
| 20 道正确答案的中位 | 0.8935 | 0.9236 |
| 20 道正确答案的最低 | 0.8061 | 0.5124 |

余弦给一道**问不存在的条文**的题打了 0.877——比 20 道真正答对的题里最低的那道还高 0.07，只比中位低 0.016。**向量检索在语义空间里看到「怀化 + 扬尘 + 条号」就认定高度相关，它无从判断这个条号是否越界。** 而 rerank 直接把它压到 0.194。

### 但要说清楚这个结论的边界

1. **对抗样本只有 4 道。** 阈值区间 (0.4462, 0.5124) 的宽度只有 0.066。n=4 不足以宣称「0.479 是工业级阈值」。要把它变成可上线的规则，至少需要 50–100 道对抗题把分布打出来。
2. **有一次逼近阈值的正确题。** L2-02（怀化散装物料遗撤，问城区内/外的处罚主体差异，是一道需要两跳、跨第二十九条与第十七条的题）rerank 只给 0.5124。**如果阈值卡在 0.5 以上，这道正确答案会被误杀。** 这说明单一 top1 阈值过于粗暴，合理形态应是：
   - 阈值只用来触发**降级三态**，不用来直接拒答：`高 → 正常作答`／`中间带 → 标注「依据强度弱，建议人工复核」`／`低 → 明确告知检索不到依据`；
   - 或改成 top-k 的聚合量（如 top3 均值的方差）而不是单点最大值。
3. **反向风险同样存在**：如果答案确实藏在语料里但表述间接（例如条文中只出现一次、被大量无关文字包围），rerank 也可能误杀。**不能用「低分即无依据」直接判死。**

### 这个发现的产品含义

之前 `research/04` 里 L4 的 4/4 拒答率，靠的是**提示词里写死一条规则**——"检索结果中没有的法规，必须明确说找不到"。这是**软约束**：模型换了、上下文挤了、温度变了都可能失守。

rerank 阈值提供的是**检索层的硬约束**：在文本还没进模型之前，就能判断这次召回到底有没有拿到能回答问题的东西。两者叠加才是可靠的。

**这也顺手改写了手册第 6 步的定位**：它原本被写成"精度优化"的可选环节（本机没 rerank 模型时甚至允许先跳过）。现在看，**重排序是本产品的安全阀，不是优化项。**

## 四、对架构的影响：还留着 Ollama 吗

现状是：本机跑 9 个 Dify 容器 + 1 个 Ollama 容器，Ollama 只承担一件事——提供 `bge-m3` 向量。

百炼一次性把**向量、重排序、对话**三块都补上了，且都是云端 HTTP 调用。也就是说，**只跑 Dify 本体、不跑 Ollama，也能建库和检索**，运维面从 10 个容器降到 9 个。

但**现在还不换**，理由是数据边界：

| 场景 | 向量该放哪 | 说明 |
|---|---|---|
| 本次语料（公开法律/地方性法规） | 云端可行 | 文本本身就是公开出版物，出网无实质风险 |
| 未来接入用户内部制度文本 | **必须本地** | 这是产品要卖给政府/企业的场景，内部文件不能出网 |

所以正确的做法是**两条路都留着、可切换**，而不是二选一。这一点应当写进 PRD 的部署形态章节，也是面试时可以讲的一个具体取舍：*"我们不是在『本地还是云端』里选一个，而是把向量化做成可插拔的一层，公开语料走云、内部文本走本地，同一套检索逻辑。"*
