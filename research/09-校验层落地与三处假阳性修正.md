# 09 · 校验层落地，与判分口径的三处假阳性修正

日期：2026-10-14　前置：`research/08`、`prd/PRD-v1.md`

本轮做了三件事：把闸门 2 从"提示词里的约束 + 判分器里的检查"变成**产品内可运行的校验层**；
给校验层做命令行与网页两个入口；把评测脚本与校验层的重复实现收敛到同一份底层。
过程中翻出五处真实缺陷，其中三处是**假阳性**——该放行的被拦了。

---

## 一、闸门 2 落地：`scripts/gatekeeper.py`

这是 PRD 第 6 节待办 1，也是 `research/08` 第七节记的最大结构缺口。

**定位**：产品的一部分，不是评测脚本。拿「问题 + 候选回答 + 本次召回的段落」，
在**不调用任何模型**的前提下判定这份回答能交付到什么强度。

**为什么必须是确定性的**：提示词里的四条硬约束是模型自己遵守的。换模型、调温度、
绕过应用直调接口，约束就没有了——没有告警、没有报错。而闸门 2 要判的三件事没有一件需要模型：

| 要判的事 | 需要什么 |
|---|---|
| 这个条号超过该法规的条数了吗 | 一张条数表 |
| 这条引用真的在本次召回里吗 | 召回的段落 |
| 这部法规还有效吗 | 一张时效台账 |

所以它可以写进 SLA、可以解释到"第几条第几项不通过"。

**四项检查与合成规则**见 `docs/项目总说明-v1.md` 第 2.3 节，此处只记本轮改了什么。

### 自检用例（不调用模型，10 组）

越界条号 / 库外法规 / 时效硬规则 / 已废止+拒答不得降级 / 清单声明无依据+正文只作历史说明 /
自相矛盾 / 正常回答放行 / 失效法规只做历史说明 / 只问效力状态不得判拒答 / 自报时效与台账不符不得放行。

**10/10 通过。** 这一组用例的价值在于：它把"校验层本身的行为"与"模型的行为"分开了。
模型换了、语料换了，这 10 组用例的期望值不该变；变了就说明校验层的判据被动过。

## 二、五处缺陷

### 缺陷 1 · 正则的「区块结束」定义（标题写法变化引发）

`BOUNDARY_BLOCK_RE` / `HISTORY_BLOCK_RE` 初版用 `(?=\n\s*【|\Z)` 判断区块结束。
模型把标题写成 `### 【引用清单】` 时，`\n\s*【` 匹配不上（"### "不是空白），
区块一路吃到文末。两处真实故障：

- `_first_paragraph` 把【引用清单】的内容当成了结论（用户看到的结论是一串条号）；
- 【历史沿革】区块吞掉它后面的整个结论区 → 时效硬规则的操作性指引检查**漏检**。

第二处更危险：该拦的没拦住，而且不报错。

修法 `_SEC_END`：把 markdown 井号前缀纳入判定，**并给「结论」加否定前瞻
`结论(?!边界)`**。第二条是修的过程中新踩出来的坑——字段行「**结论边界**：可作答」
也满足"行首是结论"，于是【边界判定】块在第二行被截断，四个字段全丢。

**教训**：区块边界这类判据，一旦依赖"标题长什么样"，就必须把模型可能用的标题写法
列全。写不全时，宁可让边界更宽（漏截）也不要更窄（误截）——误截会安静地吃掉后面的内容。

### 缺陷 2 · 没有条号可引用被当成没有依据（假阳性）

合成规则里有一句「一条可交付依据都没有 → 拒答」。这句话对"模型什么都没给出来"是对的，
但它把一类**完全正确的回答**误杀了：

```
L3-01  问《中华人民共和国噪声污染防治法》现在还有效吗？
       这个问题的依据来自**时效台账**。法规正文里没有"这部法还有效吗"这句话，
       所以它永远不会有条号可引用。→ 正确答案（已废止）被降成拒答。
L3-02  同上（海南决定）
```

这与 PRD 第 4.2 节给闸门 1 定的取向是同一条：**宁可漏挡，不可误杀**。
误杀会让用户以为库里没有，直接放弃使用。

修法用的是完全客观的判据 `_ledger_corroborated()`：
**问题指向的库内法规都在台账里，且模型自报的时效状态与台账逐字相同**。
满足即说明回答的核心主张被外部真值印证过了，按「部分作答」交付
（结论可用，但不构成可引用的条文依据）。

**不放弃否决权**：只在没有拦截项、且模型自报比"拒答"更宽松时生效；
自报「拒答」的回答永远不会被它升格。配两组自检用例（该放行 / 该拦）。

### 缺陷 3 · 正文兜底路径缺了否定语境过滤（假阳性）

`extract_cites()` 提取正文里的「《法规》第X条」时不看语境，把两类句子当成了引用：

```
L4-12  「该条例共 66 条，不存在第八十条」    → 被当成越界引用，C1 拦截
L3-02  「该决定暂调《海商法》第四条」        → 被当成库外法规引用，C2 拦截
```

两道**完全正确**的回答被判成拒答。

修法：清单**明确写「无」**时，正文里的条号按**说明性引用**处理，不登记为交付依据。
理由是清单是模型对"我依赖了哪些条目"的声明，它声明无依据时，正文里的条号是在解释、
不是在交付。**编造仍然照抓**：C2 末尾的正文扫描会检查"这个条号在本次召回里根本不存在"，
C3 的时效硬规则走 `OPERATIONAL_CITE_RE`，都不受影响。
清单**缺失**（模型没按格式输出）时不走宽松口径——它连契约都没遵守。

> 这已经是**同一根源的第 5 次**：拿一个不区分语境的指标代替语义判断
> （前四次见 `eval/README.md`）。这次的形态是"正文里出现条号 = 引用了这个条号"。

### 缺陷 4 · 法规名匹配只认书名号，产品层整块漏判（假阳性）

`query_laws()` 只认书名号内容。产品层面对的是真人提问，用户常常不打书名号
（「……授权决定，现在还有效吗？」），于是这类问题被判成"没指向任何库内法规"，
时效比对整块跳过——缺陷 2 的修法也因此失效。

修法：给 `query_laws()` 加可选参数 `include_full_names`（**默认关，评测侧行为不变**），
开启时另外接受「问题里**逐字出现库内法规的正式全称**」。
**只放开正式全称，不放开落库代号/简称** —— 简称会撞上「长名包含短名」那个坑
（「环境噪声污染防治法」包含「噪声污染防治法」）。正式全称里带「环境」二字，
逐字比对天然区分得开。这是这个坑的**第 3 次**出现，修法一次比一次收窄。

### 缺陷 5 · 演示页样本注入把标记留在 JSON 里

`build_demo.py` 初版把 `/*SAMPLES-START*/` 标记写在 `<script type="application/json">`
**内部**，注入后 JSON 里混进注释，`JSON.parse` 直接抛错，页面一片空白。
这种错只有真打开页面才发现。

修法：标记移到脚本标签**外面**（用 HTML 注释），并在构建阶段加断言——
注入后必须能被 `json.loads` 吃下去、条数要对、样本里不能含 `</script`。
**把"只有打开页面才发现"的错挪到构建阶段**，是这一步的主要收益。

## 三、评测脚本与校验层收敛到同一份底层

新建 `scripts/legalkit.py`，只放三件事：名称归一、条号解析、三张表读取。
`eval_run_app.py` 里原先各自实现的 `norm_doc` / `parse_manifest` / `cn2int` /
`load_laws` / `query_laws` / `parse_boundary` / `boundary_consistency` /
`load_stale_ledger` / `_has_window` 全部改为引用它，重复的常量与正则一并删除。

**为什么这件事必须做**：同一个"把法规名对上号""把中文条号变成数字"的需求在两处各写一遍，
就会出现两份实现、两套边界情况、两个地方改 bug。而这两处必须给出**完全一致的结论**，
否则"评测通过了、上线出问题"就是必然。

**验证方式**：改完之后用 `--rejudge` 在 `app-v7-boundary.json` 上重算，
**输出与改动前逐字节一致**（`diff` 为空）。所有指标、所有明细、所有告警列表都没动。
这是本轮唯一一个"改动前后必须完全相等"的任务，因此也是唯一一个有硬性验收标准的任务。

## 四、闸门 2 全量对照：66/66

新建 `scripts/gatekeeper_sweep.py`，把**产品校验层**跑在已保存的 66 题结果上，
对照"模型自己填的结论边界"与"产品实际交付的结论强度"。

这不是同一件事。评测脚本读的是**模型自报**（模型觉得自己答到什么程度），
交付给用户的是**规则判定**（这份回答实际能交付到什么强度）。两者长期不一致的话，
说明评测与产品在衡量两件事。

**修完上面三处假阳性之后：66/66 一致。**

| 模型自报 | 规则判定 | 题数 |
|---|---|---|
| 拒答 | 拒答 | 40 |
| 可作答 | 可作答 | 20 |
| 部分作答 | 部分作答 | 6 |

修之前是 63/66，三处分歧（L3-01 / L3-02 / L4-12）全部由校验层的假阳性造成。

**一点必要的警惕**：100% 一致本身不是"校验层多余"的证据。它只说明在这批
"按 v3 契约产生的回答"上，规则层没有额外的异议。校验层的价值在另外两处：
① 它拦得住契约被绕过时的回答（10 组自检用例覆盖）；
② 它把结论强度从"模型自称"变成"可核对"。

## 五、实际操作层：三层入口

| 层 | 文件 | 面向谁 |
|---|---|---|
| 规则层 | `scripts/gatekeeper.py` | 任何后端；也可单独 `--answer/--resources` 做离线核对 |
| 命令行 | `scripts/ask.py` | 单问 / 交互 / 批量；每次问答落盘完整 JSON |
| 网页 | `demo/index.html` + `scripts/serve_demo.py` | 演示与客户沟通 |

命令行与网页共用 `ask.py` 的 `analyze()`，**不存在两套判定文案**。

**网页有一个刻意的设计**：它内置了 7 个真实问答样本（取自 v7 的 66 题），
所以**不启动任何服务、直接双击打开也能看到真实输出**；
一旦本地服务在跑，它自动切到实问模式。
这样"给人看一眼"这件事不再依赖现场环境是否配置好。

- **闸门 1 阈值 0.40 不可迁移**（`research/07` 的结论，本轮无改动）。

- **闸门 2 还没有被强制接进应用链路**。现在靠调用约定：业务系统只允许调外层服务
  （`ask.py` / `serve_demo.py`），不允许直连 Dify 应用。这仍是当前最大的结构缺口，
  因为约定是可以被绕过的。
