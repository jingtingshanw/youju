## 二、根因：`reranking_mode` 没写，混合检索等于没融合

不是权重没落库，是**融合器压根没启动**。按 Dify 0.15.3 源码读下来：

1. `services/hit_testing_service.py:HitTestingService.retrieve` 把
   `reranking_mode=retrieval_model.get("reranking_mode") or "reranking_model"` 传给检索服务。
   —— 请求体里不写 `reranking_mode`，服务端就默认取 **`reranking_model`**。
2. `core/rag/datasource/retrieval_service.py:RetrievalService.retrieve`
   对 `hybrid_search` 起了两个线程：`embedding_search` 与 `full_text_index_search`，
   两边 `all_documents.extend(...)` —— **直接拼在一个 list 里**，此时还没有去重、没有排序、没有截断。
3. 融合全靠 `DataPostProcessor`，而它的 `_get_rerank_runner`：

```python
if reranking_mode == RerankMode.WEIGHTED_SCORE.value and weights:      # "weighted_score"
    ... 返回 WeightRerankRunner
elif reranking_mode == RerankMode.RERANKING_MODEL.value:                # "reranking_model"
    rerank_model_instance = self._get_rerank_model_instance(...)
    if rerank_model_instance is None:
        return None                                                    # ← 本机走这条
```

本机没有任何 rerank 模型，所以 `_get_rerank_model_instance` 返回 None，runner 为 None，
`invoke()` 里的 `if self.rerank_runner:` 不成立 —— **整段后处理被跳过**。

后果链条，与实测现象一一对应：

| 后果 | 源码位置 | 实测现象 |
|---|---|---|
| 不去重 | `WeightRerankRunner.run` 里才按 `doc_id` 去重 | 同一段落成对出现 |
| 不融合打分 | 加权公式只在 `WeightRerankRunner` 里 | 关键词侧的记录 `metadata["score"]` 从未被赋值 → 读出来是 `None` → 显示 0.000 |
| 不按分排序 | 同上 | 0.000 的那批排在正常分的前面 |
| 不截断 top_n | `return rerank_documents[:top_n]` 在 runner 内 | `top_k=5` 却返回 9 条（两路结果相加） |

第 4 条是最容易被忽略的：**`top_k` 在退化状态下不生效**，所以「8 条探针全部命中 top3」这个
早期结论其实是在 top_k=2、两路混排、无去重的状态下得到的，属于侥幸成立。

## 三、修复

```python
TARGET = {
    "search_method": "hybrid_search",
    "reranking_enable": False,
    "reranking_mode": "weighted_score",   # ★ 缺这一行，上面整段后处理都不会执行
    "reranking_model": {"reranking_provider_name": "", "reranking_model_name": ""},
    "top_k": 5,
    "score_threshold_enabled": False,
    "score_threshold": None,
    "weights": {"keyword_setting": {"keyword_weight": 0.3},
                "vector_setting": {"vector_weight": 0.7,
                                   "embedding_provider_name": "ollama",
                                   "embedding_model_name": "bge-m3"}},
}
```

另有两点事实需要记下：

- **0.15.3 的 `weights` schema 里没有 `weight_type` 字段**。
  我最初按较新版本的写法带了 `"weight_type": "customized"`，PATCH 回去后被静默丢弃，
  只剩 `keyword_setting` / `vector_setting` 两个数值权重。所以回读校验不能拿 `weight_type` 当条件
  —— 第一版校验脚本就是这么误报「未完全落库」的。判断依据应是数值权重本身。
- 三处配置要保持一致，任一漏写就退回退化状态：`PATCH /datasets/{id}`、
  hit-testing 请求体、应用侧的 `model_config.dataset_configs`。
  全部落在 `scripts/dify_fix_retrieval.py` / `dify_hit_test.py` / `eval_run.py` / `dify_build_app.py`。

## 五、一个必须写下来的结论

配置修好以后，分数分布**比修前更不利于「用阈值判有无依据」**：

| 状态 | 正确题 top1 区间 | 对抗题（库里没这部法）top1 |
|---|---|---|
| 修复前（未融合） | 0.669 – 0.806 | 0.700 – 0.711 |
| 修复后（正确融合） | 0.544 – 0.861 | 0.477 – 0.739 |

修复前对抗题 0.711 落在正确题区间中段；修复后最“能骗过检索”的那道对抗题
（真法规 + 真主题 + 假条号）拿到 **0.739，比 81% 的正确题还高**。

也就是说：**修好配置并没有让「分数鉴别依据有无」变得可能，反而更不可能了。**
这不是修复的副作用，是把系统调到正常状态后暴露的事实 —— 阈值路线本来就走不通，
产品的第二三层（显式引用存在性检查、时效校验）不是「优化」，是唯一可行的路径。
量化过程见 `scripts/eval_run.py` 的「指标 3」。
