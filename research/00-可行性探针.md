# 00 · 可行性探针（本机版）

日期：2026-10-13　机器：本机（Windows 11）

## 一、这一步原本要回答的问题

实施手册第 0 步叫「可行性探针」，原产出是**一次 10 模型横评**（在上一台机器上用百炼
`qwen-plus` 端点跑出，产出 107KB CSV）。**那件事是在另一台机器、另一套 key 下做的，
本轮没有复现，也不打算假装复现。**

本轮把它重做成本机口径。要回答的还是同一件事，但问题换成了更硬的形式：

> 在这台电脑上（无 GPU、无云模型授权、内网受限），
> 「政策效力核验与可溯源引用引擎」这件事**能不能真的跑起来**？

拆成四个可验证的子问题：

| # | 子问题 | 为什么它是关键路径 |
|---|---|---|
| 1 | 能不能在本机把 RAG 平台跑起来 | 跑不起来后面全是纸上方案 |
| 2 | 有没有可用的向量模型 | 没有 embedding 就建不了知识库，这是最容易卡死的一环 |
| 3 | 有没有可用的对话模型、成本和延迟是多少 | 决定这件事是「能演示」还是「能出产品」 |
| 4 | 语料能不能被可靠地结构化 | 法条切分错了，检索层的所有指标都是假的 |

## 二、逐项结论

### 2.1 RAG 平台：可行（Dify 0.15.3 本机自建）

9 个容器全部 Up：`nginx / api / worker / web / db / redis / weaviate / ssrf_proxy / sandbox`，
入口 `http://localhost`，数据库 `postgres:15-alpine`。

**唯一的实质性障碍在拉镜像这一步，不在 Dify 本身**：Docker Hub 的
`registry-1.docker.io` 可达（返回 401，正常），但签发 token 的 `auth.docker.io`
经代理后 TLS 握手失败（`schannel: failed to receive handshake`，5 秒超时），
于是所有 `docker pull` 都失败。绕法：

```bash
docker pull docker.m.daocloud.io/<repo>:<tag>
docker tag  docker.m.daocloud.io/<repo>:<tag> <repo>:<tag>
```

这一点值得单独记：它会让「Dify 装不上」看起来像是 Dify 的兼容性问题，
实际是本机网络策略问题。**归属判断错误会把整条技术路线否掉。**

### 2.2 向量模型：本轮的真正卡点，最后走本机 Ollama

Dify 里原本只配了 **DeepSeek**（`deepseek-chat` / `deepseek-coder` / `deepseek-reasoner`），
**没有任何 embedding 模型**，而 DeepSeek 官方不提供 embedding 接口。
Dify 建知识库时会取「工作区默认向量模型」（出厂指向 OpenAI 的 `text-embedding-ada-002`），
不改这一项会直接报 `Model text-embedding-ada-002 credentials is not initialized.`

排查过的四条路：

| 路线 | 实测结论 |
|---|---|
| 火山方舟 embedding | `ARK_API_KEY` 有效（账号 2132084895，能列出模型目录），但调用返回 **`ModelNotOpen`** —— 控制台一个模型都没开通。另：**方舟目录中 rerank 模型数量为 0** |
| 阿里云百炼 | 本机没有 `DASHSCOPE_API_KEY` |
| HuggingFace TEI | `huggingface.co` 直连超时被墙（`hf-mirror.com` 可达） |
| **本机 Ollama** ✅ | `registry.ollama.ai` 可达，`bge-m3`（1.2 GB、1024 维）在库中，CPU 上跑得动 |

落地：

```bash
docker run -d --name ollama --network docker_default -p 11434:11434 \
  -v ollama_models:/root/.ollama --restart unless-stopped ollama/ollama
docker exec ollama ollama pull bge-m3
```

**必须挂到 `docker_default` 网络**，Dify 才能用 `http://ollama:11434` 直连。

### 2.3 对话模型：可用，成本结构允许出产品

- 模型：`deepseek-chat`（Dify 内已配好）
- 30 题端到端平均 **2.2 秒/题**，中位 2.2 秒，最长 4.5 秒，30 题合计 66–69 秒
- 全链路没有需要 GPU 的环节（embedding 跑在本机 CPU 上的 Ollama）

按这个延迟，单次核验是「等得起的」，可以做成对话式产品而不是批处理工具。

### 2.4 语料结构化：可行，而且顺带发现台账有错

本机没有原方案依赖的 PKULaw 解析器，所以自己写了一个纯标准库的 OOXML 解析器
（`scripts/build_corpus.py`），产出结构化结果（blocks / preamble / articles / 表格）。

关键设计：**Dify 的分段标识符是字面量字符串、不支持正则**。所以采取的办法是
「先把入库文本格式化成一条一段，再把分段标识符设成换行」——
条文粒度切分就免费得到了，不需要正则。

切分结果的独立校验：用 editor_sdk 的结构化计数与自写解析器交叉核对，
**416 条有效条款，其中 6/8 份与台账完全一致**。不一致的两处反而是收获：

| 文件 | 台账 | 实测 | 结论 |
|---|---|---|---|
| 怀化市扬尘污染防治条例 | 49 | 34 | **台账有误**，应改为 34 |
| 海南决定 | 8 | 0 条条号 | 台账的「8」是表格行数，该文件是表格型、无条号 |

## 三、这一轮新增的能力边界（负面结论也要记）

以下都是**实测确认做不到**的，不是没试：

1. **本机没有 rerank 模型。** Dify 的 `volcengine_maas` 供应商只支持 `llm` 与
   `text-embedding`，方舟模型目录里 rerank 数量为 0。所以实施手册第 6 步的重排序
   在本机无法执行，当前一律 `reranking_enable: false`。
2. **云端模型无法做横评。** 方舟账号一个模型都没开通，没有百炼 key。
   跨模型对照需要用户先在控制台开通，否则这一项无法在本机补齐。
3. **Dify 的 `customizable-model` 供应商没有 provider 级凭据。**
   ollama 属于这一类，写 provider 级凭据会返回 400
   （`Provider ollama does not have provider_credential_schema`）——**这是预期行为，不是故障**。
   凭据要挂在模型上：`POST /console/api/workspaces/current/model-providers/ollama/models`。
4. **Dify 0.15.3 的 `weights` schema 里没有 `weight_type` 字段**，
   带上会被静默丢弃。回读校验不能拿它当条件（详见 `research/03`）。

## 四、这一步的最终结论

**四个子问题全部为「可行」，但代价不在技术选型上，而在「以为是技术问题、其实是配置/口径问题」的那些地方。**
本轮实际花掉最多时间的三件事，没有一件是算法问题：

- 镜像拉取被本机 TLS 策略挡住（网络归属判断）
- 建库失败源于一个出厂默认值（工作区默认向量模型指向 OpenAI）
- 混合检索的两路结果没有融合（`reranking_mode` 缺一个字段，详见 `research/03`）

这三件都属于「不实测就一定会踩、踩了又会误判为技术不可行」的类型。
所以第 0 步真正的产出不是「能不能做」的结论，而是**这台机器上的实际约束清单**：

```
可依赖：Docker / Ollama(bge-m3) / Dify 0.15.3 / DeepSeek(chat) / 本机 CPU embedding
不可依赖：Docker Hub 直连 / huggingface.co / 方舟模型（未开通）/ rerank（无）
须绕行：docker.m.daocloud.io / hf-mirror.com
```

后续所有步骤都在这份清单上跑，`research/02`、`03`、`04` 是它的展开。
