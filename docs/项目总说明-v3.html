卷首 · 一页速览

0.1 它是什么：三层数据，一个判断

L0  法律名录        308 条      「这部法还在不在」        ← 全国人大《现行有效法律目录》
L1  目录层       66,692 条      「这个方向有哪些文件」    ← 2,491 个政府门户，62% 可抓
L2  全文层       21,774 份      「这一条怎么写的」        ← 国家 18,608 + 南京 1,581 + 江苏 1,585
      ─────────────────────────────────────────────
      核验层      119,640 条条文 「你引的这一条站不站得住」← C1–C5，全部回原文核

它做的事：你问一个政策问题，或者贴一段稿子。系统从三层数据里找依据，让模型作答， 再用一层不调用模型的确定性规则逐条核对——条号是否越界、引文是否真实、法规是否失效、 名称是否错配、所问法规划界。核不过就降级或拒答。

它不做的事：不给法律意见；不替代权威数据库；不承诺覆盖全国所有地市； 不把「没抓到」说成「没有」。

为什么值得做：这个场合有个共同点——答案错了会有实际后果，而提问的人通常自己发现不了。 一份立项报告引了已经废止的《环境保护法》，读起来完全正常；一个条号写成「第四十二条」而原文只有三十九条， 也完全正常。这两类错误不会报错，只会被评审专家当场指出。

这三行的完成度不一样，这是 v3 最需要说清楚的事。 v2 的时候三者都建立在 8 部法规上， 完成度一致地低。现在第一行到 62%（门户可达率），第二行到 22%（有正文的占比）， 第三行在 v3.1 做到 100%——改动办法是把判据从「查条数表」换成「回原文搜」。 把三个数字放在一张表里，比任何一句「能力很强」都诚实。

0.3 一条链路怎么走

【⓪ 发现】目录层：地域 × 主题 → 清单 + 覆盖度（不调模型）
   │  输出：有哪些文件、各属哪一级、哪一级是空的、为什么空
   ▼
【① 定位】全文层：在 1.86 万份正文里检索（FTS5 + 中文 2-gram）
   │  输出：哪份文件的哪一条、原文片段、文号、发布日期、链接
   ▼
【② 核验】两道闸门（不调模型）
   │  闸门 1（话题级）：检索分数过低 → 判「库里没有这个话题」，不生成
   │  闸门 2（条文级）：C1 条号越界 / C2 引文查不到 / C3 时效违规
   │                     C4 名称错配 / C5 所问法规划界
   ▼
【③ 交付】结论 + 逐条依据 + 时效状态 + 结论强度 + 核验明细

第 ② 段是本项目与「普通 RAG 问答」的差别，也是投入最大的一步。 闸门 2 只做加减和字符串比对，所以结论可解释到「第几条第几项不通过」，也可以写进服务承诺。

0.4 三种交付强度

强度什么时候给用户看到什么
可作答引用的每一条都能在本次检索结果里反查到，且所依据法规现行有效结论 + 逐条依据 + 引用清单
部分作答依据可用但只能算参考（部分条文相关、或只是历史说明）结论 + 明确写出缺什么

没有「置信度偏低但照常回答」这种中间态。三种档位是产品唯一的降级机制。

    • 检索质量变了，这组成绩不能直接搬到新库（§7.5 的旧数字清单）。

第一部分 · 给没有技术背景的读者

1.1 它解决什么问题

规划院接一个项目（比如鹰潭的城市更新），第一件事是弄清这个话题在三级政府各有哪些文件： 鹰潭市的、江西省的、国务院和部委的，可能还要带历史文化保护。

现状是在四到六个政府网站之间翻。翻的过程中有三件事会出错：

  1. 漏。某个市把文件放在「政策解读」栏目里，或者入口叫「文件库」不叫「政策文件」，

    2. 你就找不到。漏掉一份关键文件，整章论证基础不完整。

  2. 旧。政府网站不会撤下失效文件，只在文末写一句「已宣布失效」。

    3. 你复制标题的时候不会注意那行小字。库里实测 702 份文件被源端标了失效， 拿它们当依据，结论是反的——工具说「有依据」，而那份依据已经作废。

  3. 编。让大模型直接回答「某某法第几条怎么规定」，它会给你一个很像的答案。

    4. 条号、数字、期限都可能编，而界面看起来一切正常。

这个产品针对这三件事，分别对应三层数据和一道核验。

1.2 四种用法

你想干的事怎么用你得到什么
立项前查清单输入地域 + 主题一份按级别分组的文件清单 + 哪一级缺、为什么缺
查一条具体规定直接提问（或输关键词）条号 + 原文 + 出处链接 + 时效状态
核对一段稿子贴进来（默认纯规则，不外发）引用清单 + 问题列表 + 漏引候选
只想看原文只做检索，不要结论命中片段 + 文件链接，自己读

第四种是刻意留的最低形态。模型挂了、没有 key、断网，前三种都做不了，第四种还能用—— 因为它只依赖 SQLite 里的数据和自己的索引。

1.3 一条结果怎么读

结论：怀化市扬尘污染防治的统一监督管理由生态环境主管部门负责。
       ✓ 可作答

依据 1  《怀化市扬尘污染防治条例》第五条
        原文：「…生态环境主管部门对扬尘污染防治实施统一监督管理…」
        时效：现行有效    链接：http://…（点击回源）
        C1 条号 ✓（该条例共 34 条）  C2 引文 ✓  C3 时效 ✓  C4 名称 ✓  C5 范围 ✓

核验说明：本次 5 项检查全部执行。库内该条例条数表已建、时效台账已确认。

四个地方要养成看：

  1. 结论强度（✓ / ! / ✕）——不是装饰，它决定了你敢不敢把这个结论写进稿子。
  2. 时效——如果不是「现行有效」，而是「未知」，说明没人确认过，不能当现行依据。
  3. C1–C5 那行——凡是有「未核」的，说明这项检查没做成，结论强度会自动降一级。
  4. 链接——每一条都必须能点回原页面。点不开的链接等于没有依据。

词大白话

2.2.1 为什么法律名录只有名字也值钱

规划师最常引的法律是《城乡规划法》《土地管理法》《建筑法》。这些法律正文不在库—— flk.npc.gov.cn 整站 /law-search/ 被 CWAP WAF 拦死（307 自跳，需执行 JS 拿会话）， 零依赖拿不下来。gov.cn 政策库只收国务院和部门文件，不收人大立法。

但「在不在现行名录」这个信息本身就能拦一类错误。一个实测例子：

查《环境保护法》→ 不在 308 条的现行目录里。不是漏抓——2026 年《生态环境法典》通过后它已被替代。

而地方目录里正有多个区县在发「关于修改涉及生态环境法典规范性文件的决定」。两件事互相印证。

这个例子说明：「这部法还在不在」和「这部法怎么写的」是两个独立的问题， 前者只需要名录，后者才需要条文。 名录便宜、稳定、可穷尽；条文贵、易变、难获取。 先做便宜的那个，是这一层存在的全部理由。

2.2.2 目录层的三个质量硬伤

库大了不等于库好用了。三个必须同时说出来的数字：

指标实测后果
无文号75.1%（50,076/66,692）效力级别只能靠标题后缀猜（「…办法」→ 规章，「…通知」→ 规范性文件），猜错就排错级
无日期10.4%（6,953/66,692）新旧排序失效，读者不知道这是 2026 年的还是 2016 年的
未来日期87 条，最大 2099-11-20日期解析的脏数据，会把它们排到最前面

为什么是这三个字段：因为它们是列表页上「本来就没有」的东西。政府站的列表页通常只给标题， 日期有时给，文号几乎不给——文号在正文的红头部分。所以 75.1% 的缺失不是抓错了，是列表页上没有。

出路只有一条：抓正文，从正文里抽。gov_full.py 那条链路已经证明可行（18,608 份的成功率 98.4%）， 只是还没接到地方站上。这也是为什么 FR-03（装配）在 v3 里被提成唯一 P0 阻塞项—— 它同时解决条数表、时效台账和文号缺失三个问题。

2.2.3 「有正文」只有 25.5%

85,300 条记录里，能直接引用的 21,774 条，占 25.5%。剩下 74% 是「我知道这份文件存在」。

这不是缺陷，是分工，但必须在界面上分开显示。混在一起显示会出现一个很糟的用法： 用户搜到一条目录，看到标题正好对，就当成依据引用了——而他其实没读过那份文件一个字。 所以界面上每条目录都必须有 仅目录 徽标，并且写明「引用前请回源」。

2.3 工作流：六步，三处在人手里

这一节回答一个问题：这东西能不能按人的工作方式走完一件事。四小节按使用者打开它 以后的顺序排：先说交付形态（装在哪、好不好用、能不能放心用），再说六步流程， 最后两节说核验——判据怎么从「查表」改成「查原文」，以及为什么核验必须排在撰写之后。

真正要回答的是三个问题，一条都不能靠「技术上可行」糊过去：

问题判据现在的答案
好不好用一个问题到可用产物，要不要人教一次完整流程约 45 秒（拆解 13 + 取证 0.6 + 撰写 30），六步全部可见，不需要培训
实不实用真实需求能不能闭环见下节：南京老门西那一问，产出 9 条依据、4 条缺口、6 条动作建议
能不能放心用每条结论能不能自己验有正文的引注回原文逐条核对，只有目录的标明「未核内容」，两档分开显示

二 · 工作流：六步，三处在人手里

原来的产品是「问一句 → 给 8 条 → 生成一段回答」。这个形态在问单个条文时成立， 在真实工作里不成立。

原因不是检索不准。拿「做南京老门西历史文化街区的城市更新」去问，规划师脑子里的 动作是分层的：先看南京自己有什么规定（条例、办法、专项规划），再看江苏省的 上位约束，再看国家的条例和部委红线，最后看别的城市同类街区怎么做的。这五层不是 检索出来的，是职业经验里长出来的。而原来的检索把这句话当成一个查询串，返回 8 个 块——用户永远不知道另外那十几份文件存在。

所以流程改成六步，三处在人手里：

谁做什么为什么不能全交给机器
1人说出需求，可以模糊需求本来就模糊，要求人说清楚是产品在偷懒
2机器拆成取证方向模型知道分层体系，但不知道这个项目的具体处境
3机器按方向找文件数量不设上限，改设证据强度
4人确认用哪些「哪些文件算相关」是判断，不是检索
5机器写结论、缺口、动作建议结论要能落到「办什么事、找谁、拿哪条去说」
6双方留痕用户的勾选行为本身就是标注

第 2 步：拆解出的不是查询，是取证方向

输出的每一条指令包含四样东西：查哪个范围（南京市 / 江苏省 / 国家 / 不限）、 找哪一类文件（法规 / 规划 / 政策 / 案例 / 标准）、为什么必须有它、 用哪些词去撞标题。

第四项是最容易做错的地方。文件库只有标题，没有正文，所以给的关键词必须是 会出现在文件名里的词：

  • 对：「历史文化名城保护」「历史文化街区」「防止大拆大建」
  • 错：「老门西更新政策」「有哪些规定」「南京老门西的历史文化街区更新需要什么文件」

模型第一次跑就给了「老门西保护规划」这种带项目名的词，标题里永远不会有。所以除了 提示词约束，代码里还做了一层领域词表切分，切出来的词和原词一起进检索：

  • 「历史文化名城名镇名村保护条例」→ 历史文化名城名镇名村 + 历史文化名城 + 名镇名村
  • 「城市更新促进条例」→ 城市更新

这一步有两个坑，都踩过。

一是不切：省级法规方向返回 0 条。

二是切了，但只留最长的那个。「历史文化名城名镇名村」在 66,692 条地方目录里一次都 不出现，照样 0 条。所以长词里含着的短词必须一起吐出来。补完之后 4 条才出来—— 省政府关于同意将宿迁、盐城、连云港列为江苏省历史文化名城的批复，和公布第九批 名镇名村的通知。

这 4 条不是省级条例，是批复和通知。它们说明的事实是「江苏省有省级名城名录，但没有 公开的省级保护条例可引」。这句话比 0 条有用得多，也直接进了报告的缺口段。

第 3 步：数量改成阈值

旧版 search(question, top_k=8)，无论问什么都只给 8 条。新版不设数量上限， 每条指令留一个天花板（40），超出的不删除，标成「还有 N 条」，可展开。

替代数量的东西是证据强度，只有两档：

档判据
直接命中命中模型排在前两位的词，或命中任何 5 字以上的专业词
同类相关只命中其它词

不设「弱相关」这一档，因为弱相关基本等于不相关，混在列表里只会浪费人的注意力。 只命中「办法 / 通知 / 规定 / 规划 / 试点 / 方案」这类泛词、不含任何主题词的， 直接丢掉——南京市碳达峰试点方案命中「试点」，它跟历史文化街区没关系。

为什么要两条判据。 只看位置（前两位）不够：切分出来的短词排在索引 3、4 上， 永远进不了前两位，于是省级法规和同类案例两层 22 条候选全部落成「同类相关」， 界面上一片灰，用户以为库里没东西。只看长度也不够：「城市更新」四个字太宽， 可它排在模型第一位时，那正是这条指令要找的东西。

5 字这条线分的是专业词和大词：历史文化街区(6)、历史文化名城(6)、防止大拆大建(6)、 控制性详细规划(7) 够具体，撞上就是冲着这件事来的；城市更新(4)、历史地段(4)、 老旧小区(4) 太宽，只能靠位置。

改完的实测：省级法规 0 → 4（3 条直接命中），同类案例 0 → 18（15 条直接命中）， 本地政策 6 条全部直接命中，其中《内秦淮河历史风貌区保护规划修编》就在老门西旁边。

顺带一件事：同模板批量文件要折叠。

国家法规方向一次返回 57 条，其中 46 条是「国务院关于同意将 X 列为国家历史文化名城 的批复」——同一句话换了 46 个地名。不折叠的话，前 19 屏全是这一句，用户滑不到 《历史文化名城名镇名村保护条例》。

折叠规则：标题按模板归一（同意将*列为、公布第*批、(年份区间)），同模板 ≥3 条时 只留分最高的一条，其余计数挂在「另有 N 条同模板文件」上。57 → 12 条，信息没丢。

界面上的标签也跟着改了。 「直接命中」原来标在每一条上，现在四层全命中，标了等于 没标。改成标在方向头上（「直接命中 6 份，其余为同类」），每条上只给落选的那些标 一个灰色的「同类」。一处汇总代替 57 个重复标签。

第 3 步还有个硬约束：两个通道不能混

层级走哪为什么
本地 / 省级catalog.db 的 items（66,xxx 条元信息）多数只有标题、文号、链接
国家catalog.db 的 fulltext（国家 18,608 份）有正文，能引到条
南京 / 江苏同一张 fulltext（3,166 份，key 前缀 lf）有正文，能引到条；查国家层时必须排除它们

items 表里 admin_level='国家' 只有 330 条——国务院政策文件库当时只把一部分清单 写进了 items。拿「国家」去 items 查，会得到「只找到 1 条」的假象，而界面上看起来 像「库里没有」。这个坑是实测踩到的：第一次跑「国家政策」方向只返回 1 条， 《历史文化名城名镇名村保护条例》没出现，而它明明在库里、有全文、能逐条引。

第 4 步：勾选就是标注

人在这里做的事是三件：勾上要用的、勾掉不要的、补一个方向。这三件都不需要额外 说明理由，行为本身就是数据：

信号含义用来改什么
drop 系统推荐了但没勾召回不准，关键词太宽收窄这个词，或降它的权重
add 系统没勾但勾了召回不全，或分档判错放宽这个词，或调分档规则
task_empty 整个方向 0 条数据没有，或词不对补数据，或换词

一个方向给 20 条候选、用户只勾 3 条，那 17 条为什么被丢，比任何离线评测都真实。

默认勾选也不是「全选」或「按分数取前 N」。规则是： 每个方向先拿 1 条直接命中的（不管有没有正文），再补 2 条有正文的。 只按有正文选，会漏掉《南京历史文化名城保护条例》这种直接命中却只抓到目录的核心 依据；只按直接命中选，会全是只有标题的条目。

第 5 步：报告的四段结构

不是一段流畅的散文，是四段固定内容：

段回答什么为什么单独成段
结论这事能不能做、按什么名义做使用者第一眼要的是判断，不是资料
依据按效力从高到低，每条带引注有正文的引到条、引原话；只有目录的只写文号日期
缺口哪些方向没找到依据最有用的部分：只给已有的，用户仍然不知道边界在哪
下一步动作级建议：办什么事、找谁、拿哪条去说「加强学习」「高度重视」不算建议

「缺口」这一段的实际效果，看南京那一问的输出：

市级层面未获取《南京历史文化名城保护条例》正文，无法确认其对老门西门西街区的

差异化管控要求（如允许更新方式、功能兼容条件、审批豁免情形等），报审前需调阅

正式文本并核验条款效力。

市级未检索到针对「老门西」专项编制的历史文化街区保护规划（仅有总统府街区规划），

该街区法定保护边界、核心/建设控制地带划分、建筑分类管控要求等关键空间管控依据缺失，

直接影响更新方案合规性判定。

这两句话不是「没找到」，是「没找到意味着什么」。这才是规划师真正需要从工具里得到的。

python app/trace.py --report 按「哪条指令最常空」「哪类文件最常被丢」聚合。

三 · 核验层：判据从「查表」改回「查原文」

上一版把 kb.db 的 980 MB 当成代价，也把核验层的问题理解成「表不够多」。这一版 把判据换了一遍，四项检查的覆盖面全变：

检查上一版判据覆盖这一版判据覆盖
C1 条号越界查条数表（8 部）0.04%回原文搜「第X条」+ 条级索引100%
C2 引文查不到查全文22.1%查全文（不变）22.1%
C3 时效违规人工台账 + 源端标记3.8%全量失效台账（四态）100%
C4 名称错配8 部精确 + 全库模糊8 部全库标题匹配100%
C5 所问法规划界规则100%规则（不变）100%

C1 能到 100%，靠的不是把条数表建满，是把「不分条」也做成一条判据。

实测：21,774 份里只有 2,198 份（10.1%）有条款结构，切出 119,640 条条文；其余 19,576 份（89.9%）全篇不分条——意见、通知、批复、函，本来就没有「第X条」。 对后者，任何条号引用都是编造，这个判据比条数表更硬：条数表只能说「没有第 108 条」， 这里能说「这份文件根本没有条」。

失效台账做成了全量四态。 21,774 行，一行一份：

状态份数界面怎么写
repealed 已废止795（源端标记 702 + 后代文件正文点名废止）「已失效，由《XXX》宣布废止」
superseded 旧版本29「这是旧版本，已被《XXX》（2025-03-24）取代，引注应改用新版」
no_signal 未见废止记录20,950「未见废止记录：全库 21,774 份正文均未点名废止该文件」

还有 66,692 条目录层文件判 unknown（只有标题、没有正文），界面上如实写「时效需回源确认」。

废止关系的来源是把 21,774 份正文扫一遍，抽出 2,933 条废止/修订关系边， 其中 466 条在库内匹配到了被点名的文件。

抽取按句子语法判宾语，不按「最近的两个词」判。 这条规则是被真实误判逼出来的： 「根据《土地管理法实施条例》有关规定，经省人民政府研究，决定废止《江苏省征地补偿安置 争议协调裁决办法》」——按距离判会把《土地管理法实施条例》这部核心上位法标成失效。 现在按中文废止句的四种语序认宾语，加三道拦截（依据词 / 模态词 / 代词指代）。 另外两条硬规则：单文件修改决定不判时效（它废的是旧版，库里同名的是新版）； 同名法规有新版入库、旧版直接判 superseded（同名法规不可能同时有效）。

「未见废止记录」不是「未知」，是一个有依据的判断——依据是把全库都读过了。 写 unknown，用户会当成「大概有效」；写「未见废止记录」，用户知道这是我们查过的结论。

四 · 核验在撰写之后，但不是自证

核验分三档，界面用三种颜色：

档含义界面
verified有正文，条号/引文/名称都对得上绿色，可照抄
unverifiable只有目录条目，能确认文件存在，不能确认内容灰色，标「未核内容」
failed有正文，但条号不存在 / 引文查不到 / 引错文件红色，必须改

**unverifiable 不参与降级。** 它是数据的边界，不是内容的错误。南京这一问里， 15 处引注中 6 处是 unverifiable——意味着南京和江苏的文件我们只拿到了标题。 把这种情况说成「报告有问题」是错的，说成「这几份文件要回源确认」才对。

强度按错的比例定，不按「有没有错」定。15 处里 1 处引文被改写，和 15 处里 8 处 条号不存在，对使用者是完全不同的两件事：前者改那一句就行，后者整篇不能用。

核验器自己也会错，这一版修了五个

  1. 引文按句首配对 → 按就近配对。 一句话里常有「以『留改拆』为主」这类术语引号，

    2. 它排在前面，于是一条逐字照抄的引文被配给了一个两字术语，C2 拿它去原文搜， 必然判「引文查不到」。改成取「这条引注之前、同句之内」最近的一个引号。

  2. 标题模糊匹配没有门槛。 kb.db 里有一份标题就叫「通知」的脏记录，任何以

    3. 「…的通知」结尾的目录标题都会命中它，于是「南京市城市更新办法」被判成「有正文」， 核验时又报「实际是《通知》」。一个脏标题能让整份报告的核验结论失真。 加长度和覆盖率约束后消失。

  3. 逐句回查算全篇。 结论和「下一步」本来就是判断和动作，该用自己的话写；

    4. 拿它们算「有出处比例」会稳定得到 0.3，然后天天报警，最后没人看这个指标。 现在只算「依据」段。

  4. C4 只认《》，不认〈〉。 引一份「公告的标题里又套了一份文件名」时，模型写

    5. 《…发布〈国土空间历史文化遗产保护规划编制指南〉等2项行业标准的公告》—— 内层用 〈〉 是对的，而 C4 归一化只剥《》（），于是名称完全正确的引注被判「名称 对不上」。这是核验器自己制造的假阳性，比漏报更坏：它会让用户从此不信核验结论。 归一化补齐 〈〉、[]、【】 后消失。

  5. 聚合保留了「第一次」的明细。 同一份文件同一处引用出现三次时，聚合只记次数；

    6. 如果第二次才判失败，红条上挂的仍是第一次「五行全绿」的明细——界面说它错了， 点开却找不到错在哪。改成失败那次覆盖明细。 顺带修了强度口径：按「错了几条」定，不按「错了几次」定。同一句话引三次、三次 都错，要改的是一句话，不是三处；拿出现次数当分母会把「改一句」说成「整篇不能用」。

还有一处不在核验器里，在提示词里

三条 C2 失败全是同一个模式：模型把概括写进引号。原文是「严格控制大规模拆除」， 它写成「不大规模拆除、不大规模增建、不大规模搬迁」——读起来更像总结，但它加了 引号，就成了伪造的引文。

原来的提示词只说「原话照抄不改写」，不够。改成分两步，并给一条出口：

引号里必须逐字照抄，不许概括、不许合并、不许改标点。做不到就别加引号，

用自己的话写——没有引号不算引文，核验也不会拿它去比对。

关键是那条出口。只堵不疏，模型要么硬编引文，要么不写依据；给了「不用引号也能写」 这条路，它才会在没把握的时候退回自己的话。

实测效果（同一句问题）：改前 9 处引注里 3 处是假引文、判「需修正」；改后 4 处引注 全部逐字可核、判「部分可核」。引注数少了，但每一处都能照着抄进文件里。

一个还没解决的

「依据密度」这个指标的合理下限还不清楚。南京那一问同一句问题连跑五次，依据段分别是 50%、55%、70%、33%、43%——同一个模型、同一份资料、同一个提示词，波动 37 个百分点。 条文类问题（「条例第三十三条讲什么」）能稳定到 90% 以上。

所以它现在只能当预警用：低于 60% 落一条 low_trace，不直接降级结论。 一个波动这么大的指标，用它判合格线，等于用噪声当裁判。

要让它能用，得先回答一个更小的问题：「依据段里一句话有没有出处」这个判定本身 可靠吗？ 现在的做法是拿 10 字窗口去原文里搜，搜到就算有。这会把「把三条并成一句 写」判成无出处——而那恰恰是好的写法。在没解决这件事之前，不加权重、不设硬门槛。

2.4 两道闸门（本项目的核心设计）

2.4.1 为什么必须是两道

因为它们防的不是同一种错。

  • 闸门 1（话题级） 防「答非所问」：库里根本没有这个话题，模型硬答。

    • 判据是「实体落地」与「标题吻合」——不是分数阈值，分数跨查询不可比。

  • 闸门 2（条文级） 防「答得像但引错了」：话题对、文件对、条号错。

    • 判据是字符串比对和原文查找。

只有闸门 1，会漏掉「引了库内另一部同名法规」这类错（它的检索分数很高）； 只有闸门 2，会在「库里完全没有这个话题」时无从下手——检索出来的东西本身就不该被引。

闸门 1 不通过时不生成。 这不是省一次模型调用，是这条产品线的核心主张： 库答不了的时候，「答不了」本身就是交付物。上一版只是显示「闸门 1 不通过」然后照样生成， 那道闸门就形同虚设。

为什么用 2-gram 不用 trigram：FTS5 的 trigram 要求查询 ≥3 字符，「征收」「补偿」这类两字词直接失效， 而这两个词恰好是政策检索里最高频的。所以自己切 2-gram，查询侧同样切，用 unicode61 索引。

2.7 十条判断

这一轮把库从 4.19 万条扩到 85,300 条之后，值得记下来的判断：

  1. 扩容解决的是「有没有」，不是「准不准」——但「准不准」不一定要靠表。 抓了 1.86 万份之后，

    2. 我以为要先建 1.86 万张条数表才能核；实际只要把判据从「查表」换成「查原文」，覆盖率当天就从 0.04% 变成 100%。数据补上之后，旧判据往往已经过时了，只是没人回头看它。

  2. 一个产品里最危险的状态不是「错了」，是「错了但看起来正常」。 编造的条号和真实的条号在界面上长得一样；

    3. 未抓取的省和没有文件的省在清单上长得一样。这两个「一样」是本产品存在的全部理由。

  3. 「未知」是第一等公民，「未见」比「未知」更有用。 96% 的文件没有被任何文件点名废止，

    4. 这件事该写成「未见废止记录」，不是「未知」——前者是我们查过的结论，后者是我们没查。 75.1% 的条目没有文号，同理：界面要写「列表页未给文号」，不能留空。

  4. 能被机器判定的部分要尽量大。 C1–C5 现在全部可判定，但它们的判定价值不一样：

    5. 查索引和比字符串是可复现的，模型判断不是。所以核验只用前一种，一种都不留给模型发挥。

  5. 抓取的天花板不在技术，在经济。 946 个站抓不到，逐个挖接口是 20–40 分钟一站，上限 40 小时。

    6. 而上海一个接口就是 10,235 条。先找大站，别按地域顺序啃。

  6. 目录的完整性和全文的可引用性是一次权衡。 66,692 条目录 vs 18,608 份全文。

    7. 全抓正文是 5,000 万字 + 一张维护不了的台账。按专题装配 50–80 份才是可控的。

  7. 规则层的价值随库增大而上升，模型的价值随库增大而下降。 库越大，模型越容易「看着像」，

    8. 而规则不受影响——它只查表。

  8. 评测集的偏斜比模型能力更影响结论。 66 题全测核验层，等于没测发现层。
  9. 人工确认是唯一的真成本，人力是唯一的瓶颈。 token 成本 10 人团队月 ¥16.2，可以忽略。
  10. 不该承诺的别承诺。 不说「覆盖全国」，不说「全库时效已核」，不说「法律条文齐备」。说清楚的缺口比藏起来的缺口安全。

3.5 这一轮踩的坑

抓取侧（都会导致整站归零，且看起来像「这个站没有文件」）

  1. title="" 空属性吞掉整条标题——绍兴嵊州 97 个链接标题全为空，漏斗在「长度 ≥ 8」归零。
  2. _HREF_OK 只认 .html/.shtml，排除掉所有无后缀详情页（塔城 /zfxxgk/zc/gfxwj/…、淮南 ?catId=…）。
  3. 「政府公报」与政策文件库同权重，还因 URL 含 zfgb 加分，挤掉真入口（邢台、铜川、东营、开封整站抓成公报期号列表）。
  4. find_next 在 index.html（页码 0）时返回自身，翻页自环——浙江 20 页只拿到 38 条。
  5. meta refresh 空壳（陕西 311 字符）、iframe 里的列表（山东外层只有 11 个导航）都要跟。
  6. 超时写死 60 秒是因为江苏 jpage 单页要 19.8 秒，但县级 1,775 站会被拖到几小时。改默认 20 秒，jpage 单独 60。
  7. 分页参数无效时每页都返回首页——必须早停（「这一页没有新条目就收手」）。

接口侧（这些是「接口能调通但不给数据」）

  1. 上海 pageNum 不报错，但永远返回第 1 页；必须用 pageNo。
  2. p.so-gov.cn 的 pageSize 被钉死 20，翻到约 30 页后静默重置回第 1 页，startDateStr/C1 只改 totalHits 不改结果集——单查询上限 600 条，做不成目录。
  3. 福建真正的入口在 SaaS 底下的 TRS WAS5：/was5/web/search?channelid=N&templet=docs.jsp&searchword= 直接返回 JSON，自带 fileno 发文字号。按文号前缀分片（闽政 7,571 → 闽政办 2,846 → 政府令），147 秒取回 6,340 条。
  4. channelid 只能从站点自己页面的 <input name="channelid"> 取，猜不出来；识别到不等于能用——青海的 WAS5 对匿名请求回 TRS 错误页。

解析侧

  1. 老页面正文不到 800 字符时会被截成 34 字（短批复），且长得像「抓取成功」。
  2. 中文占比 0.25 的线太高——8,000 字的批复大量条款编号，占比只有 0.21，被判垃圾。降到 0.12。
  3. Word 导出的 <td> 能到上千字符，正则 <[^>]{1,400}> 剥不掉，CSS 漏进正文。改成 <[a-zA-Z/!][^<>]*> 并先剥 style/class，同一份从 34 字回到 21,440 字。
  4. 精确容器（id="UCAP-CONTENT"）不要再做密度校验——Word 页面每个字包在几百字符的 <span style> 里，会误杀一半。

数据侧

  1. 福建首抓 6,340 条里 1,293 条是人事任免、表彰、政协提案答复函——都有正规文号，但拿它当政策依据比找不到更糟。过滤放在 save() 一处（_NOISE_TITLE），全库清掉 3,558 条（5.2%）。
  2. 人大网法律目录的 key 必须带序号：《宪法》后跟 5 条《宪法修正案》，只用名称会把 308 压成 293。
  3. 目录检索排序不能只按日期——2-gram OR 召回太宽（查「城市更新」会捞进「城市园林绿化管理办法」），要「完整串命中优先 + 命中 gram 数」两段打分。
