# 卷首 · 一页速览

## 0.1 它是什么：三层数据，一个判断

```
L0  法律名录        308 条      「这部法还在不在」        ← 全国人大《现行有效法律目录》
L1  目录层       66,692 条      「这个方向有哪些文件」    ← 2,491 个政府门户，62% 可抓
L2  全文层       21,774 份      「这一条怎么写的」        ← 国家 18,608 + 南京 1,581 + 江苏 1,585
      ─────────────────────────────────────────────
      核验层      119,640 条条文 「你引的这一条站不站得住」← C1–C5，全部回原文核
```

**它做的事**：你问一个政策问题，或者贴一段稿子。系统从三层数据里找依据，让模型作答，
再用一层**不调用模型**的确定性规则逐条核对——条号是否越界、引文是否真实、法规是否失效、
名称是否错配、所问法规划界。核不过就降级或拒答。

**它不做的事**：不给法律意见；不替代权威数据库；不承诺覆盖全国所有地市；
不把「没抓到」说成「没有」。

**为什么值得做**：这个场合有个共同点——**答案错了会有实际后果，而提问的人通常自己发现不了**。
一份立项报告引了已经废止的《环境保护法》，读起来完全正常；一个条号写成「第四十二条」而原文只有三十九条，
也完全正常。这两类错误不会报错，只会被评审专家当场指出。

## 0.2 三个问题，三个答案

| 用户脑子里的问题 | 谁回答 | 现在能答到什么程度 |
|---|---|---|
| 这个方向有哪些文件？ | 目录层 | 85,300 条记录，覆盖 1,492 个地域；**62% 的门户可达**，其余显式标缺 |
| 这一条具体怎么写的？ | 全文层 | 21,774 份正文可给条号 + 原文片段 + 链接；地方只有**南京和江苏**两市一省补了正文（3,166 条），其余 63,526 条仍只有目录 |
| 我引的这一条对不对？ | 核验层 | 四项在全文层可核（条号/引文/名称/时效），**覆盖 100%**；逐句回查给出依据密度 |

**这三行的完成度不一样，这是 v3 最需要说清楚的事。** v2 的时候三者都建立在 8 部法规上，
完成度一致地低。现在第一行到 62%（门户可达率），第二行到 22%（有正文的占比），
第三行在 v3.1 做到 100%——改动办法是把判据从「查条数表」换成「回原文搜」。
**把三个数字放在一张表里，比任何一句「能力很强」都诚实。**

## 0.3 一条链路怎么走

```
【⓪ 发现】目录层：地域 × 主题 → 清单 + 覆盖度（不调模型）
   │  输出：有哪些文件、各属哪一级、哪一级是空的、为什么空
   ▼
【① 定位】全文层：在 1.86 万份正文里检索（FTS5 + 中文 2-gram）
   │  输出：哪份文件的哪一条、原文片段、文号、发布日期、链接
   ▼
【② 核验】两道闸门（不调模型）
   │  闸门 1（话题级）：检索分数过低 → 判「库里没有这个话题」，不生成
   │  闸门 2（条文级）：C1 条号越界 / C2 引文查不到 / C3 时效违规
   │                     C4 名称错配 / C5 所问法规划界
   ▼
【③ 交付】结论 + 逐条依据 + 时效状态 + 结论强度 + 核验明细
```

第 ② 段是本项目与「普通 RAG 问答」的差别，也是投入最大的一步。
闸门 2 只做加减和字符串比对，所以结论可解释到「第几条第几项不通过」，也可以写进服务承诺。

## 0.4 三种交付强度

| 强度 | 什么时候给 | 用户看到什么 |
|---|---|---|
| **可作答** | 引用的每一条都能在本次检索结果里反查到，且所依据法规现行有效 | 结论 + 逐条依据 + 引用清单 |
| **部分作答** | 依据可用但只能算参考（部分条文相关、或只是历史说明） | 结论 + 明确写出缺什么 |
| **拒答** | 条号越界 / 引文查不到 / 取依据而法规已失效 / 库里没有 | 「本次检索结果中没有能支持该问题的条文」+ 检索到了什么 |

没有「置信度偏低但照常回答」这种中间态。三种档位是产品**唯一**的降级机制。

## 0.5 能信到什么程度

**实测达到的**（66 题，其中 40 题是刻意设计的「库里不可能有答案」的对抗题）：

| 指标 | 实测 |
|---|---|
| 引用可追溯（每条都能在检索结果里反查到） | 100% |
| 真编造（凭空造法名或条号） | 0% |
| 引用废止法规当现行依据（时效违规） | 0 条 |
| 对抗题边界处理正确率 | 40/40 |
| 边界判定字段合规率 | 100% |
| 规则判定与模型自报一致 | 66/66 |
| 闸门 2 规则自检（不调模型） | 11/11 |

**不能信的**：

- **这组成绩的适用边界**。它产生在「模型只看到 8 条召回」的窄上下文上。库扩到 16.7 万块之后，
  检索质量变了，这组成绩**不能直接搬到新库**（§7.5 的旧数字清单）。
- **地方文件的正文**。66,692 条地方目录里，没有一份有正文。要引用必须回源。
- **法律条文**。308 条只有名称和沿革。规划最常引的《城乡规划法》正文仍不在库。
- **时效**。21,774 份全文现在每一份都有确定状态：**已废止 795 份（3.7%）**、
  **旧版本 29 份**、**未见废止记录 20,950 份**。后者的依据是「全库 21,774 份正文都读过，
  没有一份说它失效」——这是一个有依据的判断，不是「未知」。
  **但「未见废止」不等于「一定有效」**，尤其库里只收省政府规章、不收省人大立法。
- **清单的完整性**。38% 的门户抓不到，抓不到的会被明确标出来，但确实缺。
- **没有真实用户验证**。66 题自造，出题人、判分人、被考核对象是同一个人。

# 第一部分 · 给没有技术背景的读者

## 1.1 它解决什么问题

规划院接一个项目（比如鹰潭的城市更新），第一件事是**弄清这个话题在三级政府各有哪些文件**：
鹰潭市的、江西省的、国务院和部委的，可能还要带历史文化保护。

现状是在四到六个政府网站之间翻。翻的过程中有三件事会出错：

1. **漏**。某个市把文件放在「政策解读」栏目里，或者入口叫「文件库」不叫「政策文件」，
   你就找不到。漏掉一份关键文件，整章论证基础不完整。
2. **旧**。政府网站不会撤下失效文件，只在文末写一句「已宣布失效」。
   你复制标题的时候不会注意那行小字。**库里实测 702 份文件被源端标了失效**，
   拿它们当依据，结论是反的——工具说「有依据」，而那份依据已经作废。
3. **编**。让大模型直接回答「某某法第几条怎么规定」，它会给你一个很像的答案。
   条号、数字、期限都可能编，而界面看起来一切正常。

这个产品针对这三件事，分别对应三层数据和一道核验。

## 1.2 四种用法

| 你想干的事 | 怎么用 | 你得到什么 |
|---|---|---|
| 立项前查清单 | 输入地域 + 主题 | 一份按级别分组的文件清单 + 哪一级缺、为什么缺 |
| 查一条具体规定 | 直接提问（或输关键词） | 条号 + 原文 + 出处链接 + 时效状态 |
| 核对一段稿子 | 贴进来（默认纯规则，不外发） | 引用清单 + 问题列表 + 漏引候选 |
| 只想看原文 | 只做检索，不要结论 | 命中片段 + 文件链接，自己读 |

第四种是刻意留的**最低形态**。模型挂了、没有 key、断网，前三种都做不了，第四种还能用——
因为它只依赖 SQLite 里的数据和自己的索引。

## 1.3 一条结果怎么读

```
结论：怀化市扬尘污染防治的统一监督管理由生态环境主管部门负责。
       ✓ 可作答

依据 1  《怀化市扬尘污染防治条例》第五条
        原文：「…生态环境主管部门对扬尘污染防治实施统一监督管理…」
        时效：现行有效    链接：http://…（点击回源）
        C1 条号 ✓（该条例共 34 条）  C2 引文 ✓  C3 时效 ✓  C4 名称 ✓  C5 范围 ✓

核验说明：本次 5 项检查全部执行。库内该条例条数表已建、时效台账已确认。
```

四个地方要养成看：

1. **结论强度**（✓ / ! / ✕）——不是装饰，它决定了你敢不敢把这个结论写进稿子。
2. **时效**——如果不是「现行有效」，而是「未知」，说明没人确认过，不能当现行依据。
3. **C1–C5 那行**——凡是有「未核」的，说明这项检查没做成，结论强度会自动降一级。
4. **链接**——每一条都必须能点回原页面。点不开的链接等于没有依据。

## 1.4 术语速查（大白话）

| 词 | 大白话 |
|---|---|
| 目录层 | 一份「有哪些文件」的花名册。只有名字、文号、日期、链接，没有正文 |
| 全文层 | 真正有正文、能逐条引用的那批文件 |
| 法律名录 | 全国人大公布的「现行有效法律」名单。只有法名，没有法条 |
| 条数表 | 一份文件一共有多少条。有了它才能判断「第八十条」是不是编的 |
| 时效台账 | 一份文件还有没有效的记录。只能人确认，不能机器猜 |
| 闸门 | 一道自动检查。闸门 1 看「这个话题库里有没有」，闸门 2 看「引的这一条对不对」 |
| 核不过 | 检查没通过。核不过就不给结论，或者降级成「部分作答」 |
| 未核 | 这项检查没做成（缺数据）。**未核不是通过** |
| 覆盖度 | 哪一级抓到了、哪一级没抓到。没抓到的必须写出来 |

# 第二部分 · 给 AI 产品经理

## 2.1 系统全貌

```
                    ┌──────────────── 生 成 层 ────────────────┐
   问题/稿件 ──────► │ qwen-plus（提示词 2,863 token，四条硬约束）│ ──► 结论
                    └──────────────────────────────────────────┘
                              ▲                        │
                   检索到的条文（top 8）               │ 模型自报的字段
                              │                        ▼
   三层数据 ──► 检索层 ────────┘        ┌──────── 核 验 层（不调模型）────────┐
   L0 308 条                            │ 闸门 1 话题级 · 闸门 2 五项规定检查  │
   L1 66,692 条 ──► SQLite LIKE         │ C1 条号 / C2 引文 / C3 时效          │
   L2 21,774 份 ──► FTS5 2-gram         │ C4 名称 / C5 划界                    │
                   196,343 块           └──────────────────────────────────────┘
                                                         │
                                            ┌────────────▼────────────┐
                                            │ 三张表：条数 / 台账 / 名称 │
                                            └─────────────────────────┘
```

**这张图最该记住的是右边那两列的分工。** 左边是概率的、会变的、换模型就换脾气的；
右边是确定的、可复现的、断网也能跑的。产品的可信度来自右边，不来自左边。

## 2.2 数据资产：三层，别再混着说

v2 里「数据」是一句话：8 部法规、419 个检索单元。现在必须分三层说，因为**三层能回答的问题、
可信度、维护成本完全不同**。

| | L0 法律名录 | L1 目录层 | L2 全文层 |
|---|---|---|---|
| 内容 | 全国人大《现行有效法律目录》 | 政府门户的文件清单 | 政策文件正文 |
| 规模 | 308 条 | 66,692 条（地方，含 330 条国家级）+ 18,916 条（国家级清单） | 21,774 份 / 8,520 万字 |
| 字段 | 名称、序号、法律沿革 | 标题、文号、机关、日期、级别、地域、链接 | 全文 + 元信息 + 时效原文 |
| 能回答 | 这部法还在不在 | 有哪些文件、哪一级有 | 这一条怎么写的 |
| **不能回答** | 法条怎么写的 | 一句话怎么规定的 | 全国还有哪些你没抓到 |
| 更新方式 | 人大网发新版 PDF 就重抓 | 每日增量，逐站适配 | 一次性抓取 + 增量 |
| 数据文件 | `data/law/现行有效法律目录.csv` | `data/catalog.db` · `items` | `data/fulltext/` + `data/kb.db` |

### 2.2.1 为什么法律名录只有名字也值钱

规划师最常引的法律是《城乡规划法》《土地管理法》《建筑法》。这些法律**正文不在库**——
`flk.npc.gov.cn` 整站 `/law-search/` 被 CWAP WAF 拦死（307 自跳，需执行 JS 拿会话），
零依赖拿不下来。gov.cn 政策库只收国务院和部门文件，不收人大立法。

但「在不在现行名录」这个信息本身就能拦一类错误。一个实测例子：

> 查《环境保护法》→ 不在 308 条的现行目录里。不是漏抓——2026 年《生态环境法典》通过后它已被替代。
> 而地方目录里正有多个区县在发「关于修改涉及生态环境法典规范性文件的决定」。两件事互相印证。

这个例子说明：**「这部法还在不在」和「这部法怎么写的」是两个独立的问题，
前者只需要名录，后者才需要条文。** 名录便宜、稳定、可穷尽；条文贵、易变、难获取。
先做便宜的那个，是这一层存在的全部理由。

### 2.2.2 目录层的三个质量硬伤

库大了不等于库好用了。三个必须同时说出来的数字：

| 指标 | 实测 | 后果 |
|---|---|---|
| 无文号 | **75.1%**（50,076/66,692） | 效力级别只能靠标题后缀猜（「…办法」→ 规章，「…通知」→ 规范性文件），猜错就排错级 |
| 无日期 | **10.4%**（6,953/66,692） | 新旧排序失效，读者不知道这是 2026 年的还是 2016 年的 |
| 未来日期 | **87 条**，最大 2099-11-20 | 日期解析的脏数据，会把它们排到最前面 |

**为什么是这三个字段**：因为它们是列表页上「本来就没有」的东西。政府站的列表页通常只给标题，
日期有时给，文号几乎不给——文号在正文的红头部分。所以 75.1% 的缺失不是抓错了，是**列表页上没有**。

**出路只有一条**：抓正文，从正文里抽。`gov_full.py` 那条链路已经证明可行（18,608 份的成功率 98.4%），
只是还没接到地方站上。这也是为什么 FR-03（装配）在 v3 里被提成唯一 P0 阻塞项——
它同时解决条数表、时效台账和文号缺失三个问题。

### 2.2.3 「有正文」只有 25.5%

85,300 条记录里，能直接引用的 21,774 条，占 25.5%。剩下 74% 是「我知道这份文件存在」。

**这不是缺陷，是分工**，但必须在界面上分开显示。混在一起显示会出现一个很糟的用法：
用户搜到一条目录，看到标题正好对，就当成依据引用了——而他其实没读过那份文件一个字。
所以界面上每条目录都必须有 `仅目录` 徽标，并且写明「引用前请回源」。

## 2.3 工作流：六步，三处在人手里

这一节回答一个问题：这东西能不能按人的工作方式走完一件事。四小节按使用者打开它
以后的顺序排：先说交付形态（装在哪、好不好用、能不能放心用），再说六步流程，
最后两节说核验——判据怎么从「查表」改成「查原文」，以及为什么核验必须排在撰写之后。

### 一 · 交付形态不是问题，好不好用才是

上一版把「`kb.db` 980 MB，MVP 拷不走了」当成一个代价，还分了轻包/全包。这是把
部署细节当成了产品问题。

**体积只有一个后果：装在哪。** 三种装法都是现成的，不需要产品层面做取舍：

| 装法 | 命令 | 适合 |
|---|---|---|
| 本机 | `python app/server.py` | 现在就打开用 |
| 容器 | `docker compose up` | 给团队用，数据不外流 |
| 只读副本 | 拷 `kb.db` + `catalog.db`（约 1.0 GB） | 断网环境、阅卷现场 |

真正要回答的是三个问题，一条都不能靠「技术上可行」糊过去：

| 问题 | 判据 | 现在的答案 |
|---|---|---|
| **好不好用** | 一个问题到可用产物，要不要人教 | 一次完整流程约 45 秒（拆解 13 + 取证 0.6 + 撰写 30），六步全部可见，不需要培训 |
| **实不实用** | 真实需求能不能闭环 | 见下节：南京老门西那一问，产出 9 条依据、4 条缺口、6 条动作建议 |
| **能不能放心用** | 每条结论能不能自己验 | 有正文的引注回原文逐条核对，只有目录的标明「未核内容」，两档分开显示 |

### 二 · 工作流：六步，三处在人手里

原来的产品是「问一句 → 给 8 条 → 生成一段回答」。这个形态在问单个条文时成立，
在真实工作里不成立。

原因不是检索不准。拿「做南京老门西历史文化街区的城市更新」去问，规划师脑子里的
动作是**分层的**：先看南京自己有什么规定（条例、办法、专项规划），再看江苏省的
上位约束，再看国家的条例和部委红线，最后看别的城市同类街区怎么做的。这五层不是
检索出来的，是职业经验里长出来的。而原来的检索把这句话当成一个查询串，返回 8 个
块——用户永远不知道另外那十几份文件存在。

所以流程改成六步，三处在人手里：

| | 谁 | 做什么 | 为什么不能全交给机器 |
|---|---|---|---|
| 1 | 人 | 说出需求，可以模糊 | 需求本来就模糊，要求人说清楚是产品在偷懒 |
| 2 | 机器 | 拆成取证方向 | 模型知道分层体系，但不知道这个项目的具体处境 |
| 3 | 机器 | 按方向找文件 | 数量不设上限，改设证据强度 |
| 4 | **人** | 确认用哪些 | 「哪些文件算相关」是判断，不是检索 |
| 5 | 机器 | 写结论、缺口、动作建议 | 结论要能落到「办什么事、找谁、拿哪条去说」 |
| 6 | 双方 | 留痕 | 用户的勾选行为本身就是标注 |

#### 第 2 步：拆解出的不是查询，是取证方向

输出的每一条指令包含四样东西：**查哪个范围**（南京市 / 江苏省 / 国家 / 不限）、
**找哪一类文件**（法规 / 规划 / 政策 / 案例 / 标准）、**为什么必须有它**、
**用哪些词去撞标题**。

第四项是最容易做错的地方。文件库只有标题，没有正文，所以给的关键词必须是
**会出现在文件名里的词**：

- 对：「历史文化名城保护」「历史文化街区」「防止大拆大建」
- 错：「老门西更新政策」「有哪些规定」「南京老门西的历史文化街区更新需要什么文件」

模型第一次跑就给了「老门西保护规划」这种带项目名的词，标题里永远不会有。所以除了
提示词约束，代码里还做了一层**领域词表切分**，切出来的词和原词一起进检索：

- 「历史文化名城名镇名村保护条例」→ 历史文化名城名镇名村 + 历史文化名城 + 名镇名村
- 「城市更新促进条例」→ 城市更新

**这一步有两个坑，都踩过。**

一是不切：省级法规方向返回 0 条。

二是切了，但只留最长的那个。「历史文化名城名镇名村」在 66,692 条地方目录里一次都
不出现，照样 0 条。所以长词里含着的短词必须一起吐出来。补完之后 4 条才出来——
省政府关于同意将宿迁、盐城、连云港列为江苏省历史文化名城的批复，和公布第九批
名镇名村的通知。

这 4 条不是省级条例，是批复和通知。它们说明的事实是「江苏省有省级名城名录，但没有
公开的省级保护条例可引」。这句话比 0 条有用得多，也直接进了报告的缺口段。

#### 第 3 步：数量改成阈值

旧版 `search(question, top_k=8)`，无论问什么都只给 8 条。新版**不设数量上限**，
每条指令留一个天花板（40），超出的不删除，标成「还有 N 条」，可展开。

替代数量的东西是**证据强度**，只有两档：

| 档 | 判据 |
|---|---|
| 直接命中 | 命中模型排在前两位的词，**或**命中任何 5 字以上的专业词 |
| 同类相关 | 只命中其它词 |

不设「弱相关」这一档，因为弱相关基本等于不相关，混在列表里只会浪费人的注意力。
只命中「办法 / 通知 / 规定 / 规划 / 试点 / 方案」这类泛词、不含任何主题词的，
直接丢掉——南京市碳达峰试点方案命中「试点」，它跟历史文化街区没关系。

**为什么要两条判据。** 只看位置（前两位）不够：切分出来的短词排在索引 3、4 上，
永远进不了前两位，于是省级法规和同类案例两层 22 条候选全部落成「同类相关」，
界面上一片灰，用户以为库里没东西。只看长度也不够：「城市更新」四个字太宽，
可它排在模型第一位时，那正是这条指令要找的东西。

5 字这条线分的是专业词和大词：历史文化街区(6)、历史文化名城(6)、防止大拆大建(6)、
控制性详细规划(7) 够具体，撞上就是冲着这件事来的；城市更新(4)、历史地段(4)、
老旧小区(4) 太宽，只能靠位置。

改完的实测：省级法规 0 → 4（3 条直接命中），同类案例 0 → 18（15 条直接命中），
本地政策 6 条全部直接命中，其中《内秦淮河历史风貌区保护规划修编》就在老门西旁边。

**顺带一件事：同模板批量文件要折叠。**

国家法规方向一次返回 57 条，其中 46 条是「国务院关于同意将 X 列为国家历史文化名城
的批复」——同一句话换了 46 个地名。不折叠的话，前 19 屏全是这一句，用户滑不到
《历史文化名城名镇名村保护条例》。

折叠规则：标题按模板归一（`同意将*列为`、`公布第*批`、`(年份区间)`），同模板 ≥3 条时
只留分最高的一条，其余计数挂在「另有 N 条同模板文件」上。57 → 12 条，信息没丢。

**界面上的标签也跟着改了。** 「直接命中」原来标在每一条上，现在四层全命中，标了等于
没标。改成标在方向头上（「直接命中 6 份，其余为同类」），每条上只给落选的那些标
一个灰色的「同类」。一处汇总代替 57 个重复标签。

#### 第 3 步还有个硬约束：两个通道不能混

| 层级 | 走哪 | 为什么 |
|---|---|---|
| 本地 / 省级 | `catalog.db` 的 `items`（66,xxx 条元信息） | 多数只有标题、文号、链接 |
| 国家 | `catalog.db` 的 `fulltext`（国家 18,608 份） | 有正文，能引到条 |
| 南京 / 江苏 | 同一张 `fulltext`（3,166 份，key 前缀 `lf`） | 有正文，能引到条；查国家层时必须排除它们 |

`items` 表里 `admin_level='国家'` 只有 330 条——国务院政策文件库当时只把一部分清单
写进了 items。拿「国家」去 items 查，会得到「只找到 1 条」的假象，而界面上看起来
像「库里没有」。这个坑是实测踩到的：第一次跑「国家政策」方向只返回 1 条，
《历史文化名城名镇名村保护条例》没出现，而它明明在库里、有全文、能逐条引。

#### 第 4 步：勾选就是标注

人在这里做的事是三件：勾上要用的、勾掉不要的、补一个方向。这三件都不需要额外
说明理由，**行为本身就是数据**：

| 信号 | 含义 | 用来改什么 |
|---|---|---|
| `drop` 系统推荐了但没勾 | 召回不准，关键词太宽 | 收窄这个词，或降它的权重 |
| `add` 系统没勾但勾了 | 召回不全，或分档判错 | 放宽这个词，或调分档规则 |
| `task_empty` 整个方向 0 条 | 数据没有，或词不对 | 补数据，或换词 |

一个方向给 20 条候选、用户只勾 3 条，那 17 条为什么被丢，比任何离线评测都真实。

默认勾选也不是「全选」或「按分数取前 N」。规则是：
**每个方向先拿 1 条直接命中的（不管有没有正文），再补 2 条有正文的。**
只按有正文选，会漏掉《南京历史文化名城保护条例》这种直接命中却只抓到目录的核心
依据；只按直接命中选，会全是只有标题的条目。

#### 第 5 步：报告的五段结构

不是一段流畅的散文，是五段固定内容（2026-10-24 由四段扩为五段）：

| 段 | 回答什么 | 为什么单独成段 |
|---|---|---|
| 判断 | **第一句给出立场**：能做 / 不能做 / 有条件能做（条件是什么） | 使用者第一眼要的是判断，不是资料。「需要根据具体情况判断」等于把问题退回去 |
| 依据 | 按约束性质分三档：硬约束 / 程序义务 / 可争取的空间 | 不按文件层级罗列。第三档最有价值——它是方案的余地所在 |
| 路径 | 2—4 条路子，每条写清审批层级、周期、代价 | 这一段决定这份东西有没有用。按「代价从小到大」排，不按「效果从好到坏」 |
| 缺口 | 哪些方向没找到依据、意味着什么 | **最有用的部分**：只给已有的，用户仍然不知道边界在哪 |
| 下一步 | 动作级建议：办什么事、找谁、拿哪条去说 | 「加强学习」「高度重视」不算建议 |

「判断」段为什么必须给立场：上一版是「结论 + 依据梳理」，读起来像一份整理过的资料，
而不是一个同行的判断。第一句不表态，后面写得再全，用户仍然要自己下决心——
那这个工具就只是个搜索框。

**「依据」段有一个硬规矩：只写有正文的文件。** 只有目录的文件（B 类）不许进依据段，
哪怕标题看起来最切题——它回答不了「哪条约束管着我」，只能说明「世上存在这么一份文件」。
这类文件写到「缺口」段去，写成「《某文件》本库只有目录、无正文，需调取原文核实」。

这条规矩是被实测逼出来的。上一版提示词为了防止模型对着标题编内容，允许它写
「从文件名称看，该文件针对的是…」。结果生成出来的依据段里混进了三条这种句子：

> 据《市政府办公厅关于印发南京市城市更新试点实施方案的通知》（宁政办发〔2022〕15号），
> 该文件已由南京市政府办公厅发布，从名称看针对城市更新试点的工作安排。

「文件名叫这个名字，所以它是关于这件事的」——零信息量，且把前面真条文的分量一起拉低。
宁可 5 条真条文，不要 6 条真条文 + 3 条凑数。

**「判断」段还有一个时间基准问题。** 模型不知道今天是哪天。实测它读到
《南京历史文化名城保护条例》「本条例自 2026 年 7 月 1 日起施行」，
就写「该条例 2026 年 7 月 1 日才施行，项目若在此之前报批适用 2010 年版」——
而当时已经是 2026 年 10 月 24 日，新条例生效近四个月。对一个做时效判断的系统，
这是硬伤。修法是把 `date.today()` 直接写进提示词的输入里，并明确要求：
涉及施行日期先跟今天比，已过施行日就按现行有效写，不要再提过渡期。

「缺口」这一段的实际效果，看南京那一问的输出：

> 市级层面未获取《南京历史文化名城保护条例》正文，无法确认其对老门西门西街区的
> 差异化管控要求（如允许更新方式、功能兼容条件、审批豁免情形等），报审前需调阅
> 正式文本并核验条款效力。
>
> 市级未检索到针对「老门西」专项编制的历史文化街区保护规划（仅有总统府街区规划），
> 该街区法定保护边界、核心/建设控制地带划分、建筑分类管控要求等关键空间管控依据缺失，
> 直接影响更新方案合规性判定。

这两句话不是「没找到」，是「没找到意味着什么」。这才是规划师真正需要从工具里得到的。

#### 第 6 步：埋点记的是四类信号，不是鼠标轨迹

| 类型 | 触发 | 落库 |
|---|---|---|
| `drop` / `add` | 见上表 | `pick` 表 |
| `task_empty` | 某方向 0 条 | `mark` 表 |
| `cite_fail` | 引注核验不通过 | `mark` 表，带具体哪条检查失败 |
| `low_trace` | 依据段逐句回查 < 60% | `mark` 表 |
| `gap` | 报告「缺口」段的每一条 | `mark` 表 |
| 用户手动 | 「不相关」按钮、补方向、想看更多 | `mark` 表，kind 不同 |

界面右上角显示「本次留痕 N」，展开能看到这一次留下了什么——**留痕本身可见，
才有可能被用来改东西**。写进日志文件的东西没人看。

`python app/trace.py --report` 按「哪条指令最常空」「哪类文件最常被丢」聚合。

### 三 · 核验层：判据从「查表」改回「查原文」

上一版把 `kb.db` 的 980 MB 当成代价，也把核验层的问题理解成「表不够多」。这一版
把判据换了一遍，四项检查的覆盖面全变：

| 检查 | 上一版判据 | 覆盖 | 这一版判据 | 覆盖 |
|---|---|---:|---|---:|
| C1 条号越界 | 查条数表（8 部） | 0.04% | 回原文搜「第X条」+ 条级索引 | **100%** |
| C2 引文查不到 | 查全文 | 22.1% | 查全文（不变） | 22.1% |
| C3 时效违规 | 人工台账 + 源端标记 | 3.8% | 全量失效台账（四态） | **100%** |
| C4 名称错配 | 8 部精确 + 全库模糊 | 8 部 | 全库标题匹配 | **100%** |
| C5 所问法规划界 | 规则 | 100% | 规则（不变） | 100% |

**C1 能到 100%，靠的不是把条数表建满，是把「不分条」也做成一条判据。**

实测：21,774 份里只有 2,198 份（10.1%）有条款结构，切出 **119,640 条条文**；其余
**19,576 份（89.9%）全篇不分条**——意见、通知、批复、函，本来就没有「第X条」。
对后者，任何条号引用都是编造，这个判据比条数表更硬：条数表只能说「没有第 108 条」，
这里能说「这份文件根本没有条」。

**失效台账做成了全量四态。** 21,774 行，一行一份：

| 状态 | 份数 | 界面怎么写 |
|---|---:|---|
| `repealed` 已废止 | **795**（源端标记 702 + 后代文件正文点名废止） | 「已失效，由《XXX》宣布废止」 |
| `superseded` 旧版本 | **29** | 「这是旧版本，已被《XXX》（2025-03-24）取代，引注应改用新版」 |
| `no_signal` 未见废止记录 | **20,950** | 「未见废止记录：全库 21,774 份正文均未点名废止该文件」 |

还有 66,692 条目录层文件判 `unknown`（只有标题、没有正文），界面上如实写「时效需回源确认」。

废止关系的来源是把 21,774 份正文扫一遍，抽出 **2,933 条废止/修订关系边**，
其中 466 条在库内匹配到了被点名的文件。

**抽取按句子语法判宾语，不按「最近的两个词」判。** 这条规则是被真实误判逼出来的：
「根据《土地管理法实施条例》有关规定，经省人民政府研究，决定废止《江苏省征地补偿安置
争议协调裁决办法》」——按距离判会把《土地管理法实施条例》这部核心上位法标成失效。
现在按中文废止句的四种语序认宾语，加三道拦截（依据词 / 模态词 / 代词指代）。
另外两条硬规则：单文件修改决定不判时效（它废的是旧版，库里同名的是新版）；
同名法规有新版入库、旧版直接判 `superseded`（同名法规不可能同时有效）。

**「未见废止记录」不是「未知」，是一个有依据的判断**——依据是把全库都读过了。
写 `unknown`，用户会当成「大概有效」；写「未见废止记录」，用户知道这是我们查过的结论。

### 四 · 核验在撰写之后，但不是自证

核验分三档，界面用三种颜色：

| 档 | 含义 | 界面 |
|---|---|---|
| `verified` | 有正文，条号/引文/名称都对得上 | 绿色，可照抄 |
| `unverifiable` | 只有目录条目，能确认文件存在，不能确认内容 | 灰色，标「未核内容」 |
| `failed` | 有正文，但条号不存在 / 引文查不到 / 引错文件 | 红色，必须改 |

**`unverifiable` 不参与降级。** 它是数据的边界，不是内容的错误。南京这一问里，
15 处引注中 6 处是 `unverifiable`——意味着南京和江苏的文件我们只拿到了标题。
把这种情况说成「报告有问题」是错的，说成「这几份文件要回源确认」才对。

强度按**错的比例**定，不按「有没有错」定。15 处里 1 处引文被改写，和 15 处里 8 处
条号不存在，对使用者是完全不同的两件事：前者改那一句就行，后者整篇不能用。

#### 核验器自己也会错，这一版修了五个

1. **引文按句首配对 → 按就近配对。** 一句话里常有「以『留改拆』为主」这类术语引号，
   它排在前面，于是一条逐字照抄的引文被配给了一个两字术语，C2 拿它去原文搜，
   必然判「引文查不到」。改成取「这条引注之前、同句之内」最近的一个引号。
2. **标题模糊匹配没有门槛。** `kb.db` 里有一份标题就叫「通知」的脏记录，任何以
   「…的通知」结尾的目录标题都会命中它，于是「南京市城市更新办法」被判成「有正文」，
   核验时又报「实际是《通知》」。一个脏标题能让整份报告的核验结论失真。
   加长度和覆盖率约束后消失。
3. **逐句回查算全篇。** 结论和「下一步」本来就是判断和动作，该用自己的话写；
   拿它们算「有出处比例」会稳定得到 0.3，然后天天报警，最后没人看这个指标。
   现在只算「依据」段。
4. **C4 只认《》，不认〈〉。** 引一份「公告的标题里又套了一份文件名」时，模型写
   `《…发布〈国土空间历史文化遗产保护规划编制指南〉等2项行业标准的公告》`——
   内层用 〈〉 是对的，而 C4 归一化只剥《》（），于是名称完全正确的引注被判「名称
   对不上」。这是核验器自己制造的假阳性，比漏报更坏：它会让用户从此不信核验结论。
   归一化补齐 〈〉、[]、【】 后消失。
5. **聚合保留了「第一次」的明细。** 同一份文件同一处引用出现三次时，聚合只记次数；
   如果第二次才判失败，红条上挂的仍是第一次「五行全绿」的明细——界面说它错了，
   点开却找不到错在哪。改成失败那次覆盖明细。
   顺带修了强度口径：按「错了几条」定，不按「错了几次」定。同一句话引三次、三次
   都错，要改的是一句话，不是三处；拿出现次数当分母会把「改一句」说成「整篇不能用」。

#### 还有一处不在核验器里，在提示词里

三条 C2 失败全是同一个模式：模型把概括写进引号。原文是「严格控制大规模拆除」，
它写成「不大规模拆除、不大规模增建、不大规模搬迁」——读起来更像总结，但它加了
引号，就成了伪造的引文。

原来的提示词只说「原话照抄不改写」，不够。改成分两步，并给一条出口：

> 引号里必须逐字照抄，不许概括、不许合并、不许改标点。**做不到就别加引号**，
> 用自己的话写——没有引号不算引文，核验也不会拿它去比对。

关键是那条出口。只堵不疏，模型要么硬编引文，要么不写依据；给了「不用引号也能写」
这条路，它才会在没把握的时候退回自己的话。

实测效果（同一句问题）：改前 9 处引注里 3 处是假引文、判「需修正」；改后 4 处引注
全部逐字可核、判「部分可核」。引注数少了，但每一处都能照着抄进文件里。

#### 一个还没解决的

「依据密度」这个指标的合理下限还不清楚。南京那一问同一句问题连跑五次，依据段分别是
50%、55%、70%、33%、43%——**同一个模型、同一份资料、同一个提示词，波动 37 个百分点。**
条文类问题（「条例第三十三条讲什么」）能稳定到 90% 以上。

所以它现在只能当**预警**用：低于 60% 落一条 `low_trace`，不直接降级结论。
一个波动这么大的指标，用它判合格线，等于用噪声当裁判。

要让它能用，得先回答一个更小的问题：**「依据段里一句话有没有出处」这个判定本身
可靠吗？** 现在的做法是拿 10 字窗口去原文里搜，搜到就算有。这会把「把三条并成一句
写」判成无出处——而那恰恰是好的写法。在没解决这件事之前，不加权重、不设硬门槛。


## 2.4 两道闸门（本项目的核心设计）

### 2.4.1 为什么必须是两道

因为它们防的不是同一种错。

- **闸门 1（话题级）** 防「答非所问」：库里根本没有这个话题，模型硬答。
  判据是「实体落地」与「标题吻合」——不是分数阈值，分数跨查询不可比。
- **闸门 2（条文级）** 防「答得像但引错了」：话题对、文件对、条号错。
  判据是字符串比对和原文查找。

只有闸门 1，会漏掉「引了库内另一部同名法规」这类错（它的检索分数很高）；
只有闸门 2，会在「库里完全没有这个话题」时无从下手——检索出来的东西本身就不该被引。

**闸门 1 不通过时不生成。** 这不是省一次模型调用，是这条产品线的核心主张：
库答不了的时候，「答不了」本身就是交付物。上一版只是显示「闸门 1 不通过」然后照样生成，
那道闸门就形同虚设。

### 2.4.2 闸门 2 的五项检查

| 检查 | 判据 | 失败后果 | 在 1.86 万份上的可用性 |
|---|---|---|---|
| C1 条号越界 | **回原文搜「第X条」**（条级索引 119,640 条，再回全文兜底） | 依据不通过 | **100%** |
| C2 引文查不到 | 引用文本在原文中找不到（≥70% 吻合判「改写」而非编造） | 依据不通过 / 降为存疑 | ✅ 有全文就能查 |
| C3 时效违规 | 全量失效台账（四态：已废止 / 旧版本 / 未见废止记录 / 目录层未知） | 拦截该依据 | **100%** |
| C4 名称错配 | 全库标题匹配（含「地方版 vs 中央版」专项判断） | 提示名称有误 | **100%** |
| C5 所问法规划界 | 引用了不在问题范围内的法规 | 提示超出范围 | ✅ |

**C1 的判据改动值得单独说。** 上一版是「条号 > 条数表」，把 8 部法规的条数抄在
`article_counts.json` 里，只能核 0.04%。这一版改成回原文搜：全文在库，搜索就是判据。
更关键的是，它顺带把 89.9% 全篇不分条的文件也纳入了判定——对这类文件，
**引用任何条号都是编造**，这个判据比条数表更硬。

C5 的诞生过程值得单独记：66 题在 Dify 链路上一次没犯的错——模型把库内《呼伦贝尔市城市市容和
环境卫生管理条例》当成用户所问的库外《城市市容和环境卫生管理条例》，C1–C4 全部通过——
换成直连 `qwen-plus` 第一次跑就复现了。

**它证明的是：写在提示词里的硬约束，可靠性跟模型绑死；搬进规则层才成立。**

### 2.4.3 判据缺失时的行为，比判据存在时更重要

| 缺什么 | 对应检查 | 正确行为 | 错误行为 |
|---|---|---|---|
| 原文（目录层条目） | C1/C2 | 标「仅目录，无正文可核」，不得引用 | 默认通过 |
| 废止记录 | C3 | 写「未见废止记录」并说明查过全库 | 默认「现行有效」，或含糊写「未知」 |
| 名称映射 | C4 | 只做字符串相似度，标「疑似」 | 判「名称正确」 |
| 模型没给引注 | 全部 | **逐句回查**替代，用依据密度定量 | 当作「无问题」放行 |

**判据是「没抓到不能伪装成没问题」，同时「没查到不能伪装成查过了」。**
这条原则在数据层同样适用：38% 的门户抓不到，界面上必须写「该级未覆盖」，
不能留白——留白会被读成「没有」。

## 2.5 检索：16.7 万块上的实测

2026-10-20 实测。**两层分开测，因为它们用的是两套索引，性能不是一个量级：**

全文层（`kb.db`，FTS5 + 2-gram，196,343 块）：

| 查询 | 耗时 | 首条结果 |
|---|---:|---|
| 历史建筑 修缮 | **5 ms** | 《历史文化名城名镇名村保护条例》第三十三条 |
| 征收补偿 标准 | **6 ms** | 《关于在超大特大城市积极稳步推进城中村改造的指导意见》 |
| 城市更新 补偿 | **9 ms** | 《城市更新"十五五"规划》 |
| 老旧小区 改造 | **35 ms** | 《关于加强城镇老旧小区改造配套设施建设的通知》 |

目录层（`catalog.db.items`，LIKE 扫 6.5 万行）：

| 查询 | 命中数 | 耗时 |
|---|---:|---:|
| 征收补偿 | 2,037 | 110 ms |
| 城市更新 | 2,438 | 118 ms |
| 历史文化保护 | 2,694 | 123 ms |
| 老旧小区 | 273 | 265 ms |

全文层返回的字段：`title / label（条号）/ snippet（原文片段）/ doc_no / published / url / issuer / score`。

**「历史建筑 修缮」那一条值得看细节**：它返回的原文是「历史建筑的所有权人应当按照保护规划的要求，
负责历史建筑的维护和修缮」——这是能直接写进报告的一句话，带条号和链接。这是「可溯源」的具体样子。

**目录层那 110–265 ms 是这套做法的上限。** 它靠 `LIKE '%…%'` 扫全表，规模再涨一个数量级就必须换 FTS。
现在 6.5 万行是它还能用的最后一段；这也是「不再盲目扩库、先把核验层补上」的一个技术理由。

**一个已知缺陷**：命中的 `label` 有时会带上一块的尾部，形如
「（五）建筑的测绘信息记录和相关资料。 第三十三条」。原因是按 1,500 字切块，没有对齐条边界。
它现在不影响人读，但会影响 C2（拿 label 去做引文比对会误判）。修法在 FR-03 里。

**为什么用 2-gram 不用 trigram**：FTS5 的 trigram 要求查询 ≥3 字符，「征收」「补偿」这类两字词直接失效，
而这两个词恰好是政策检索里最高频的。所以自己切 2-gram，查询侧同样切，用 unicode61 索引。

### 检索范围三档（2026-10-24 新增）

库有边界，但用户不知道边界在哪。所以把「查哪儿」交给用户，三档：

| 值 | 行为 | 实测耗时 | 适用 |
|---|---|---|---|
| `kb` | 只查本地库 | 约 1.0 秒 | 默认。南京、江苏、国家级够用 |
| `both` | 库优先，某方向有正文不足 3 份才联网补 | 10—40 秒 | 库外城市（广州等） |
| `web` | 不查库，只现抓政府站 | 20—40 秒 | 验证库里没有的东西 |

`both` 刻意**不做全方向联网**：8 个方向各抓一轮要一分多钟，而库内已经有 6 份带正文的
方向再抓一遍纯属浪费。联网在这套系统里唯一站得住的位置是「补缺口」。

### 联网通道：为什么最后没用搜索引擎

这是本项目踩得最深的一处。原本的设想是「库内没有就搜一下」，实测四条路全断：

| 通道 | 结果 |
|---|---|
| 必应 | **无视 `site:` 约束**。搜 `site:www.gz.gov.cn 城市更新`，首两条是国务院文件，一条广州的都没有 |
| 搜狗 | 反爬，直接空响应 |
| 360 | 结果链接加密，拿不到真实 URL |
| 百度 | 裸请求返回 1.4 KB 拒绝页 |

`site:` 在商业搜索引擎里是**倾向，不是约束**。要硬约束只能本地做域名过滤，
但那样召回量会掉到个位数——因为搜索引擎已经把大部分结果换掉了。结论：
**公开搜索引擎不能作为政务文件的检索源。**

改用两条通道：

1. **城市政策库 JSON 接口**。广州的 `gz_gfxwjk` 自报 6,989 份，翻页拿全，带文号、
   施行时间、源端自己的时效标记（有效 / 失效 / 失效（提前废止））。
   这份标记比我们从正文反推的台账硬——台账是「全库没有一份文件提到它被废止」，
   源端标记是「发布机关说它失效了」。
2. **现探门户栏目**。复用离线采集那套 `probe_site`，按已知栏目路径抓列表页。

两条都不经过搜索引擎，所以「搜不到」不会再伪装成「没有规定」。

**三条硬规矩写在 `app/websearch.py` 文件头**：只收政府域名、抓不到正文不算数、失败要说话。

### 已知拿不到的城市：把它做成一句话，而不是一次探测

**合肥**。市政府门户全站返回 HTTP 521 + 加速乐 `__jsl_clearance` 校验。
实测过程写在这里，免得以后有人再走一遍：

1. 拦截页是一段字符串拼接脚本，形如 `('_')+('_')+('j')+('s')+('l')+...`，
   用 node 的 `vm` 托管一个假的 `document` 就能算出第一层
   `__jsl_clearance_s=1792812634.26|-1|sTVciG%2B4duuyCNvcS18FlMYdZFo%3D`。
2. 带上它再请求，响应码仍是 521，但**内容从 850 字节变成 22—46 KB**——
   说明页面已经给出来了，只是状态码没改。同时它会下发 `__jsluid_s` 会话标识。
3. 两个 cookie 一起带（必须用 cookie jar，手动覆盖 `Cookie` 头会把
   `__jsluid_s` 冲掉），第二轮拿到的是 `_0x382b` 数组加 base64 的第二层混淆脚本，
   需要完整的 `window` / `navigator` / canvas 环境才能执行。

到这里停。第二层是持续对抗：源站随时可以换算法，绕过它换来的稳定性不值这个成本，
而政务数据本身也不该靠破解拿到。

所以改成**配置化短路**：`BLOCKED_SITES` 里写一条，`search()` 在算完 `place`
之后立刻返回原因，0.00 秒，不探测、不浪费预算。界面上用橙色阻断框显示
「**看不到，不等于没有**」——这句是重点。放进灰色空状态里，用户只会读成
「合肥确实没这方面政策」，而我们根本没看到那个站。

**一个做合规判断的系统，把「看不到」说成「没有」，是最不该犯的错。**

### 整库抓取：源端的总数会变，别拿它当结束条件

广州库第一次自报 6,989 份，隔几小时再问变成 6,209 份。差 780 份，不是我们抓漏，
是源端在调（文件下架或换批次）。

所以 `list_all()` 的结束条件是**翻到空页**，不是「已抓条数 ≥ total」。
`total` 只用来显示进度。

配套的三个坑，都是实测踩出来的：

| 坑 | 表现 | 处理 |
|---|---|---|
| `json_ext` 不一定是对象 | 第 116 页有一条「政策解读」是 `[]`，`ext.get()` 抛 `AttributeError`，进程死在第 1,515/6,989 条 | 非 dict 一律当空元数据 |
| 单页失败直接 `continue` | 那一页 20 条永久消失，而后台任务没人会发现 | 失败页收进 `again`，主循环后补抓两轮 |
| 用 `len(batch)` 推进页码 | batch 被 `stop_at` 过滤过，长度变短，页码往回退、同页反复抓 | 推进到窗口末尾 `window[-1] + 1` |

并发实测：单页稳定 11 秒，但那是 TLS 握手与等响应的开销——4 页并发 3.25 秒跑完，
串行要 44 秒。这个站对同一 IP 的并发不友好（6 页并发实测反而 57 秒），
所以并发度保持 4，靠补抓兜住偶发失败。

### 上海：换了一种数据源形态

广州是 GET + JSONP，字段埋在 `json_ext` 里还要按 `_gz_zcwjk_` 前缀取。
上海是 **POST + 扁平 JSON**，两个接口：

```
POST /gwk/policy/page     {pageNo, pageSize}      列表，pageSize 上限 150
POST /gwk/policy/detail   {businessId, siteId}    详情，正文在 txt 字段
```

数据比广州好一档：除文号（`docType` + `docYear` + `docNo` 三段要拼）、
施行/失效日期外，还带 `effectiveFlag` 源端时效、`evolutionList` 沿革
（这份文件取代了哪一份）、`relates` 关联的政策解读。

**两个会让抓取「成功但全错」的坑：**

1. **分页参数名是 `pageNo`，不是 `pageNum`。** 写错时接口**不报错**，
   静默忽略、永远返回第 1 页。表现是「翻了 106 页只拿到 95 条」。
   第一次跑就是这样——靠 url 去重才没入库一万条重复数据，
   否则会显示「入库 10,000 条」而实际上全是同一页的 95 条。
   现在 `list_all()` 有闸：连续 3 页零新增就中止并报警。
2. **详情必须同时给 `businessId` 和 `siteId`。** 只给 businessId 时接口返回
   `{"msg":"success","code":0,"data":{}}`——**成功但空**。这个形态最容易被
   误判成「这份文件本来就没有正文」，从而白白丢掉整批正文。

速度差很多：详情接口 **0.17 秒/条**（正文在 JSON 里，不用抓 HTML 再抽），
比广州抓正文页的 0.4—0.8 秒快三倍；列表 100 条/页、69 秒翻完 107 页。

正文是 HTML 片段（不是整页），`extract()` 能直接吃，段落和
「第一条（目的和依据）」这类结构都保留得住。

**目录层原有的 10,235 条上海条目来路不明**：它们的 url 是
`zhengce/list#<hash>`，但该 hash 与接口的 `businessId` 交集为 0，
且抓下来全是同一个 4,423 字节的 SPA 框架页、正文 0 字。
所以上海没有去挂接这批旧目录，直接用接口重建——数据更全，还能顺带拿到
时效和沿革。列表里混着 `test_` 开头的测试记录，必须过滤。

**一个必须记住的坑**：`www.gz.gov.cn` 的证书配置老旧，默认 SSL 上下文会卡在旧版重协商上，
裸 `urllib` 稳定挂死 30 秒。必须用 `net.get(insecure=True)`。之前在江西、安徽、海南、湖南
四个站上踩过同一处，注释就写在 `scripts/catalog/net.py` 里。

**限流是硬约束**：连续请求几轮后响应从 0.6 秒掉到 6.6 秒，等 45 秒才恢复。
所以正文落 `data/webcache/`，TTL 7 天，只缓存成功结果。

### 一块正文切不出条文，整份就废了

在线抓回来的正文常是「一段话到底」——容器里只有文本节点和 `<br>`，抽出来两万字一行。
`split_blocks` 会把整份当一块、`n_art=0`，于是一份根本没被读过的文件被判成
`unverifiable`。实测《广州市城市更新办法配套文件》19,149 字切成 1 块、0 条。

修法是 `_resplit_long_lines`：只在「条号前紧跟句末标点或空白」时断行，
避免把「按照第三条规定」劈开；「第一章 总则第一条」挤在一起的要先把章标题剥掉再断。
修完同一份文件变成 91 块 91 条。

### 「有 19 条」和「有 19 条能引」是两回事

案例方向实测 19 条，其中 16 条正文 0 字（只有目录）。列表填满但一条条文都引不出，
用户会以为这一层查到了。所以每个方向多返回两个字段：

- `n_usable`：正文字数 ≥ 800 的条数，即真正能引出条文的
- `note`：这一栏为什么空、为什么只有标题

界面上 `19 份` 旁边必须显示 `其中 0 份有正文可引`，列表上方必须显示 note。

## 2.6 评测体系与它的偏斜

### 现状

66 题：L1 基础 12 / L2 推理 8 / L3 边界 6 / L4 对抗 40。

**两个偏斜，一个比一个严重：**

1. **对抗题占 60.6%**。真实使用里不会是这个比例。它测的是「这套系统有多难被打穿」，
   不是「正常使用中有多好用」。拿它当验收依据，会得出一个漂亮但错位的结论。
2. **v3 新增：全部 66 题都测核验层，没有一题测发现层。** 也就是说，「清单全不全」
   「覆盖度报得准不准」「仅目录条目有没有被误当依据」这三件事，**一次都没被评测过**。
   而它们占了产品价值的一半以上。

### 该怎么做

| 项 | 规格 |
|---|---|
| 规模 | 120 题门槛 / 200 题目标 |
| 能力维度 | 基础 25% / 推理 30% / 边界 20% / 对抗 25% |
| 难度 | 简单 30% / 中等 45% / 复杂 25% |
| **目标数据层** | **目录层 / 全文层 / 核验层，三层都要有题** |
| 样本来源 | 真实提问 50%（必须非本人提供）+ 稿件引用 30% + 对抗 20% |
| 标注 | 2 名规划师交叉复核，本人只仲裁 |

第二行和第四行是 v3 加的。**「必须由非本人提供」是硬要求**：出题人、判分人、被考核对象
是同一个人的时候，测的是「我有没有按我的预期实现」，证明不了「这东西对别人有用」。

## 2.7 十条判断

这一轮把库从 4.19 万条扩到 85,300 条之后，值得记下来的判断：

1. **扩容解决的是「有没有」，不是「准不准」——但「准不准」不一定要靠表。** 抓了 1.86 万份之后，
   我以为要先建 1.86 万张条数表才能核；实际只要把判据从「查表」换成「查原文」，覆盖率当天就从
   0.04% 变成 100%。**数据补上之后，旧判据往往已经过时了，只是没人回头看它。**
2. **一个产品里最危险的状态不是「错了」，是「错了但看起来正常」。** 编造的条号和真实的条号在界面上长得一样；
   未抓取的省和没有文件的省在清单上长得一样。这两个「一样」是本产品存在的全部理由。
3. **「未知」是第一等公民，「未见」比「未知」更有用。** 96% 的文件没有被任何文件点名废止，
   这件事该写成「未见废止记录」，不是「未知」——前者是我们查过的结论，后者是我们没查。
   75.1% 的条目没有文号，同理：界面要写「列表页未给文号」，不能留空。
4. **能被机器判定的部分要尽量大。** C1–C5 现在全部可判定，但它们的判定价值不一样：
   查索引和比字符串是可复现的，模型判断不是。所以核验只用前一种，一种都不留给模型发挥。
5. **抓取的天花板不在技术，在经济。** 946 个站抓不到，逐个挖接口是 20–40 分钟一站，上限 40 小时。
   而上海一个接口就是 10,235 条。**先找大站，别按地域顺序啃。**
6. **目录的完整性和全文的可引用性是一次权衡。** 66,692 条目录 vs 18,608 份全文。
   全抓正文是 5,000 万字 + 一张维护不了的台账。按专题装配 50–80 份才是可控的。
7. **规则层的价值随库增大而上升，模型的价值随库增大而下降。** 库越大，模型越容易「看着像」，
   而规则不受影响——它只查表。
8. **评测集的偏斜比模型能力更影响结论。** 66 题全测核验层，等于没测发现层。
9. **人工确认是唯一的真成本，人力是唯一的瓶颈。** token 成本 10 人团队月 ¥16.2，可以忽略。
10. **不该承诺的别承诺。** 不说「覆盖全国」，不说「全库时效已核」，不说「法律条文齐备」。说清楚的缺口比藏起来的缺口安全。

## 3.5 这一轮踩的坑

**抓取侧（都会导致整站归零，且看起来像「这个站没有文件」）**

1. `title=""` 空属性吞掉整条标题——绍兴嵊州 97 个链接标题全为空，漏斗在「长度 ≥ 8」归零。
2. `_HREF_OK` 只认 `.html/.shtml`，排除掉所有无后缀详情页（塔城 `/zfxxgk/zc/gfxwj/…`、淮南 `?catId=…`）。
3. 「政府公报」与政策文件库同权重，还因 URL 含 `zfgb` 加分，挤掉真入口（邢台、铜川、东营、开封整站抓成公报期号列表）。
4. `find_next` 在 `index.html`（页码 0）时返回自身，翻页自环——浙江 20 页只拿到 38 条。
5. meta refresh 空壳（陕西 311 字符）、iframe 里的列表（山东外层只有 11 个导航）都要跟。
6. 超时写死 60 秒是因为江苏 jpage 单页要 19.8 秒，但县级 1,775 站会被拖到几小时。改默认 20 秒，jpage 单独 60。
7. 分页参数无效时每页都返回首页——必须早停（「这一页没有新条目就收手」）。

**接口侧（这些是「接口能调通但不给数据」）**

8. 上海 `pageNum` 不报错，但永远返回第 1 页；必须用 `pageNo`。
9. `p.so-gov.cn` 的 `pageSize` 被钉死 20，翻到约 30 页后静默重置回第 1 页，`startDateStr`/`C1` 只改 `totalHits` 不改结果集——单查询上限 600 条，做不成目录。
10. 福建真正的入口在 SaaS 底下的 TRS WAS5：`/was5/web/search?channelid=N&templet=docs.jsp&searchword=` 直接返回 JSON，自带 `fileno` 发文字号。按文号前缀分片（闽政 7,571 → 闽政办 2,846 → 政府令），147 秒取回 6,340 条。
11. `channelid` 只能从站点自己页面的 `<input name="channelid">` 取，猜不出来；**识别到不等于能用**——青海的 WAS5 对匿名请求回 TRS 错误页。

**解析侧**

12. 老页面正文不到 800 字符时会被截成 34 字（短批复），且长得像「抓取成功」。
13. 中文占比 0.25 的线太高——8,000 字的批复大量条款编号，占比只有 0.21，被判垃圾。降到 0.12。
14. Word 导出的 `<td>` 能到上千字符，正则 `<[^>]{1,400}>` 剥不掉，CSS 漏进正文。改成 `<[a-zA-Z/!][^<>]*>` 并先剥 `style/class`，同一份从 34 字回到 21,440 字。
15. 精确容器（`id="UCAP-CONTENT"`）不要再做密度校验——Word 页面每个字包在几百字符的 `<span style>` 里，会误杀一半。

**数据侧**

16. 福建首抓 6,340 条里 1,293 条是人事任免、表彰、政协提案答复函——都有正规文号，但拿它当政策依据比找不到更糟。过滤放在 `save()` 一处（`_NOISE_TITLE`），全库清掉 3,558 条（5.2%）。
